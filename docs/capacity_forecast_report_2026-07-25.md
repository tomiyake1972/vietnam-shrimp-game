## 1. 85.5% の実効率は、コード上のどこから出ているか

| 項目 | 実体 |
|---|---|
| 関数 | `calculateFactoryEffectiveCapacity(factory: Factory): FactoryEffectiveCapacity` |
| ファイル | `app/lib/v2/production/capacity.ts`（30行目〜） |
| 内部ヘルパー | `applyRates(nominal, baseUtilizationRate, equipmentAvailabilityRate)` = `nominal * baseUtilizationRate * equipmentAvailabilityRate` を `roundHosoEqTons`（小数2桁）で丸める |
| 補正要因① | `Factory.baseUtilizationRate: Ratio` — 「基準稼働率（0〜1）。計画上の標準操業度。」（`app/lib/v2/production/types.ts:66`）。BAL の値 = **0.9** |
| 補正要因② | `Factory.equipmentAvailabilityRate: Ratio` — 「設備利用可能率（0〜1）。故障・保全等による可用性。」（同 `:68`）。BAL の値 = **0.95** |
| 設定箇所 | `app/lib/v2/companyLab/fixtures.ts:28-29` の `factory()` ヘルパーで `ratio(0.9)` / `ratio(0.95)` |
| 計算 | **0.9 × 0.95 = 0.855 = 85.5%** |

**エンジンに存在する補正要因はこの2つだけです。** 人員充足率・設備立ち上がり・品質リスクといった「実効能力そのものを削る係数」は `calculateFactoryEffectiveCapacity` には存在しないため、画面にも作っていません（人員と品質は別段階の制約として後述の⑤や品質処理で効きます）。

また、能力プールごとに異なる補正値は存在せず、1つの工場の5プールすべてが同じ2要因を掛けます。`factory.status !== "active"` の場合のみ、5プールすべてが 0 になります。

### BAL-F1（2015Q2 時点）の実効率テーブル

| 能力プール | 名目能力 | 実効率 | 実効能力 | 補正要因 |
|---|---:|---:|---:|---|
| 共通前処理能力 | 22,000 t | 85.50% | 18,810 t | 基準稼働率0.9 × 設備利用可能率0.95 |
| HOSO加工能力 | 10,000 t | 85.50% | 8,550 t | 同上 |
| PD加工能力 | 8,000 t | 85.50% | 6,840 t | 同上 |
| VAP加工能力 | 6,000 t | 85.50% | 5,130 t | 同上 |
| 冷凍・保管能力 | 20,000 t | 85.50% | 17,100 t | 同上 |

画面では `実効率 = 実効能力 ÷ 名目能力` として表示しているため、丸めによって「名目 × 表示上の実効率 ≠ 表示上の実効能力」に見えることはありません。

## 2. ご指示との差異：実際の制約適用順序

ご指示では「共通能力 → 商品別能力 → 凍結・包装能力」と書かれていましたが、`allocateProductionPlans`（`app/lib/v2/production/allocation.ts`）の実装は次の順序です。**冷凍・包装が商品別設備より先**に効きます。実装のとおりに表示しています。

1. 原料在庫（自社プール、`status === "available"` のロット、HOSO換算原料ベース）
2. 工場共通処理能力（工場プール、原料投入ベース）
3. **冷凍・包装能力**（工場プール、完成品ベース）
4. **商品別設備能力**（工場×商品、完成品ベース）
5. 有効労働能力（工場ワーカープール）

歩留まり（`saleableRecoveryRatio`）は②と③のあいだで**一度だけ**適用されます。現行値は HOSO/PD/VAP とも 1.00 です。

その他の確認結果：

- **優先度は数字が小さいほど高い**（`CompanyProductionPlanEntry.priority` のコメント、`production/types.ts:167`）。
- **同順位は先着ではなく比例配分**（`waterFillAllocate`、`app/lib/v2/rawMaterials/waterFill.ts`。「入力配列の順序には一切依存しない」）。使い残した上位ティアの枠は下位ティアへ繰り越されます。
- **希望量が商品別実効能力を超えた場合**は④で切り詰められ、理由は `productCapacityShortage`。
- **原料不足・人員制約も見込みに含まれます**（①と⑤）。
- **主因と補足要因**は、`shortfallReasons` の先頭を主因、以降を補足要因として表示しています。

## 3. BAL Turn 2 の処理見込み：優先順位変更の前後比較

Turn 2 はまだ確定していないため、現在案としては Turn 1 提出値と同じ生産計画（HOSO 2,200t / PD 600t / VAP 200t、優先度 1/2/3）、同じワーカー配置（正社員6,000人・残業率9%・出勤率95%・技能 HOSO0.85 / PD0.8 / VAP0.75）を使用しました。

### A. 現在案（HOSO=1, PD=2, VAP=3）

| 商品 | 優先度 | 希望量 | 商品別実効能力 | 処理見込み | 未処理見込み | 制約 |
|---|---:|---:|---:|---:|---:|---|
| HOSO | 1 | 2,200 t | 8,550 t | **2,200 t** | 0 t | なし |
| PD | 2 | 600 t | 6,840 t | **600 t** | 0 t | なし |
| VAP | 3 | 200 t | 5,130 t | **200 t** | 0 t | なし |

### B. VAP を優先度1へ変更（VAP=1, HOSO=2, PD=3）

| 商品 | 優先度 | 希望量 | 処理見込み | 未処理見込み | 制約 |
|---|---:|---:|---:|---:|---|
| HOSO | 2 | 2,200 t | **2,200 t** | 0 t | なし |
| PD | 3 | 600 t | **600 t** | 0 t | なし |
| VAP | 1 | 200 t | **200 t** | 0 t | なし |

**結論：現在案の規模では優先順位を変えても処理見込みは1tも変わりません。** 希望量の合計が 3,000t にすぎず、共通前処理 18,810t・冷凍包装 17,100t・各商品別能力のいずれにも届いていないためです。優先順位は「能力が足りないときの取り合いの順番」なので、能力が余っている限り効果はありません。

### C/D. 能力が競合する規模での比較（参考）

希望量を HOSO 8,000t / PD 6,000t / VAP 5,000t（合計 19,000t > 共通前処理 18,810t）に引き上げると、優先順位の効果がはっきり出ます。

| 商品 | C: HOSO1/PD2/VAP3 | D: VAP1/HOSO2/PD3 | 差 |
|---|---:|---:|---:|
| HOSO | 8,000 t | 8,000 t | ±0 |
| PD | 6,000 t | **4,100 t** | **▲1,900 t** |
| VAP | **3,100 t**（未処理1,900t） | **5,000 t** | **＋1,900 t** |
| 合計 | 17,100 t | 17,100 t | ±0 |

VAP を最優先にすると VAP は希望量どおり 5,000t 処理できるようになり、そのぶん PD が 1,900t 減ります。合計が両方 17,100t で一致するのは、冷凍・保管能力の実効値 17,100t が全体の上限として効いているためです（主因は共通処理能力、補足要因が冷凍・包装能力として画面に表示されます）。

**「VAP の処理可能量は約810t」といった固定値は表示していません。** 810t は「VAP が優先度3で、HOSO と PD が先に共通能力を使い切る」という特定の入力に対する結果であり、入力が変われば変わる値だからです。画面の表は常に現在の入力値から再計算され、見出しには「現在の入力に基づく処理見込み」と明記しています。

## 4. 実装の要点

- 新設した `app/v2/company-lab/processingForecastViewModel.ts` は、UI 用の簡易計算を一切持たず、エンジンの純粋関数 `allocateProductionPlans` と `calculateFactoryEffectiveCapacity` をそのまま呼びます（`allocateProductionPlans` は入力を一切変更しないと実装コメントで明言されており、見込み計算として安全に共用できます）。
- 画面（`DecisionEditor`）はレンダリング本体で現在のドラフトから再計算するため、優先度を変更した瞬間に見込みが更新されます。
- Excel の Processing Capacity シートも同じ関数の戻り値を書き写すだけで、計算を二重に持っていません（`processingCapacityForecast.test.ts` が画面と Export の値の1行単位の一致を検証）。
- 会社別ブックは自社の工場・生産計画・原料ロットのみ。GM ブック `<labId>_turn<N>_gm_databook.xlsx` を別ファイルとして新設し、全5社を会社ごとのシートで確認できます。
- テストは 22 件追加（画面側17 / Export側5）。全体で 1,474 件すべて通過、`tsc` / `eslint` / `npm run build` もクリーン。

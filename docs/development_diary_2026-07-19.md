## 3. Phase 1：市場・価格形成（`3419ee9`、統合 `e842488`）

4か国（エクアドル EC・インド IN・インドネシア ID・ベトナム VN）のHOSO FOB価格を、**Market Opening**（`openHosoMarket`：国別需給圧力L_i・世界共通圧力Gを確定するだけで価格には触れない）→**Market Clearing**（`clearHosoMarket`：L_i・G・決定論的ショックから当期価格を確定する）の二段階で算出する`calculateMarketQuarter(input, parameters, randomStream)`を実装した。

ベトナム国内未凍結原料市場は、国際HOSO価格から導く買付上限・需給調整・按分最低受注ルールを持つ、独立した市場（`vietnamRawMarket.ts`）として実装し、国際HOSO価格計算とは意図的にファイル・型を分離した（ベトナム国内市場の係数変更が国際価格計算に波及しない一方向参照）。PD/VAPプレミアムは、各国の処理能力に対するPD/VAP需要の稼働率と、国別`qualityScore`入力から算出する（特定国名をハードコードせず、データから品質優位が自然に立ち上がる設計）。

全定数は`MARKET_PARAMETERS_V1`に集約し、マジックナンバーを排除した。国別需要配分は、まだ国別供給・市場別需要が安定計算できないとの判断から、完全な数量ベースのsoftmax原産地シェア配分（仕様書§9.1）ではなく、簡略化した世界影響度ウェイト式（§9.2：EC 0.45/IN 0.25/VN 0.18/ID 0.12）を採用し、この簡略化を明示的に文書化した。新規テスト44件。

## 4. Phase 2：長期シナリオ・イベントエンジン（`0cf4b84`、統合 `f09ae24`）

国別生産能力・放養量・稼働率・生残率・疾病圧力・輸出可能比率・養殖コスト・飼料/エネルギー/人件費・PD/VAP加工能力・地域潜在需要・経済指数・消費成長・冷凍在庫・物流能力・貿易制限・供給信頼性・品質スコアという20種類の「基礎変数」を、長期トレンド＋ランプアップ/持続/回復曲線を持つイベントで動かすエンジンを実装した。

**このモジュールは価格を一切直接設定しない**ことを型レベルで強制した。`ScenarioBaseVariable`には価格フィールドが一切存在せず、「疾病→HOSO価格+10%」のような効果は仕様として書けない（コンパイルエラーになる）。

イベントの重複時合成規則も明文化した。乗算的効果（`multiplicative`、比率として扱い重複時は比率同士を乗算。例：-10%が2つ重なると0.9×0.9=0.81で-19%、単純な-20%にはならない）と加算的効果（`additivePoint`、点数として扱い重複時は差分を合算）を区別し、乗算→加算→変数域へのクランプの順で適用する。Canonical（決定論固定）モードは乱数を一切消費せず、Variationモードのみ固定順序で乱数を消費してシード再現性を保つ。情報開示レベルは`public⊂standard⊂advanced⊂gm`の累積構造とし、ゲーム終了後のみ開示される`postGame`チャネルは他レベルから厳格に隔離した。ベースライン含む5シナリオ（各8年・32ターン）を実装した。新規テスト195件（新規76件、既存を含め195件）。

## 5. Phase 3：業界シミュレーション統合テスト環境（`11ac073`＋`42015db`、統合 `11c352c`）

Phase 1（市場）とPhase 2（シナリオ）を接続し、`/v2/industry-lab`画面から32四半期を実際に回して検証できる、最初の統合実行環境を実装した。`initializeIndustrySimulation`・`advanceIndustrySimulation`（イミュータブルな状態遷移）・`runIndustrySimulation`（完走までの一括実行）の3つの純粋関数として公開した。

会社の意思決定機構がまだ存在しないため、2ターン目以降の国内調達意向は「直近4四半期の実績調達量の移動平均×係数（既定1.0）」で暫定的に代替し、この仮定を`assumptions.ts`に文書化しUIの`AssumptionsNotice`パネルに常時表示した。フォーム入力値と実行中のシミュレーション状態を厳格に分離し（入力を変えただけでは実行中の状態を汚染しない）、情報レベル別の表示はレンダリング時のフィルタではなく、レコードごとに4レベル分を事前計算して保存する構造にした（レベル間の情報漏洩を構造的に防止）。CLI（`npm run v2:simulate`）は経済ロジックを一切持たない薄いラッパーとし、CLI出力とUI直接呼び出しの結果がバイト単位で一致することをテストで確認した。

## 6. Phase 4：販売計画・営業力・契約配分・バックログ（`f9f2de8`＋`5b26b1d`、統合 `c74f7ee`）

5社が市場×商品ごとに販売計画（希望数量・価格調整・営業人員）を提出し、水位法（waterFillAllocate）で契約を配分する仕組みを実装した。営業人員はミカエリス・メンテン型の飽和曲線（`x/(x+k)`）でカバレッジ・処理能力に変換され、0人でも下限のカバレッジを持ちつつ人員を増やすほど逓減する。契約は成約時単価を固定し、まだ売上・PL・BSには一切計上しない（`SalesContract`・`MarketProductAllocationResult`に金額フィールドが存在しないことをテストで確認）。

実装から約15分後、値下げ競争の抜け穴を発見し即座に修正した（`5b26b1d`）。当時の価格競争力スコア`priceScore = exp(-priceSensitivity×(askPrice-basePrice)/basePrice)`には上限がなく、値下げすればするほど際限なく成約力が伸びてしまい、極端な安値提示＋大量の営業人員＋大量の希望数量を組み合わせれば1社が需要のほぼ全量を独占できるという非現実的な抜け道が存在した。これに対し、(1)価格競争力スコアを`[0.5, 1.6]`にクランプする飽和処理、(2)個社の成約上限に市場需要×最大供給者シェア（既定0.35）を追加、(3)将来の与信管理システムとの接続点として`approvedAllocationCap`（承認済み取引枠）を追加、という3つの独立したガードレールを設けた。値引きされた契約が成約後に単価を書き換えられないことも回帰テストで確認している（このガードレールは「いくら値下げできるか」を制限するものであり、「価格そのもの」を制限するものではない）。新規66件（既存287件＋新規66件＝353件）。

## 7. Phase 5：国内原料・輸入・養殖・原料在庫（`1136b6b`〜`3eb7d37`、統合 `5a93e43`）

Phase 4の未履行契約から必要原料量を集計する（自動発注はせず情報提供のみ）、国内買付意向をベトナム国内市場価格に接続し水位法で配分する、国別供給上限に基づき輸入を配分する（国際価格へは書き戻さない）、放養強度・バイオセキュリティ・疾病圧力から収穫量を導く単純な線形モデル、ロット単位のFIFO在庫という一連のモジュールを実装した（353→411）。

続けて、Phase 4と同種の抜け穴を発見・修正した（`da5189b`、411→418）。会社が希望数量を意図的に過大申告（例：100万トン）するだけで国内市場価格を吊り上げられる問題に対し、実効購買意向の上限（調達能力・承認済み購買上限・基準供給量×最大価格影響シェアのmin）を設けた。また、市場価格未満で入札しても取得原価を市場価格未満にはできない下限処理（`unitCost = max(市場価格, 入札価格)`）を導入した。

さらに、Phase1〜4を1ターンとして繋ぐ純粋なターン・オーケストレーター`runTurn()`（418→436）、次ターンへ何を持ち越すかを決める状態遷移層`buildNextTurnInput`（436→451、契約・原料ロットは持ち越し、販売計画・調達意向・輸入発注・養殖計画は毎ターンリセット）、永続化専用の最小状態モデルとシリアライズ契約`PersistedGameStateV2`（451→486、ターン実行IDによる二重適用防止という最初の冪等性ガードを実装）、Redis永続化アダプター（486→499、本番環境での`deleteGame`を無条件拒否する安全策を実装層に前倒しで組み込み）を、それぞれ独立した責務のレイヤーとして積み上げた。develop/v2への統合コミットは`5a93e43`。

## 8. Phase 6：工場・ワーカー・生産・完成品在庫・契約履行（`0c74f8b`〜`f589a7b`、統合 `1b5b4da`）

工場設備・ワーカー・商品別能力・原料在庫がすべて揃って初めて生産できる仕組みを実装した（499→560）。原料→共通加工能力→冷凍/梱包→商品別設備→労務という優先順位付きの制約配分を、各段階で水位法により行う。

直後（`62ab198`、560→572）、2件の実質的なバグを発見・修正した。1つ目はHOSO換算歩留まりの二重適用で、契約・原料・完成品在庫・能力はすべてHOSO換算トンという共通単位で管理しているにもかかわらず、PD（歩留り約80%）等の**物理**歩留り比率をそのままHOSO換算数量に掛けてしまい、物理的な減少をHOSO換算上の損失として二重に計上していた。物理歩留り（`physicalYieldRatio`、参照専用）とHOSO換算上の真の回収率（`saleableRecoveryRatio`、規格外・破損等のみを表す）を明確に分離し、HOSO換算の数量計算には後者のみを使うよう修正した。2つ目はワーカー重複計上で、同じ100人の労務力がHOSO・PD・VAPそれぞれについて独立に「100人分の能力」として数えられ、実質300人分の能力があるかのような計算になっていた問題を、工場ごとの有限な共有人員プールとして水位法で配分する方式に修正した。

続けて、5社の統合テスト環境（`b7f4755`、572→608）を実装した。BAL（バランス型）・MASS（大量生産・価格競争型）・JPQ（日本・品質志向型）・VAP（VAP特化型）・CONSV（保守的・財務慎重型、まだ財務諸表がないため`commitmentRestraint`という行動抑制係数で表現）という5つの検証用フィクスチャ会社を用意し、契約→調達→生産→履行の四半期サイクルを決定論的に回せる統合ランナー・CLI・`/v2/company-lab`画面を実装した。

5社規模で経済を回してみたところ、ベトナム国内原料価格が下限（$0.05）に張り付く問題が判明し、これがPhase 6.2のバグではなくPhase 3のシナリオ供給過剰ドライバに起因する構造的な問題であることを特定した（`f589a7b`、608→623）。国内買付・履行の集計が累計契約リストから誤って合算されていた問題、物理歩留りとHOSO換算歩留りの再混同、農家留保価格の導入（$2.25/kg＝養殖コスト+疾病リスク+マージン）と、それを下回った場合に価格ではなく数量を調整する仕組み、5社の買付意向だけがベトナム全体の需要を代表してしまっていた点への外部加工業者需要の追加、根拠のなかった調達能力の一律約100倍補正の撤廃と工場能力連動式への置き換え、国際HOSO価格が下限に張り付く問題（固定需要シェア配分と積分型価格式に起因）への価格応答的な需要再配分・コスト連動アンカーへの平均回帰・±35%の国別価格スプレッド上限の導入、PD/VAP最低受注プレミアムの導入、契約時点の予想原価スナップショット（`ContractCostSnapshot`）の追加など、7つの是正を1コミットで行った。persistence schemaVersionを1→2へ加算的に更新した。develop/v2への統合は`1b5b4da`（Phase 6〜6.3の4コミットをまとめてマージ）。

## 9. Phase 7A：品質・顧客信頼・納期信頼性（`efc8c7b`、`7523d4e`、統合 `9d1cef7`）

会社×商品の品質、会社×市場の顧客信頼、会社×市場の納期信頼性、会社×工場×商品の増産履歴を、ターンをまたいで蓄積するモジュールを実装した（既存のPhase 4販売配分ロジックが持っていたが未接続だった`qualityReputation`・`customerRelationship`・`deliveryReliability`フィールドへ、初めて実際の値を供給する形で接続した。配分ロジック自体は無変更）。

稼働率・残業・臨時労働比率・商品構成複雑度・原料鮮度・増産履歴の6要因からなる操業リスクスコアが、規格外（格落ち・手直し・廃棄＋重大事故）の発生率を決める。廃棄のみが実際の数量損失であり、格落ち・手直しは記録のみで完成品数量を減らさない（原料消費＝完成品数量＋加工損失、という数量保存則は維持される）。重大事故は市場価格・シナリオイベントの乱数列とは独立にシード分離された乱数を使い、同一シードでの完全再現性を保証している。

特に重要な設計として、当期の意思決定を組み立てる`buildCompanyOwnState`が、当期の品質状態を更新する前の状態を必ず参照するという呼び出し順序を徹底し、「今期の品質結果が今期の受注に遡及的に影響しない」という制約を、特別な分岐を作らずに満たしている。persistence schemaVersionを3へ更新した（後方互換）。追加検証（`7523d4e`）では、ゼロ負荷時の回収率が厳密に1.00になること、50シードにわたる無生産組合せで事故が絶対に発生しないこと、価格競争力が上限で頭打ちになりそれ以上の値引きが競争力を増やさないことなどを、具体的な数値例で固定テスト化した。develop/v2への統合は`9d1cef7`。

## 10. Phase 7B：品質・信頼・納期ダッシュボード（`964889c`）

Phase 7Aが計算・保存した品質・操業リスク・顧客信頼・納期信頼性の実績値を、「なぜ今期の成約量がこうなったか」を経営者が理解できる形で可視化する表示層を、`/v2/company-lab`の「品質ダッシュボード」タブとして実装した。品質・信頼・納期の計算式自体は一切変更しないという制約を徹底し、表示専用の関数はエンジンの計算結果とビット単位で一致することをテストで確認している。

エンジン側では、価格競争力の内訳計算を`computeCompetitivenessWeight`から`computeCompetitivenessBreakdown`（5要因の内訳を返す）へ最小限リファクタリングし、リファクタ前後で出力がビット単位で一致することを200件の決定論的疑似ランダムケースで検証した。警告の閾値は、初期の暫定値では「商品構成複雑度」警告が98.75%のターンで、「労務稼働率」警告が61%のターンで誤って発火していたため、5シナリオ×決定論/変動×32ターン（1,600会社ターン分）の実際の分布に対して較正し直した。また、5社すべてがほぼ常に3商品を同時生産するため`complexityStress`が99.37%のバッチで1.0に張り付き、実質的にほぼ一定の+0.10を操業リスクへ加算するだけの信号になっていること（重大事故率を約0.52%から約0.92%へ実際に押し上げている）を突き止めたが、警告閾値自体は到達不能な範囲に設定されていたため「事実上休止中の警告カテゴリ」として診断のみ記録し、Phase 8以降の校正対象とした。

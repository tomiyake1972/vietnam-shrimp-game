# ShrimpX V2 研修用デプロイ手順書

- 作成日: 2026-10-14
- 対象: 受講者が join リンクで参加する研修（Independent Player Flow）
- 方針: **APP_ENV=staging で運用する（案1）**。コード変更は行わない。

---

## 0. なぜ APP_ENV=staging なのか

V2（Company Lab / Management Console / 受講者画面）は、**APP_ENV=production では
動かないように作られています**。これは不具合ではなく、意図的な多重防御です。

| ファイル | 本番での挙動 |
|---|---|
| `app/lib/stagingAdmin.ts` | 管理トークン検証が常に403 |
| `app/lib/companyLabUiSession.ts` | GMセッション署名鍵を導出しない（発行も検証も失敗） |
| `app/api/v2/play/_lib/context.ts` | 常に403 |
| `app/api/v2/play/join/[joinId]/route.ts` | 常に403 |
| `app/lib/v2/player/sessionCookie.ts` | 受講者Cookieの署名鍵を導出しない |

`companyLabUiSession.ts` のコメントが理由を明記しています。

> 本番（APP_ENV=production）ではセッション署名鍵自体を導出しない。これにより発行だけで
> なく検証も本番では必ず失敗し、仮に本番環境に STAGING_ADMIN_TOKEN が誤って設定されて
> いて、かつ非本番環境で正しく署名された Cookie 値を持ち込まれても、決して有効と判定されない。

V2 の認証は「全員で共有する1本の Bearer トークン」で、利用者アカウントがありません。
本番で使える認証方式ではない、という判断でこの防御が置かれています。

### APP_ENV=staging でも本番品質の運用ができます

- `APP_ENV` は Vercel のプロジェクト設定で**明示指定**する値で、`VERCEL_ENV` とは独立しています
  （`app/lib/env.ts` が自動フォールバックを明確に禁止し、未設定なら例外で停止します）。
- `APP_ENV=staging` のデプロイにも**独自ドメインを割り当てられます**。
- 「staging」は Redis のキー分離（`staging:` プレフィックス）とこの防御のための内部ラベルで
  あって、「お試し環境」という意味ではありません。

**現在の production デプロイで動いているのは V1（`/` のゲームコード→ロビー）** であり、
V2 の研修アプリとは別物です。研修用は別デプロイとして用意します。

## 1. 必要な環境変数

Vercel のプロジェクト設定で指定します。**値はこの文書に書きません。**

### 必須

| 変数名 | 用途 | 未設定だとどうなるか |
|---|---|---|
| `APP_ENV` | 環境判定。`staging` を指定 | Vercel上では例外で起動停止 |
| `STAGING_KV_REST_API_URL` | Redis 接続先 | **ビルドが失敗する**（後述） |
| `STAGING_KV_REST_API_TOKEN` | Redis 認証 | 同上 |
| `STAGING_ADMIN_TOKEN` | GMログイン＋受講者Cookieの署名鍵の導出元 | GMがログインできず、受講者Cookieも発行できない |

### 任意（使う機能がある場合のみ）

| 変数名 | 用途 | 未設定時 |
|---|---|---|
| `STAGING_EXPORT_TOKEN` | 管理者向けエクスポート | エクスポート機能が使えないだけ |
| `ANTHROPIC_API_KEY` | AI説明・AI経営会議 | その機能だけ使えない |
| `STANDARD_AI_EXPLANATION_MODEL` | 上記のモデル指定 | 既定値 |
| `AI_MANAGEMENT_MEETING_MODEL` | 同上 | 既定値 |

### ビルド時の注意（既知事象）

`STAGING_KV_REST_API_URL` が未設定だと、TypeScript コンパイル成功後に
V1 既存route `/api/game/[gameCode]/admin/clone` でビルドが停止します。
**初回デプロイの前に環境変数を設定してください。** これは開発日誌に記録済みの既存事象で、
V2 の変更とは無関係です。

### Redis について

本番用（`KV_REST_API_*`）とテスト用（`STAGING_KV_REST_API_*`）は、現在は同一の
Upstash データベースを指す前提です（Vercel Marketplace の仕様変更で無料プランでは
別DBを追加できなくなったため）。分離はキーの `staging:` プレフィックスだけで行われます。

**以前、Redis の帯域上限超過で停止した経緯があります。** 研修前にプランと
使用量を確認してください。これは `APP_ENV` の問題ではなく、プラン・データ量の問題です。

## 2. GM（進行役）の操作手順

### 2-0. 当日の流れ（これだけ覚えれば回ります）

```
会社設定 → 保存確認 → リンク発行 → 配布 → 参加確認 → 提出確認 → Turn進行
```

| 手順 | 画面で見るもの |
|---|---|
| 会社設定 | 経営モードを `Standard AI` → `自分で操作` |
| 保存確認 | 画面下部に「保存先: サーバー（Redis、正本）＋このブラウザ（軽量キャッシュ）」 |
| リンク発行 | 「独立PLAYER参加」にその会社が出る → 「参加リンク発行」 |
| 配布 | 会社ごとに違うリンクを、会社名と対応づけて渡す |
| 参加確認 | その会社が「参加済み」になる |
| 提出確認 | 「Turn N：PLAYER会社は全社提出済みです」 |
| Turn進行 | 「1 Turn」。未提出が残っていればサーバー側でも拒否されます |

### 2-1. ログイン

```
https://<研修用ドメイン>/v2/company-lab/play/login
```

管理トークン（`STAGING_ADMIN_TOKEN` と同じ値）を入力します。
セッションは HttpOnly Cookie で保持されます。

### 2-2. Run を作成し、受講者が使う会社を PLAYER にする

```
/v2/management/setup
```

1. シナリオを選ぶ（既定は `baseline`）
2. **販売市場モデルを選ぶ**（後述。ここは後から変更できません）
3. 受講者に割り当てる会社の制御モードを `STANDARD_AI` → `PLAYER` に変える
4. 「開始」で Run を作成

作成後は `/v2/management?run=<runId>` へ遷移します。

#### 販売市場モデルの選択（研修設計に関わります）

| モデル | 市場集中による価格下落 | 受講者に見える混雑度 |
|---|---|---|
| `legacy-waterfall-v1`（既定） | **働かない** | 表示されない |
| `tiered-v200-crowding-v1` | 働く | 表示される |

「同じ市場に集中すると価格が下がる」ことを学ばせたい場合は
`tiered-v200-crowding-v1` を選んでください。既定のままだと、
混雑度の表示も、それに連動する Standard AI の市場回避も働きません。

**Run 開始後は変更できません**（保存済み Run の `salesModelId` の意味が
変わってしまうため、変更UIを設けていません）。

会社の割り当ては **Run の途中でも変えられます**。Management Console の
「経営モード」で `自分で操作` に切り替えると、その保存が成立した時点で
「独立PLAYER参加」の一覧に現れ、リンクを発行できます。Turn を進める必要は
ありません。`Standard AI` に戻せば、同じく即座に参加対象と提出待ちの数から
外れます。

> **2026-10-18 より前のビルドを使う場合の注意**
> それ以前は、会社を `自分で操作` にしても Turn を1つ進めるまで参加枠に
> 現れず、リンクを発行できませんでした（提出待ちの社数も合いませんでした）。
> `7ffdd3f` 以降では解消しています。古いビルドで当たった場合は、
> 1 Turn 進めると現れます。

### 2-3. 受講者ごとに参加リンクを発行する

Management Console の Player Seat 一覧で、会社ごとに参加リンクを発行します。

```
https://<研修用ドメイン>/v2/play/join/<secret>
```

- **平文のリンクが返るのは発行直後の1回だけ**です。サーバーには保存されません。
  控えずに画面を閉じた場合は、再発行してください。
- 一覧で「発行済み」「参加済み」「今Turn提出済み」が確認できます。
- 再発行すると**旧リンクは即座に失効します**。

### 2-4. 受講者へ配布する

リンクは会社ごとに異なります。宛先を取り違えると別の会社として参加してしまうので、
会社名とリンクを対応づけて配ってください。

#### 配る URL と、配らない URL

| 用途 | URL | 配布先 |
|---|---|---|
| GM用（Run作成・会社設定・リンク発行・Turn進行） | `/v2/management`（ログインは `/v2/company-lab/play/login`） | **GMだけ**。受講者には配らない |
| 参加者用 | `/v2/play/join/<secret>`（会社ごとに発行） | その会社の受講者だけ |

受講者には**共通の管理者URLを配らない**でください。参加者が必要とするのは
自分の会社の参加リンク1本だけです。

参加リンクは**それ自体が資格情報**です。公開のログ・課題資料・Git・
スクリーンショットへ記録しないでください。誤って露出した場合は、
その会社のリンクを再発行すれば旧リンクは即座に失効します。

### 2-5. ターンを進める

全社の提出を確認してから Management Console で Advance します。
受講者の画面は自動で次の Turn に切り替わります（ページを開いたままで構いません）。

## 3. 受講者への案内

受講者に伝えることは次の3点だけです。

1. 配布されたリンクを開く（初回で参加が完了します）
2. 2回目以降は同じリンクでも、`/v2/play/workspace` でも開けます
3. 提出したら、GMが次のターンへ進めるまで待つ（画面は開いたままで構いません）

### 参加リンクの性質（2026-10-14 変更）

- **同じリンクを何度でも開けます。** 開くたびに新しいセッションが発行されます。
- 以前のセッションは失効しないので、**PCとスマホの併用ができます**。
- ブックマークからの再訪問・端末変更・Cookie消失のいずれも、
  GMの手を借りずに復帰できます。
- Cookie の有効期間は30日です。

**引き換えに受け入れていること**: リンクを知っている人は誰でもその会社として
参加できます。リンク自体が資格情報であるという設計です。
配布経路の管理（チャットの誤爆・画面共有での露出）に注意してください。
失効させたいときは GM が再発行すれば旧リンクは即座に無効になります。

## 4. 管理者画面と受講者画面の分離（現状）

| 項目 | 状態 |
|---|---|
| 受講者画面に Analysis へのリンク | **無い**（E2E PSE-4 で固定） |
| 受講者画面に会社・Run の切替UI | **無い**（同上） |
| 受講者画面から「/」への導線 | **外した**（「/」にGMコンソールへのリンクがあるため） |
| `/api/v2/management/*` | Bearer または GMセッションCookieが必要。受講者のseat Cookieでは通らない |
| `/v2/management/player`（GM代理のPLAYER画面） | GM自身のブラウザタブ内キャッシュを正本にしており、受講者の端末からは原理的に開けない |

受講者が URL を直打ちしても、管理APIは認証で弾かれます。

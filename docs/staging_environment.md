# ShrimpX テスト環境構築・運用手順

このドキュメントは、Vercel・Upstashの操作に詳しくない方でも迷わず作業できることを目指して書かれています。専門用語が出てくる箇所は、できるだけ「画面のどこを見て、何を押すか」を具体的に説明します。

管理画面の項目名・ボタン名は各サービスの更新によって変わることがあります。本書は2026年7月時点の一般的な画面構成をもとに書いていますが、実際の画面と表記が多少異なる場合は、名称そのものよりも「目的」（例：「新しいデータベースを作る」「環境変数を追加する」）に注目して、近い機能のメニューを探してください。

---

## 1. この環境を作る目的

このゲーム（ベトナムエビ産業経営シミュレーション）には、実際に大会や授業で使う「本番環境」とは別に、機能追加や不具合修正を安全に試せる「テスト環境（ステージング環境）」が必要です。

テスト環境があることで、次のことが安全にできるようになります。

- 新機能やバグ修正を、本番の参加者データに一切触れずに試せる
- テストゲームを何度でも作り直し・初期化・削除できる
- ゲーム内の意思決定・ターン処理・GM操作を、本番同様の画面で確認できる
- 「もし途中でおかしくなったら」を試して壊し方・直し方を確認できる

このドキュメントは、そのテスト環境を実際に構築し、日常的に使い、何かあったときに対処するための手順書です。

---

## 2. 本番環境とテスト環境の違い

| 項目 | 本番環境 | テスト環境 |
|---|---|---|
| 使う人 | 実際の大会・授業の参加者 | 開発者・GM（三宅さん） |
| Vercelプロジェクト | 本番用プロジェクト（既存） | テスト用プロジェクト（新規作成） |
| Upstash Redis | 本番用データベース（既存） | テスト用データベース（新規作成） |
| 画面上部のバナー | 表示されない | 「⚠️ DEVELOPMENT/STAGING/PREVIEW / TEST ENVIRONMENT」というオレンジのバナーが常に表示される |
| ゲームの初期化・削除・複製・スナップショット機能 | 使えない（ボタンを押しても本番では拒否される） | 使える（管理トークン入力が必要） |
| GMによるA〜E社の代行操作 | 使えない | 使える |
| データの扱い | 消してはいけない実データ | いつ消えても・作り直しても問題ないテストデータ |

本番環境とテスト環境は、**Redisデータベースそのものが別**です。同じデータベースを共有していません。これは「テスト環境で何をしても本番データに影響しない」ための一番の安全策です。

## 3. 全体構成

```
[GitHubリポジトリ tomiyake1972/vietnam-shrimp-game]
        │
        ├── main ブランチ ─────────────→ [本番Vercelプロジェクト] ──→ [本番Upstash Redis]
        │                                   環境変数: APP_ENV=production
        │                                              KV_REST_API_URL / TOKEN
        │
        └── feature/staging-test-environment ブランチ
            （将来は staging / develop 等の常設ブランチも検討）
                                       ─→ [テスト用Vercelプロジェクト] ──→ [テスト用Upstash Redis]
                                           環境変数: APP_ENV=staging
                                                      STAGING_KV_REST_API_URL / TOKEN
                                                      STAGING_ADMIN_TOKEN
```

同じアプリケーションのコードが、設定されている環境変数の違いによって「本番として動く」か「テスト環境として動く」かが決まります。コードは共通、接続先とふるまいだけが変わる、という構成です。

- [ ] Upstashのアカウントを持っている（なければ新規登録が必要です）
- [ ] Vercelのアカウントを持っている（GitHubアカウントでログインできるものが便利です）
- [ ] GitHubリポジトリ `tomiyake1972/vietnam-shrimp-game` にアクセスできる
- [ ] 本番用のUpstash Redis・Vercelプロジェクトの情報（URL・トークン）を、誤って上書きしない自信がある（不安な場合は、この手順書を最初から最後まで一度読んでから作業を始めてください）

## 5. Upstashでテスト用Redisを作る

1. [Upstash](https://upstash.com/) にログインします。
2. ダッシュボードで「新しいデータベースを作成する」に相当するボタン（2026年7月時点では "Create Database" のような表記）を探して押します。
3. データベース名には、本番用と区別できる名前を付けてください。推奨名:

   ```text
   vietnam-shrimp-game-staging
   ```

4. リージョン（データベースを置く地域）は、本番用データベースと同じか、Vercelのデプロイ地域に近い場所を選んでください（迷ったら本番用と同じ地域で構いません）。
5. データベースが作成されたら、詳細画面に「REST API」に関する項目があります。ここに次の2つの値が表示されます。

   - **REST URL**（`https://xxxxx.upstash.io` のような形式）
   - **REST TOKEN**（長い英数字の文字列）

   この2つを、後でVercelの環境変数 `STAGING_KV_REST_API_URL` / `STAGING_KV_REST_API_TOKEN` に設定します。

6. **重要な注意点**

   - この画面に表示されるURL・TOKENは、パスワードと同じくらい重要な情報です。**チャットやドキュメント、GitHubのコードやコミットメッセージには絶対に貼り付けないでください。**
   - 本番用データベースの画面と見た目が似ています。作業中はブラウザのタブ名やデータベース名をよく確認し、本番用データベースの画面で操作しないよう注意してください。
   - 無料プラン（Free tier）を使う場合、保存できるデータ量やリクエスト回数に上限があります。Upstashの管理画面でプランの詳細・現在の利用量を確認できます。テスト目的であれば通常は無料プランの範囲内で足りますが、上限に近づいた場合は管理画面の警告を確認してください。
   - このテスト用データベースに対して、本番Redisに対するような「絶対に消してはいけない」というデータは基本的に存在しません。ただし、テスト運用中に「動作確認用のゲームコード一覧」など残しておきたいデータがある場合は、むやみに全削除しないよう注意してください（本書の管理機能は特定ゲームのみを対象とし、Redis全体を削除する操作は用意していません）。

## 6. Vercelでテスト用プロジェクトを作る

1. [Vercel](https://vercel.com/) にログインします。
2. 新しいプロジェクトを作成します（"Add New..." → "Project" のようなメニュー）。
3. GitHubリポジトリ一覧から `tomiyake1972/vietnam-shrimp-game` を選択し、インポートします。
4. プロジェクト名には、本番用と区別できる名前を付けてください。推奨名:

   ```text
   vietnam-shrimp-game-staging
   ```

5. Framework Preset（フレームワークの種類）は **Next.js** を選択してください（通常は自動検出されます）。
6. Root Directory（リポジトリ内のどのフォルダを対象にするか）は、特別な事情がなければ空欄（リポジトリのルート）のままで構いません。
7. デプロイ対象のブランチを設定します。現段階では以下のブランチを使用してください。

   ```text
   feature/staging-test-environment
   ```

   Vercelのプロジェクト設定にある「Production Branch」（本番扱いにするブランチ）の項目に、上記ブランチ名を指定します。

   将来的には、常設のテスト用ブランチ（例: `staging` や `develop`）を作り、そちらをテスト用プロジェクトの対象ブランチにする運用も検討できます。機能ブランチ（`feature/...`）は作業が終わると削除されることが多いため、長期運用する場合は常設ブランチへの切り替えを推奨します。

8. **本番プロジェクトとテスト用プロジェクトを分ける理由**

   Vercelの1つのプロジェクトには、1組の「本番用環境変数（Production）」しか設定できません。もし本番用とテスト用を同じプロジェクト内でブランチだけ切り替えて運用しようとすると、環境変数の設定を誤ると本番Redisとテスト用Redisを取り違えるリスクが高まります。プロジェクト自体を分けることで、「テスト用プロジェクトには本番Redisの情報を一切入力しない」という単純なルールだけで事故を防げます。

## 7. GitHubリポジトリを接続する

Vercelでプロジェクトを作成する際（手順6）に、GitHubアカウントとの連携・対象リポジトリへのアクセス許可を求められます。指示に従ってGitHub側で連携を許可してください。

一度接続すれば、指定したブランチに新しいコミットがpushされるたびに、Vercelが自動的に再デプロイします。

## 8. 使用ブランチを設定する

手順6-7で設定した内容の確認です。

- テスト用Vercelプロジェクトの「Production Branch」（本番扱いのブランチ）設定を、`feature/staging-test-environment` にします。
- このブランチにコミットをpushするたびに、テスト用Vercelプロジェクトが自動的に再デプロイされます。
- 本番Vercelプロジェクトの「Production Branch」は、これまで通り `main` のままにしてください（変更しないでください）。

## 9. 環境変数を設定する

Vercelのプロジェクト設定画面から、「Environment Variables」（環境変数）のメニューを開きます。

### テスト用Vercelプロジェクトに設定する変数

| 変数名 | 値 | 備考 |
|---|---|---|
| `APP_ENV` | `staging` | |
| `STAGING_KV_REST_API_URL` | 手順5で取得したUpstashのREST URL | |
| `STAGING_KV_REST_API_TOKEN` | 手順5で取得したUpstashのREST TOKEN | |
| `STAGING_ADMIN_TOKEN` | 任意の十分に長いランダムな秘密文字列（作成方法は8章参照） | |

コードの実装（`app/lib/redis.ts`）を確認したところ、本番用Redisの接続情報（`KV_REST_API_URL` / `KV_REST_API_TOKEN`）は、`APP_ENV=production` と判定された場合にしか参照されません。したがって、テスト用Vercelプロジェクトには **`KV_REST_API_URL` / `KV_REST_API_TOKEN` を設定する必要はありません**（設定しても使われませんが、誤操作防止のため設定しないことを推奨します）。

### 本番Vercelプロジェクトに設定する変数（確認のみ、既存設定を変更する必要はありません）

| 変数名 | 値 |
|---|---|
| `APP_ENV` | `production` |
| `KV_REST_API_URL` | 既存の本番用Upstash Redis URL |
| `KV_REST_API_TOKEN` | 既存の本番用Upstash Redis TOKEN |

本番Vercelプロジェクトには、原則として以下を設定しないでください。

- `STAGING_KV_REST_API_URL`
- `STAGING_KV_REST_API_TOKEN`
- `STAGING_ADMIN_TOKEN`

### Environment区分（Production / Preview / Development）について

Vercelの環境変数は、「Production」「Preview」「Development」という3つの区分ごとに別々の値を設定できます。テスト用Vercelプロジェクトでは、少なくとも **Production区分**に上記の値（`APP_ENV=staging` など）を設定してください（手順6で指定したブランチはこのプロジェクトの「Production Branch」として扱われるため）。

Pull Requestごとに作られるPreview Deployment（プレビューデプロイ）も利用してテストしたい場合は、同じ値を **Preview区分**にも設定してください。コードの実装上、`APP_ENV`が明示的に設定されていなくても、VercelのPreviewデプロイでは自動的に `VERCEL_ENV=preview` が設定され、環境判定は「本番ではない」側（テスト環境と同じ扱い）になります。ただしRedis接続情報（`STAGING_KV_REST_API_URL` 等）は自動では設定されないため、Preview区分にも明示的に設定しておく必要があります。

**未設定の場合の挙動**: `STAGING_KV_REST_API_URL` や `STAGING_KV_REST_API_TOKEN` が設定されていない状態でテスト用プロジェクトが動くと、アプリはその環境変数が存在しないことを示す明確なエラーで失敗します。本番用の値へ自動的に切り替わることはありません。「動いているように見えるが実は本番Redisに繋がっていた」という事故を防ぐための、意図された挙動です。

## 10. 初回デプロイ

手順6〜9の設定が終わると、Vercelは自動的に最初のデプロイを開始します。デプロイ状況は、Vercelのプロジェクトダッシュボードの「Deployments」タブで確認できます。

- 「Building」→「Ready」と表示が変われば成功です。
- 途中で失敗（Failed）した場合は、ビルドログを開いてエラーメッセージを確認してください。ほとんどの場合、環境変数の設定漏れが原因です（20章「トラブル時の確認事項」を参照）。

デプロイが完了すると、`https://（プロジェクト名）.vercel.app` のようなURLが発行されます。これがテスト環境のURLです。

## 11. テスト環境の動作確認

発行されたURLをブラウザで開きます。

- 画面の一番上に、オレンジ色のバナーで「⚠️ STAGING / TEST ENVIRONMENT — この環境（staging）のデータは本番環境とは別です」のような表示が出れば、テスト環境として正しく動作しています。
- 本番環境のURLを開いても、このバナーが出ないことを確認してください。

## 12. テストゲームを作る

トップページ、またはGMコンソール画面（`/gm`）から、通常のゲーム作成と同じ操作でゲームを作成します。

テスト環境（`APP_ENV=staging` など、本番以外）で作成したゲームは、**サーバー側の判定によって自動的に「テストゲーム」として扱われます**。作成時に特別なチェックボックスなどを操作する必要はありません（逆に、クライアント側からのリクエストを細工しても本番環境ではテストゲームを作ることはできません)。

GMコンソール画面には、作成したゲームのゲームコードに加えて、次のような情報が表示されます。

```
TEST GAME｜Environment: staging｜Seed: 1a2b3c4d5e6f7a8b
```

- `Seed` はゲームごとに自動生成されるランダムシードです。同じシードで別のテストゲームを複製すると、乱数を使う処理が同じ結果になります（14章「同一シード」を参照）。

## 13. GMとしてA〜E社を操作する

作成したテストゲームのGM画面（`/gm/{ゲームコード}`）を開くと、「🎮 テスト操作」という紫色のセクションが表示されます。ここには社A〜社Eそれぞれの「操作」ボタンがあります。

- 各ボタンを押すと、その会社の意思決定画面が、GMが代わりに操作できるモードで開きます。
- AI担当（AI-A、AI-B等）に設定されている会社も、この画面から人間が代わりに意思決定を入力できます。GMが操作しても、その会社の担当設定（AI担当かどうか）自体は書き換わりません。

このセクションは、本番環境では一切表示されません。

---

## 14. 提出状況を確認する

GM画面の「意思決定の提出状況」セクションで、各社の提出状況を確認できます。

- 各社ごとに「未提出／提出済み／再提出済み」の状態
- 「操作者」（Player／GM Test／AIのいずれか）
- 「提出回数」（同じ四半期に何度提出したか）
- 「最終提出時刻」（日本時間で表示）

この画面は5秒ごとに自動更新されます（ブラウザのタブが非表示の間は更新を止めます）。手動で更新したい場合は「🔄 更新」ボタンを押してください。

## 15. テストゲームを初期化する

GM画面下部の「⚠️ テストゲーム管理」セクションで実施します。

1. 「管理トークン」欄に、Vercelに設定した `STAGING_ADMIN_TOKEN` の値と同じ文字列を入力します。
2. 「初期状態に戻す」ボタンを押します。
3. 確認パネルが表示されるので、内容を確認して「実行する」を押します。

初期化すると、次のようになります。

- 保持される: ゲームコード・タイトル・担当設定（A〜E社が人間かAIか）・テストゲームであることの情報・乱数シード・作成日時
- リセットされる: 現在の年・四半期・フェーズ、これまでの意思決定・ターン処理結果、各社の資産状況（初期値に戻る）
- **保存済みのスナップショットは削除されません**（初期化前の状態を残しておきたい場合は、初期化前にスナップショットを保存しておくことを推奨します）

---

## 16. テストゲームを複製する

同じ「テストゲーム管理」セクションで実施します。

1. 「複製方式」で、以下のどちらかを選びます。
   - **現在の状態**: 今のゲームの年・四半期・意思決定履歴・ターン結果をすべて複製する
   - **初期状態**: タイトルと担当設定だけを複製し、それ以外は初期状態にする
2. 「乱数シード」で、以下のどちらかを選びます。
   - **同じシード**: 複製元と同じ乱数シードを使う（同じ条件で再現したい場合）
   - **新しいシード**: 新しく生成したシードを使う
3. 「このゲームを複製」ボタンを押します。管理トークンが正しければ、新しいゲームコードが発行されます。

複製元のゲームは一切変更されません。

---

## 17. スナップショットを保存・復元する

「現在の状態を保存」欄にラベル（任意、例:「Q2開始前」）を入力し、「現在の状態を保存」ボタンを押すと、その時点のゲーム状態が保存されます。

- 1つのゲームにつき保存できるスナップショットは最大20件です。20件を超えると、最も古いものから自動的に削除されます。
- 保存されたスナップショットは、下の一覧に新しい順で表示されます。

「この状態に戻す」ボタンを押すと、確認パネルが表示されます。「復元する」を押すと、次の処理が行われます。

1. **復元する前に、現在の状態が自動的に「復元前の自動保存」として保存されます**（誤って復元しても、直前の状態に戻せるようにするため）。
2. 選択したスナップショットの内容にゲームが復元されます。
3. ゲームコード・作成日時・テストゲームかどうか・環境の情報は、**スナップショットに保存されていた値ではなく、常に復元先ゲーム（今操作しているゲーム）の値がそのまま使われます**。これは、万一スナップショットの中身に古い・誤った安全情報が入っていても、それによって安全上の判定が誤って変わらないようにするための設計です。

「削除」ボタンで、個別のスナップショットを削除できます。

### 本番環境でのスナップショット一覧APIの挙動（意図した仕様）

スナップショット一覧を取得するAPI（`GET /api/game/[gameCode]/snapshots`）は、読み取り専用で管理トークンを必要としません。本番環境や、テストゲームでないゲームに対してこのAPIを呼び出した場合、エラーではなく **「スナップショットは0件」という空の一覧を返します**（`200`応答）。

これは意図した仕様です。理由は次のとおりです。

- このAPIは状態を変更しない読み取り専用の操作であること
- 「本番ゲームにはそもそもスナップショットという概念上のデータが存在しない」という事実をそのまま返しているだけであること
- エラー（403等）で明示的に拒否すると、「テストゲーム管理機能が存在すること」自体を外部から推測される手がかりを与えてしまうこと

一方で、「管理系の機能は本番で完全に無効」という原則をより一貫させたい場合は、将来的にこの一覧APIも403または404に統一する変更を検討できます。現時点では、上記の理由により空配列を返す設計を維持しています。

## 18. テストゲームを削除する

「このテストゲームを削除」ボタンを押すと、確認パネルが表示されます。誤操作防止のため、**表示されているゲームコードと完全に同じ文字列を入力しないと削除ボタンが押せません。**

削除すると、次のものがすべて削除されます。

- ゲームの状態（セッション情報）
- 各社の状態
- すべての四半期分の意思決定・ターン処理結果
- すべてのスナップショット
- ゲーム一覧からの登録

この操作は元に戻せません。削除前に残しておきたい情報がある場合は、事前にスナップショットを保存するか、内容を控えておいてください。

他のゲームには一切影響しません。Redisデータベース全体を削除するような操作は、本システムには存在しません。

---

## 19. 本番へコードを反映する流れ

1. テスト用ブランチ（`feature/staging-test-environment` または将来の常設テスト用ブランチ）で、テスト環境を使って動作確認する。
2. `docs/staging_test_checklist.md` の各項目をひととおり確認し、チェックを入れる。
3. GitHub上でPull Requestを作成する。
4. 変更内容をレビューする。
5. 問題なければ、本番ブランチ（`main`）へマージする。
6. 本番Vercelプロジェクトのデプロイが自動的に走ることを確認する。
7. 本番環境のURLを開き、テスト環境バナーや「テストゲーム管理」セクションが表示されないことを確認する。
8. 本番Redisに既存のゲームが1件でもあれば、その過去ゲームが正しく読み込めることを確認する。
9. 本番環境で新規ゲームを1件作成できることを確認する。
10. テスト用Redis（Upstashのテスト用データベース）に、この本番ゲームが作られていないことを確認する。

本番Redisのデータ移行や、本番の既存ゲームの削除・初期化は、この手順の対象外です。行わないでください。

## 20. トラブル時の確認事項

### 画面が開かない

- Vercelの「Deployments」タブで、最新のデプロイが成功（Ready）しているか確認する。
- 「Environment Variables」に必要な変数がすべて設定されているか確認する。
- 環境変数を追加・変更した後は、**再デプロイしないと反映されません**。「Redeploy」を実行する。
- `APP_ENV` が `staging`（テスト環境の場合）になっているか確認する。

### Redis接続エラーが表示される

- `STAGING_KV_REST_API_URL` / `STAGING_KV_REST_API_TOKEN` の値が正しいか確認する（コピー時に前後の空白が入っていないか等）。
- 誤って本番Redisの値を設定していないか確認する。
- Upstashの管理画面で、対象のデータベースが停止・削除されていないか確認する。

### 管理操作（初期化・削除・複製・スナップショット）が403エラーになる

- 操作している環境が本番ではないか確認する（本番では常に403になる仕様です）。
- 操作対象がテストゲームであるか確認する（`isTestGame` が真であること。通常のテスト環境で作成したゲームは自動的にテストゲームになります）。
- Vercelに `STAGING_ADMIN_TOKEN` が設定されているか確認する。
- GM画面の「管理トークン」欄に、Vercelに設定したものと同じ文字列を入力しているか確認する。
- 環境変数を変更した後、再デプロイしたか確認する。

### 操作の途中でエラーになった

初期化・削除・復元は、複数のRedisキーを順番に書き換える処理です。**Redisの完全なトランザクション（全部成功するか全部失敗するかのどちらかを保証する仕組み）としては実装されていません。** そのため、通信エラーなどでごく稀に途中まで反映された状態が残る可能性があります。

エラーが出た場合は、次を確認してください。

1. GM画面を再読み込みする。
2. 現在の年・四半期が想定通りか確認する。
3. A〜E社の会社状態（現金・純資産など）が想定通りか確認する。
4. 提出状況が想定通りか確認する。
5. スナップショット一覧を確認する。
6. 内容がおかしい場合は、直前のスナップショット（特に復元操作を行っていれば自動保存された「復元前の自動保存」）から復元することを検討する。

この制約は今後の改善候補です（将来的にはRedisのトランザクション機能や、処理状態を記録するフラグの導入を検討できます）。

### `next dev` でGM画面が「読み込み中...」のまま止まる

これは開発時に使う `next dev`（Turbopack）特有の既知の事象で、Vercel上の本番相当のビルド（`npm run build` → `npm start`）では再現しません。開発中にこの症状が出た場合は、`npm run build && npm start` で本番ビルドモードとして起動し、同じ手順で再現するかどうかを確認してください。テスト環境・本番環境ともに、Vercel上のデプロイはこの本番ビルドモードで動作するため、影響はありません。

## 21. セキュリティ上の注意

- `STAGING_ADMIN_TOKEN` の値そのものを、コード・ドキュメント・チャット・スクリーンショットのどこにも書かない・写さないでください。
- 管理トークンの生成には、次のようなコマンドを使うと安全なランダム文字列を作れます。

  ```bash
  openssl rand -hex 32
  ```

  または、お使いのパスワード管理ソフトの「ランダムなパスワードを生成する」機能で、十分に長い（32文字以上を推奨）ランダムな文字列を生成しても構いません。

- 管理トークンは、GM画面の「管理トークン」欄に入力すると、そのブラウザタブの `sessionStorage`（そのタブを閉じるまで有効な一時的な保存領域）に保存されます。ページを再読み込みしても、同じタブであれば入力し直さずに済みます。ただし、次の点に注意してください。

  - `localStorage`（ブラウザを閉じても残る保存領域）には保存されません。
  - 共有のパソコンやタブレットで操作した場合は、**操作が終わったら必ずそのタブを閉じてください。** 閉じないままにすると、同じ端末を使う別の人が管理トークンを引き継いで使える状態になってしまいます。
  - このトークンをRedisやゲームのデータ自体に保存することはありません。

- 管理トークンを本番環境で使うことはありません（本番では常に拒否されます）。誤って本番用の秘密情報として使い回さないでください。

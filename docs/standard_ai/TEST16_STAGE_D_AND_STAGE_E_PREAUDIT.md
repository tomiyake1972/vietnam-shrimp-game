## 0. 先に報告すべき訂正 — HOSO capex の現行工期は 1Q ではなく **3Q** だった

Phase 1監査 §7 で、現行 `hosoLineExpansion` の工期を「1Q」と記載しました。**これは誤りです。**

```
standardConstructionQuarters は paymentRatios.length から導出される
現行 paymentRatios = [0.3, 0.4, 0.3]  →  工期 3Q
```

`postCompletionReadinessQuarters: 1`（完成後の立ち上げ1Q）を工期と取り違えていました。

ご指示の「工期1Q」を満たすには `paymentRatios` を単期へ寄せる必要があるため、
**`[1.0]` としました。結果として 8M USD 全額が単一四半期の現金流出になります。**
旧設計（3四半期に 2.4M / 3.2M / 2.4M 分割）より単期の資金負担は重くなります。

この点は指示の「工期1Q」から必然的に導かれる帰結ですが、Phase 1の記載が誤っていたため
判断3の検討時に前提として共有できていませんでした。分割払いを残したい場合は
工期が延びます（両立しません）。**どちらを優先するかご指示ください。**

## 2. 段階D ベンチマーク: **5社×8Q で変化ゼロ**

| Co | contracts C→D | opProfit C→D | raw shortage C→D | 期末現金 |
|---|---|---|---|---|
| BAL | 108,403 → 108,403 | 86.3 → 86.3M | 8,116 → 8,116 | 48.8M |
| MASS | 101,294 → 101,294 | -25.2 → -25.2M | 74,909 → 74,909 | 2.7M |
| JPQ | 96,704 → 96,704 | 59.6 → 59.6M | 41,935 → 41,935 | 31.7M |
| VAP | 99,650 → 99,650 | 62.2 → 62.2M | 36,134 → 36,134 | 29.6M |
| CONSV | 97,630 → 97,630 | 69.8 → 69.8M | 21,876 → 21,876 | 35.1M |

**主因: 8Qの間、どの会社も一度も設備投資を提案していないため。**
capex パラメータを変えても、その案件が起票されなければ何も動きません。

### 2.1 原因（推測ではなく diagnostics の実測値）

ベンチマークに capex diagnostics の保存を追加して確認しました。

```
5社×8Q の capex diagnostics 全92件 = すべて CAPEX_DEFERRED
新規投資提案 = 0件
```

見送り条件の内訳（商品別判定 90件中）:

| 満たさなかった条件 | 件数 |
|---|---|
| **sustained（前期稼働率が持続的に高い）** | **86** |
| safe（現金・借入余力） | 84 |
| noExcess（完成品在庫が過剰でない） | 0 |
| alreadyPlanned（同区分が進行中） | 0 |

`shortfallRatio` は 1.05〜1.35 で**しきい値1.05を超えており、能力不足自体は正しく検知されています**。
落ちているのは持続性条件です。

```
sustained = 前期設備稼働率 >= capexSustainedUtilizationThreshold (0.92)
```

実測の前期設備稼働率:

| Co | T2 | T3 | T4 | T5 | T6 | T7 | T8 |
|---|---|---|---|---|---|---|---|
| BAL | 0.398 | 0.608 | 0.653 | — | — | — | — |
| MASS | 0.476 | 0.388 | 0.506 | 0.413 | 0.469 | 0.215 | 0.300 |
| JPQ | 0.367 | 0.355 | 0.458 | 0.483 | 0.505 | 0.510 | 0.525 |
| VAP | 0.303 | 0.360 | 0.493 | 0.481 | 0.516 | 0.531 | 0.525 |
| CONSV | 0.444 | 0.387 | 0.445 | 0.488 | 0.539 | 0.545 | 0.541 |

**0.92 に届いている四半期は一つもありません。最大でも 0.65 です。**

### 2.2 これは何を意味するか

段階Cで **設備能力を上げ（common 30,000）、同時に養殖能力を下げた（4,000）** ため、
律速が **設備 → 原料** へ移りました。原料が入らないので設備が回らず、稼働率が 0.3〜0.5 に張り付きます。

その結果、
- 設備は「不足している」と判定される（shortfallRatio > 1.05 = 作りたい量に対して能力が足りない）
- しかし「回っていない」ので投資は見送られる（稼働率 < 0.92）

という状態が固定されています。**capex 経路そのものが8Q通して閉じています。**

段階B→Cで原料不足が JPQ 8倍・VAP 5倍・CONSV 10倍に増えた件（段階C所見§2）の、
より深い帰結がこれです。

### 2.3 **これは Standard AI のバグではありません**

「稼働率が低いのに設備を増やさない」は判断として正しい挙動です。
問題は**ゲームバランス側**、すなわち

- 養殖 4,000t に対して外部原料調達が追いついていない
- したがって設備投資の意味が消えている

という点にあります。指示Lの「HOSO大量モデルの弱点＝大量原料調達」は効きすぎており、
現状は「弱点」ではなく「唯一の律速」になっています。

### 2.4 変更していないこと

`capexSustainedUtilizationThreshold`（0.92）は **Standard AI の判断ロジック**であり、
今回の指示範囲（ゲームバランスのパラメータ）に含まれないため**変更していません**。
これを下げれば投資は動きますが、それは「原料不足を設備投資で隠す」ことになります。

**判断をお願いします:**
- (a) 現状のまま段階E/Fへ進み、最終ベンチマークで外部原料調達の反応を確認する
- (b) 先に外部原料調達側（供給量・価格・リードタイム）を確認し、原料が入る状態にしてから段階Eへ進む
- (c) 養殖 4,000t を見直す

**(b) を推奨します。** 原料が律速のままだと、段階E（商品集中効果＝Worker削減）も
同じ理由で効果が観測できない可能性が高いためです（Worker を減らしても作る原料がない）。

## 3. 段階E 事前監査: 「計画生産量を labor 計算へ渡す影響範囲」

ご指示「想定より広範囲なら停止して報告」に該当したため、**実装せず停止しました。**

### 3.1 生産エンジン内部は想定どおり狭い（問題なし）

`production/labor.ts` の配分ループには `d.candidateQuantity`（＝その計画の生産予定量）が
すでに存在します。判断1で確定した「計画生産量ベース」は、エンジン内部では
**追加の配線なしにそのまま使えます**。循環もしません。

同様に、計画量を引数で受け取っている呼び出し元も機械的な対応で済みます:

| 呼び出し元 | 計画量の入手先 | 対応 |
|---|---|---|
| `production/labor.ts` 配分ループ | `d.candidateQuantity` | 機械的 |
| `companyLab/workforce.ts` `computeRequiredRegularHeadcount` | `input.quantityByProduct` | 機械的 |
| `DecisionEditor.tsx` PD省人化プレビュー | `productionRow.desiredQuantity` | 機械的 |

### 3.2 **想定外: 計画生産量を持たない呼び出し元が4箇所ある**

これらは labor の3関数を「計画とは無関係の定数」として使っています。
集中係数は生産量の関数なので、**ここでは係数が定義できません。**

| # | 箇所 | 現在の用途 | 問題 |
|---|---|---|---|
| 1 | `adminExport/managementAccountingModel.ts:539` `effectiveTonsPerRegularWorker(params)` | **製造原価計算書**（指示Gの対象） | 引数が `params` のみ。商品別の**定数**として設計されている。集中係数を入れると定数でなくなり、`test15ManagementSheets.ts:472` 以降のExcel列の意味が「パラメータ」から「計画依存値」へ変わる |
| 2 | `companyLab/openingStateSummary.ts:303` `tonsPerRegularWorker` | **Turn1期初画面**の表示、および `aiExplanation/buildExplanationContext.ts:255` 経由で**相談役AIの説明コンテキスト** | 期初時点では生産計画が**まだ存在しない**。係数の入力が無い |
| 3 | `standardAi/diagnosis/businessScaleProfile.ts:312` | Standard AI の労働制約診断。`requiredHeadcountForQuantity(1トン, …)` で「1トンあたり人数」を定数として求め、総人数を割って `supportedScaleTons` を出す | **判断1の循環がここで再発する。** 求めたいのは生産可能量なのに、集中係数はその生産量に依存する。しかもここには計画量が無く、あるのは商品ミックス前提と総人数だけ |
| 4 | `investmentPlanningViewModel.ts:569` | 投資計画画面「N人増やしたら何t作れるか」 | 出力が生産量なので、係数の入力に使えない（#3と同じ循環） |

さらに calibration script 3本（`test15FourCaseSimulation` / `test15PdMechanizationPreflightCalibration` /
`test15NewFactoryConstructionPreflightCalibration`）とテスト2ファイルが同じ関数群を参照しています。

### 3.3 停止した理由

Phase 1 §6 では「`effectiveEfficiencyPerHeadTons` の1関数に入れれば全経路へ自動反映される」と
評価しました。**それは生産エンジン内部については正しいのですが、上記4箇所については誤りです。**
判断1の「計画生産量は Worker 配分の前に確定しており循環しない」という前提も、
**生産エンジンの内側でのみ成立**します。#3・#4 では循環が復活します。

したがって段階Eは「係数を1箇所で掛ける」では終わらず、
**4箇所それぞれについて「集中係数をどう扱うか」の設計判断**が要ります。

### 3.4 選択肢

各箇所について、取り得る扱いは3つです。

- **(i) 集中係数を適用しない**（基準係数のまま表示・診断する）
  → 「画面では足りると出たのに実際は足りない」を生む。#1（製造原価計算書）は指示Gが
    集中係数の表示を求めているので、少なくとも#1では採れない
- **(ii) 計画生産量を引数として通す**
  → #1・#2 は呼び出し元をたどれば計画に到達できる可能性がある（要調査）。
    #3・#4 は計画が原理的に存在しないため採れない
- **(iii) その箇所専用の代表生産量を定義する**（例: 前期実績、または能力の何割か）
  → #3・#4 はこれしかない。ただし「診断と実際の係数がずれる」ことを許容する設計判断になる

**推奨:**
- #1 製造原価計算書 → **(ii)**（指示Gの要求を満たすため。計画量に到達できるか要調査）
- #2 期初画面・相談役AI → **(i)**（期初は計画が存在しないため。「基準効率であること」を明記して表示）
- #3 Standard AI 診断 → **(iii)** で前期実績生産量を使う（循環回避。診断の性格上、近似が許容される旨は既に `dataQuality.note` に明記されている）
- #4 投資計画画面 → **(iii)** で当期の計画生産量を使う（画面には計画が入力済みのため到達可能。要調査）

**この4件の扱いを確定いただければ段階Eを実装します。**

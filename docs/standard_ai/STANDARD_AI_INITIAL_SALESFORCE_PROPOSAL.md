## 1. 現在値と提案値（C1）

現行5社の初期営業人数（`fixtures.ts`）と、相対関係を保ったまま30〜40へ写像した値。

| 会社 | archetype | 現在 | 提案 | 備考 |
|---|---|---|---|---|
| BAL | balanced | 18 | **37** | |
| MASS | massMarket | 22 | **40** | 最大 |
| JPQ | japanQuality | 14 | **33** | |
| VAP | vapSpecialist | 14 | **33** | JPQと同値（現状も同値） |
| CONSV | conservative | 10 | **30** | 最小 |
| 合計 | | 78 | **173** | 約2.2倍 |

### 写像の選び方

2案を計算した。

**案1: 単純比例（全社を一律 ×2.24 して合計を175前後にする）**

| BAL | MASS | JPQ | VAP | CONSV |
|---|---|---|---|---|
| 40 | 49 | 31 | 31 | 22 |

→ MASS 49人が40を超え、CONSV 22人が30を下回る。**30〜40のレンジを満たさない**ため不採用。

**案2: 線形写像（最小10→30、最大22→40）** ← 採用

- 順位関係を完全に保つ（MASS > BAL > JPQ = VAP > CONSV）
- 全社が30〜40に収まる
- 「全社35人固定」ではない

**トレードオフ（正直に記す）**: 相対比は圧縮される。
現在は最大/最小 = 22/10 = 2.2倍だが、提案後は 40/30 = 1.33倍になる。
「会社ごとの営業力の差」はゲーム開始時点では今より小さくなる。
30〜40というレンジ指定と、現在の10〜22という広い分布を両立させると、
数学的にどうしても圧縮が起きる。レンジを優先した。

## 2. Test15保存データへの影響（C2）

**migrationは不要である。**

根拠（コード実測）:

- `fixtures.ts` の `salesForceHeadcountTotal` は**静的なフィクスチャ値**であり、
  ターンをまたいで増減しない。
- 実際に配分可能な人数は `state.salesForceHiringState`（`CompanyLabState`）が持つ。
- `buildInitialSalesForceHiringState(fixtures)` は
  `initializeCompanyLab` からのみ呼ばれる＝**新規ラボ作成時だけ**。
- 進行中のラボは永続化された `salesForceHiringState` を読むため、
  fixture値を変えても現在人数は変わらない。

したがって初期人数の変更は **new lab / new game / new fixture initialization にのみ適用され、
進行中のTest15の営業人数は一切書き換わらない**（指示C2の要求どおり）。

なお `?? f.salesForceHeadcountTotal` というフォールバックが runner.ts に2箇所あるが、
これは `salesForceHiringState` を持たない**古い保存データ**専用の経路である。
Test15は当該フィールドを持つため、この経路には入らない。

新30%増員ルールは保存データに依存しないため、実装後の今後Turnからそのまま適用される。

## 3. 実測: 適用すると何が起きたか

提案値を実際に `fixtures.ts` へ入れて全テストを実行した。結果は **9件失敗**。

### 3.1 機械的な失敗（4件・修正済み）

初期人数を定数で直書きしていたテスト。仕組みの検証であって人数に依存しないため、
fixtureから読む形へ修正した（commit `4b8f6f5`）。この修正は初期人数を変えなくても
正しい改善であるため、**そのまま残してある**。

### 3.2 挙動が変わったことによる失敗（5件・未対応）

**これが重要な発見である。**

| # | テスト | 何が壊れたか |
|---|---|---|
| 492 | SAI-5因果(1): 営業基盤が成約配分の順位を決めている | 営業基盤の差が縮んだため順位が変わった |
| 558 | Test15 4ケース比較A: 需要制約下で新工場建設がbaselineより悪化する | 営業力が増え、需要制約の効き方が変わった |
| 566 | NFPC-4: 倍率が大きい環境ほど設備稼働率が高い | 同上 |
| 1163 | Test14 Turn1型ゴールデンケース: **営業が強い制約**と診断される | 営業37人では営業がボトルネックでなくなった |
| 1166 | SAI-6.4 Golden Case: 生産計画が22,100tより明確に小さくなる | 営業力増でdelivery demandが増え、生産計画が縮まなくなった |

とくに **1163** が本質的である。このゴールデンケースは
「営業が強い制約、生産能力・Workerに余力」という状況を意図的に作って
Standard AIの診断を固定している。初期営業を18→37にすると、
**営業はもうボトルネックではなくなる**。テストが壊れたのではなく、
ゲームのバランスが実際に変わったということである。

## 4. 適用を保留した理由

初期人数の変更（`fixtures.ts`）は **このbranchにcommitしていない**。

理由:

1. 上記5件は「期待値を書き換えれば通る」種類の失敗ではない。
   1163・1166は**設計意図（この状況では営業が制約である）を固定するテスト**であり、
   期待値だけ書き換えると、そのテストが何を守っているのか分からなくなる。
2. 指示Dは、初期人数増加・market-aware allocation・30%増員上限の3つを
   同時に入れるため **5社×8Qのベンチマークを必ず行うこと** としている。
   そのベンチマーク（営業不足/過剰・上限への張り付き・人件費による利益破壊の確認）を
   実施する前に初期人数だけ倍にすると、どの変更が何を壊したのか切り分けられなくなる。
3. market-aware allocation と 30%ルールは既にこのbranchへ入っており、
   **それだけで営業配置と増員速度の挙動が変わっている**。
   初期人数はその上に乗る3つ目の変数である。

「勝手に50〜100へ拡大しない」という指示は守っている。提案値は30〜40の範囲内である。

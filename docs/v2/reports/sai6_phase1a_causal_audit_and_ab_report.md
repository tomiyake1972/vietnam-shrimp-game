## 1. 因果監査（Work item 1）

### 1.1 方法

`control`設定（SAI-5機能OFF）、4 seed × 5社 = 20会社ケースについて、各ケースの最初の
`paymentDefault`の3四半期前からdefault発生四半期までを追跡した。各四半期について、
期首現金・当期の信頼できる回収見込み（`receiptsFromCustomers`）・当期支出・
資金見通し上の必要借入プロキシ・AIの実際の希望借入額・銀行の承認額・借入余力・
国内買付の希望量と実行量・`PROCUREMENT_CASH_CONSTRAINED`診断・原料不足量・売上高・
営業利益・paymentDefaultの有無を記録した（全項目 `artifacts/sai6/phase1a/window.csv`）。

### 1.2 分類結果

| 類型 | 件数 | 説明 |
|---|---:|---|
| A. 借入不足による流動性破綻 | **5** | 借入余力があるのに必要額を借りず、それが原料調達の現金制約→原料不足に先行して連鎖 |
| B. 借入では解決できない構造的赤字 | 0 | 借入余力がほぼ枯渇しており、借入判断の是正では解決しない |
| C. タイミングのズレ等 | 0 | 借入不足自体はあるが、調達縮小には結びついていない |
| D. 下流の結果／その他 | 15 | 破綻前の窓で借入不足→調達縮小→原料不足の連鎖が確認できない |

A類型の5ケース（sai5-ab-001/BAL・JPQ・VAP、sai5-ab-002/MASS、sai5-ab-004/VAP）は、
破綻四半期が中盤〜後半（12〜24Q目）に分布し、借入不足が調達制約に先行することを確認できた
（**当時の判定。Phase 1A-2で反証・訂正 — 下記参照**）。

D類型の15ケースは、多くが早期破綻（6〜10Q目）であり、破綻前の窓に入った時点で
すでに借入余力自体が極めて小さい（平均0.15M〜7.6M程度）。これは「借入判断の是正が
効く前に、そもそも借りる余地がほとんど残っていない」初期資本構成上の構造的要因と考えられ、
Phase 1Aの対象（借入の求め方の是正）では解決しない領域である（**この記述自体は
Phase 1A-2でも概ね支持されたが、B類型0件という当時の分類との整合性を三宅さんに指摘され、
再分類で「D類型」ではなく「B類型（借入では解決できない構造的赤字）相当」に統合した**）。

> **【2026-08-01夜・訂正】** Phase 1A-2の再検証により、A類型5ケースのうち4件
> （BAL・JPQ・VAP、MASS）は実際には「借入余力の上限に承認額が常に一致する」ケースであり、
> D類型15件と同じ構造だった。残る1件（sai5-ab-004/VAP）も小さな差はあるが、新式のほうが
> **少なく**借りる方向であり、旧解釈（借入を増やせば救えた）とは逆だった。
> B類型（0件）とD類型（15件）の説明が矛盾していた点（三宅さんのご指摘）は、実際には
> D類型として分類していた15件の内実がB類型の定義に一致していたことが原因であり、
> 誤ったラベル付けだったと判明した。新しい6分類（1〜6）による正式な再分類は
> `docs/v2/reports/sai6_phase1a2_causal_connection_report.md` §2 を参照（全20ケースが
> 新分類「3. 借入余力不足で借入判断是正だけでは救えない」に該当し、うち9ケースは
> 早期破綻のため「5. 破綻前3Qでは原因を特定できない」の注記付き）。

### 1.3 仮説検証の判定条件

| 条件 | 判定 |
|---|---|
| (a) 破綻前の複数ケースで借入余力が残っている | 確認 |
| (b) 実際の借入額が資金見通し上の必要額を下回っている | 確認 |
| (c) 現金制約による原料調達縮小が続いている | 確認 |
| (d) 十分な借入があればその縮小の一部を回避できた可能性がある（A類型が存在する） | 確認 |

**総合判定（当時）: 仮説を支持する証拠あり → Work item 2（Phase 1A実装）へ進む条件を満たす。**

ただし、20ケース中5ケースに限られる（25%）ことは正直に明記する。破綻の主因は
Phase 0-5で確認済みの原料制約（7,259 t/Q）が支配的であり、資金調達側の是正が
効くのはその一部（借入余力が実際に残っている中盤〜後半の破綻ケース）に限られる。

> **【2026-08-01夜・訂正】** 条件(d)「十分な借入があればその縮小の一部を回避できた可能性がある」
> は、当時は反実仮想での検証を行わないまま「A類型が存在する」ことのみで確認済みとしていた。
> Phase 1A-2でA類型5件を四半期単位で再検証した結果、4件は「希望額と承認額の差が銀行の与信上限
> 由来であり、算定式の是正とは無関係」と判明し、条件(d)は実データでは証明できないことが分かった
> （反実仮想はpure functionレベルでのみ検証可能。`sai6_phase1a2_causal_connection_report.md` 作業4参照）。
> 総合判定は「仮説を支持する証拠はほぼ確認できなかった（19/20ケースで借入余力不足が支配的）」に訂正する。

## 2. Phase 1A実装（Work item 2）

### 2.1 是正した式

```
[旧式・既定]
desiredAmountUsd = max(0, targetMinimumCashUsd - cashUsd)

[新式・fundingOutlookEnabled=true のときのみ]
reliableCashInflowsUsd  = 当期に決済期が到来する売掛金（前期末までに発生済み、金額確定）
plannedCashOutflowsUsd  = 当期に決済期が到来する買掛金
                        + 既存借入の当期約定利息・元本
                        + 当期自身の調達・労務の意思決定に基づく現金支出見積り
                        + fixture由来の販管費固定費
projectedEndingCashBeforeNewBorrowingUsd = cashUsd + reliableCashInflowsUsd - plannedCashOutflowsUsd
desiredAmountUsd = max(0, targetMinimumCashUsd - projectedEndingCashBeforeNewBorrowingUsd)
```

将来の市場結果・当期の乱数・他社の非公開情報は一切参照しない。借入余力による上限は
既存の銀行審査（`financing/bankUnderwriting.ts`）がそのまま適用する（重複実装なし）。

### 2.2 変更ファイル

- `app/lib/v2/companyLab/standardAi/parameters.ts` — `fundingOutlookEnabled: boolean`（既定false）を追加
- `app/lib/v2/companyLab/standardAi/decision/finance.ts` — `FundingOutlookInputs`・新式ロジック追加（旧式は無変更のまま分岐）
- `app/lib/v2/companyLab/standardAi/policy.ts` — 当期の調達・労務決定から`FundingOutlookInputs`を構築して`finance.ts`へ渡す
- `app/lib/v2/companyLab/standardAi/reasonCodes.ts` — 診断コード `FUNDING_OUTLOOK_BORROWING_REQUESTED` を追加
- `app/lib/v2/companyLab/standardAi/autoplay/runCase.ts` — A/B比較用に`AutoplayCaseConfig.fundingOutlookEnabled`を追加（他のSAI-5/SAI-6オプションと同型・独立）

### 2.3 決定順序への影響

`policy.ts`の既存パイプライン（sales→production→procurement→labor→finance→capex）は変更していない。
finance判断はもともとprocurement・labor判断の後に実行されるため、「当期自身の調達・労務決定」を
finance判断に読み込むために順序変更は不要だった。

### 4.1 解釈

ON/OFFでほぼ差が出なかった。因果監査でA類型（仮説どおりの連鎖）が確認できたのは20ケース中5件のみで、
残り15件は早期破綻（6〜10Q目）かつ借入余力自体がすでに小さい状態から始まっており、
Phase 1Aの対象（借入の求め方の是正）が効く余地が構造的に小さい。加えて、A類型のケースでも
`PROCUREMENT_CASH_CONSTRAINED`診断はAIの調達計画自体（procurement.ts、cashPressureに基づく自己抑制。
finance判断より前に確定する）由来のものが多く、finance側の借入額是正だけでは調達数量の
自己抑制を直接は変えられない（procurement.tsの自己抑制ロジックはPhase 1Aの対象外）。

**判断**: 実測が示すとおり、この状態でフラグをONにしても目に見える改善は得られない。
三宅さんのご指示どおり、係数やロジックを強引に調整して結果を作ることはせず、
**フラグは既定OFFのまま据え置く**。原因は主に (1) 原料制約が支配的すぎる、(2) 早期破綻ケースの
借入余力がそもそも枯渇している、(3) procurement.ts側の自己抑制がfinance是正と独立に効いている、
の3点であり、いずれもPhase 1Aの範囲外（Phase 1C以降・原料調達側の見直し）で扱うべき論点である。

## 5. 未解決の問題・今後の論点

- procurement.ts自身の`cashPressure`ベースの自己抑制（`cashConstrainedProcurementDampingAtSeverePressure`）
  が、finance側の借入是正と独立に発火しており、両者の関係が未整理。Phase 1C以降で調達側の
  資金認識ロジックも合わせて見直す必要がある。
  Phase 1Bで実装予定の「借入余力超過時の計画縮小」を待つよりも優先度が高いかもしれない。
- 早期破綻（6〜10Q目）ケースの根本原因は、初期資本構成（開業時点の現金・借入余力）に
  ある可能性が高く、Phase 1A/1Bの対象外。SAI-4/5の初期条件設定を再確認する必要がある。
- Phase 0-5の推奨初期閾値（15%/3Q/15%/1Q）はPhase 1D本体実装後に別途検証が必要（未検証のまま）。

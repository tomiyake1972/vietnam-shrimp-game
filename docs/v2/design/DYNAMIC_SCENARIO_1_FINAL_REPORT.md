## 1. 最終 Scenario architecture

3層分離を正式設計として実装した。

| Layer | 決めるもの | 実装 |
|---|---|---|
| **A. Scenario** | 構造需要・商品ライフサイクル・世界景気循環・産地供給・産地コスト競争力・外生ショック | `ScenarioDefinition`（トレンド＋イベント＋上書き宣言） |
| **B. Market Engine** | 実現価格・市場清算・実際の成約・在庫圧力・外部供給者との競争 | 既存モジュール（**無変更**） |
| **C. Five-company** | 提示供給量・market crowding・シェア・成約転換・収益性・戦略的押し出し | 既存モジュール（**無変更**） |

Scenario が価格を書けないことは型で強制されている（`ScenarioBaseVariable` に価格変数が存在しない）。
market / production engine に turn 番号の分岐は1つも追加していない。

**新規追加した機構は3つだけ**（すべて opt-in、未指定シナリオは既存挙動と完全一致）:

| 機構 | 目的 | 未指定時 |
|---|---|---|
| `productLifecycleOverrides` | 市場×商品の長期構造をシナリオが決める | `PRODUCT_LIFECYCLE_PARAMETERS_V1` を同一参照で返す |
| `structuralDemandAnchor` | 供給未達で市場構造が消滅しないようにする | 従来の消費国在庫挙動 |
| `requiredCapabilities` | シナリオが必要とする機能を自分で宣言する | `config` をそのまま返す |

## 4. Console への DS1 配線

**方式**: シナリオ定義が必要機能を宣言し、`initializeCompanyLab` が
呼び出し側の設定へ**足りない分だけ**マージする。

```ts
// dynamicScenario1.ts
requiredCapabilities: {
  productLifecycle: true,        // productLifecycleOverrides が効くために必須
  supplyPremiumFeedback: true,   // 殺到→翌期プレミアム低下の内生競争経路
  salesBaseAccumulation: true,   // 市場別営業基盤の蓄積
}
```

`applyScenarioRequiredCapabilities(config, definition)`（`companyLab/runner.ts`）。

**#04 の条件との対応**

| 条件 | 対応 |
|---|---|
| DS1 だけ | 宣言を持つのは DS1 のみ。他シナリオは `config` を同一参照で返す |
| 他 Scenario の挙動不変 | テストで同一参照を検証。既存3135テスト全 pass |
| Standard AI policy 変更なし | 未変更 |
| グローバル default 変更なし | `MARKET_PARAMETERS_V1` / `PRODUCT_LIFECYCLE_PARAMETERS_V1` とも未変更 |
| Scenario definition を SSoT | 宣言はシナリオ定義に存在。呼び出し側は関知しない |
| Console 専用の別需要式を作らない | 需要式は既存のまま。フラグのマージのみ |

**無効化はできない**設計にしてある（宣言できるのは有効化 true だけ）。
呼び出し側が明示的に設定した値は保持される。

**実測**（Management Console の `createSimulationSession` 経由）:
```
dynamic-scenario-1  sai5 = {"productLifecycle":true,"supplyPremiumFeedback":true,"salesBaseAccumulation":true}
baseline            sai5 = null
```

さらに「`productLifecycleOverrides` を持つのに `productLifecycle` を宣言していない」
定義を検出するテストを入れ、将来のシナリオ追加時の設定漏れを防いでいる。

## 1. 発端と、**前回報告の訂正**

Phase A の SAI-3A グリッド探索（`/tmp/pd_labor` の48コミットスタック）で、
14点すべてにおいて「通常審査を通った借入 = 0.00回」と観測し、
**「financing.ts の資金繰り判断が実質的に働いていない」と報告した。**

**この報告は誤りだった。** 本診断で、通常融資の承認経路は正常に動作することを確認した。
`origin/develop/v2` 上で同じ標準初期条件・同じシードを実行すると、
**120行中44行で通常融資が承認され、承認総額は 264,175,616 USD** である。

誤った結論に至った原因は2つあり、両方とも私の側にある。

### 1-1 グリッドの軸のラベルを取り違えていた（主因）

`GridPoint` の `shortTermLoansUsd` / `longTermLoansUsd` を、私はコメントで
「借入枠（資金繰り判断が働く余地を決める副軸）」と説明していた。
**実際にはこれは既存の借入残高である。**
`financing/initialPortfolio.ts` が `financeState.shortTermLoans` / `longTermLoans` を
1対1で `LoanRecord` へ写し、それが `borrowingCapacity` の `existingLoanBalance` になる。

```
追加借入可能額 = max(0, grossLimit − existingLoanBalance)
```

つまり私はグリッドで「余力を増やす軸」のつもりで**債務を増やしていた**。
P5/P6/P7 では債務を 95,000,000 USD（ST 40M + LT 55M）まで積み上げており、
担保ベース上限（約 37〜41M）を大きく上回るため、余力は構造的に恒久ゼロになる。

### 1-2 破綻していた点では凍結が重なっていた（副因）

債務を上げなかった点（P0〜P4, R1, R2, R4〜R6）は、48コミットスタックの
PD労働係数 1.8 により全社が支払不能に至っており、
`underwritingFrozen = creditTier === "E" || severeArrears || insolvent` で
通常融資が停止していた。これは**設計どおりの挙動**である。

### 1-3 ただし「P5は破綻率0%なのに承認0」は1-1だけで説明できる

`sai3a-grid-search.json` を読み直すと P5 は破綻率 **0%**、R3 は **5%**、P6 は **2%** で、
それでも通常融資 0.00 だった。これらはすべて債務を 84〜95M へ引き上げた点であり、
**1-1（債務過大）だけで完全に説明がつく**。凍結では説明できない。

**なお本ブランチには48コミットスタックが無いため、スタック側の数値そのものは
ここでは再現していない。** 上記は develop/v2 上での対照実験と、
スタックの成果物JSON（読み取りのみ）の突き合わせによる。

## 2. 通常融資の処理経路（実コード）

```
① standardAi/decision/finance.ts  buildStandardAiFinancingRequest
     desiredAmountUsd = cash < targetMinimumCash ? targetMinimumCash − cash : 0
     desiredLoanType = "workingCapital", 満期4Q, 満期一括, emergencyAcceptable = true
        ↓
② financing/liquidityClose.ts  planQuarterFinancing      ← 期首（前期末情報のみ）
     ├ computeCreditScore                → tier A〜E
     ├ checkCovenants                    → anyBreach
     └ computeBorrowingCapacity          → availableAdditionalCapacityUsd
        ↓
③ financing/bankUnderwriting.ts  underwriteLoanApplication
     frozen なら 承認0
     それ以外 approvedAmountUsd = min(desiredAmountUsd, availableAdditionalCapacityUsd)
        ↓
④ financing/liquidityClose.ts  closeQuarterWithFinancing
     normalDrawUsd = plan.underwriting.approvedAmountUsd
     → LoanRecord を生成（isEmergency: false）
     → Pass1 で loanDrawUsd として現金へ反映
        ↓
⑤ 緊急融資の判定（通常融資「後」の不足額に対してのみ）
     shortfall = max(0, 利息 + 約定元本 − max(0, Pass1後の現金))
     shortfall > 0 かつ emergencyAcceptable なら緊急融資
        ↓
⑥ totalLoanDrawUsd = normalDrawUsd + emergencyDrawUsd
   → Pass2 で確定、endingShortTermLoans / endingLongTermLoans へ反映
```

### 2-1 借入余力の式

```
collateralBasedLimit = 売掛金×0.7 + 使用可能原料×0.4 + 未着原料×0.15 + 製品×0.3
earningsBasedLimit   = max(0, 前期EBITDA相当【四半期値】) × 2.0
creditTierCap        = max(0, 純資産) × {A:1.5, B:1.1, C:0.75, D:0.4, E:0}

grossLimit           = min( max(collateralBasedLimit, earningsBasedLimit), creditTierCap )
availableAdditional  = frozen ? 0 : max(0, grossLimit − existingLoanBalance)
```

## 3. ゼロ承認の直接原因

**標準初期条件が、担保ベース上限（約37,000,000 USD）を大きく上回る
既存債務（57,000,000 USD = ST 24M + LT 33M）を最初から持っている。**

したがって turn1 の時点で `availableAdditionalCapacity = max(0, 37.17M − 57M) = 0`。
**会社は健全（信用区分B・スコア75.3・純資産100,327,709 USD）である。**
債務超過でも延滞でもなく、凍結もされていない。それでも承認額は0になる。

turn5 で初期短期借入（満期4四半期の満期一括）が満期到来して返済され、
既存債務が 57M → 27.28M へ落ちる。これで初めて余力が生まれ、**turn6 から承認が始まる**。

| turn | 申請件数 | 承認件数 | 凍結件数 | 緊急件数 | 承認総額 |
| --- | --- | --- | --- | --- | --- |
| 1 | 15 | **0** | 0 | 0 | 0 |
| 2 | 0 | 0 | 0 | 0 | 0 |
| 3 | 15 | **0** | 0 | 0 | 0 |
| 4 | 15 | **0** | 0 | 0 | 0 |
| 5 | 15 | **0** | 0 | 15 | 0 |
| 6 | 15 | **15** | 0 | 0 | 161,501,101 |
| 7 | 15 | 14 | 0 | 0 | 9,548,660 |
| 8 | 15 | 15 | 0 | 0 | 93,125,854 |

**凍結件数は全期間で0。**
【用語是正・§11-6参照】却下は全て、既存借入残高(`existingLoanBalance`)が
`grossLimit`を上回った（＝`availableAdditionalCapacityUsd = max(0, grossLimit -
existingLoanBalance)`がゼロになった）ことによる。この`grossLimit`の算定基準
として`collateralBasedLimit`が選ばれていた（`bindingConstraint = collateralBased`）
というのは「担保が絞っている」ことを意味しない——`max(collateral, earnings)`の
うち担保ベース値の方が大きかったというだけであり、余力をゼロにした真因は
既存債務控除の方である（詳細は§11-6・§12の用語是正を参照）。
信用区分は却下61件のうち A が31件・B が30件、
つまり**却下されたのはすべて信用区分AまたはBの健全企業**である。

## 4. バグか、仕様・パラメータの問題か

**バグではない。** 三宅さん指定のチェック項目を個別に確認した結果は以下のとおり。

| チェック項目 | 結果 |
| --- | --- |
| 単位の取り違え（百万 vs ドル） | なし。全経路USD。`creditTierCap` = 純資産100,327,709 × 1.1 = 110,360,480 で整合 |
| 四半期値と年換算の混同 | **コードは自己整合**。入力名 `ebitdaLikeQuarterlyUsd`、係数名 `earningsMultiple`。ただし「四半期EBITDA×2.0」は年間EBITDA換算で0.5倍にあたり、一般的な2〜3倍より保守的（§6候補1） |
| 符号反転 | なし |
| DSCR・自己資本比率・流動比率・負債比率の分子分母 | covenant側。本件では `anyBreach = false` が全期間continuedで、拘束していない |
| 借入前後の状態の取り違え | なし。`prevFinanceState`（前期末）を使用。銀行が当期実績を見ない設計はコメントでも明示 |
| 参照タイミング | 正しい。期首に確定し、当期のturnResultは受け取れない関数シグネチャ |
| 既存債務の二重控除 | grossLimitの算定基準として選ばれた経路（担保ベース）では**なし**。純資産経路（tierCap）は純資産が債務控除後の値なので二重性はあるが、tierCapがgrossLimitを実際に縮小した行は§13の集計で0件（develop/v2）〜15件（pd_labor）であり、大半の行では影響しない |
| undefined・初期値による自動却下 | turn1の `earningsBasedLimit = 0`（前期実績が無いため）は事実。ただし担保ベースが常に上回るため原因ではない |
| **健全な初期企業も却下されるか** | **却下される。これが本件の核心**（§3） |
| 承認されたのに実行されない経路 | **ない。** turn6: 承認 11,321,353 → `loanDrawUsd` 11,321,353 → 短期借入 2,530,739 → 13,852,092 と正しく反映 |
| 通常と緊急の二重実行 | なし。turn5 は 通常0 + 緊急 2,530,739 = `loanDrawUsd` 2,530,739 |

したがって、これは**標準初期条件（fixture）と与信パラメータの組み合わせの問題**であり、
三宅さんの指示に従い**私の判断でパラメータを緩めることはしない**。§6に候補を数値で示す。

### 9-2 候補1の矛盾の根本原因（三宅さんの手計算 vs 前回スクリプトの0）

### 9-4 四半期EBITDA vs 年間換算EBITDA — 明示的な仕様判断（コードのバグではない）

現行実装（`liquidityClose.ts:86-88, 128`）:
`ebitdaLike = 前期の営業利益 + 前期の減価償却`（**四半期値そのもの**、年換算しない）。
`earningsBasedLimitUsd = ebitdaLikeQuarterlyUsd × earningsMultiple`（`borrowingCapacity.ts:53`）。
現行`earningsMultiple = 2.0`は、**四半期EBITDA×2.0**であり、年換算では**年間EBITDA×0.5**に相当する

| 解釈 | multiplier=2.0（現行） | multiplier=8.0（候補1） |
| --- | --- | --- |

**これはコードのバグではなく、明示的な仕様判断（スペック上の選択）としてオーナー確認が必要な点**:
現行コードは「四半期EBITDA×multiplier」方式であり、`multiplier=8.0`は
（三宅さんの意図どおり）四半期基準のまま倍率を上げるだけで年間EBITDA×2相当の水準

薄める必要があり、両者は同じ経済的意味を異なる`multiplier`値で表現する等価な選択肢。

## 11. 同一時点スナップショット基盤（三宅さんの是正指示・2026-08-03）

### 11-1 背景と問題意識

§9の是正で「参照時点の混在」を解消したが、その是正自体もB/S行やturn間の
手動再構成（前turnのB/S値を担保入力として近似する等）に依存しており、
近似の域を出ていなかった。三宅さんの指摘（tierCap 118.461M vs 119.933Mの不一致等）を

オブジェクトそのものを、その呼び出しの場でそのまま捕捉する**基盤を構築した。

### 11-2 捕捉の仕組み（observation-onlyフック）

`app/lib/v2/financing/liquidityClose.ts`に、以下の2つの登録式コールバックを追加した:

- `setUnderwritingSnapshotObserver(observer)`: `planQuarterFinancing`内で

1. オブザーバーは`let`変数に保持され、デフォルトは`undefined`。`if (observer)`の

2. コールバックは値を読み取って配列にpushするだけで、会社状態・返り値・RNGを

3. `SNAP-1`テスト（`app/lib/v2/financing/__tests__/underwritingSnapshotInvariants.test.ts`）で、

### 11-2a オブザーバー機構のコードレビュー向け詳細（三宅さんの是正指示・2026-08-04）

**登録/解除の方法**: `setUnderwritingSnapshotObserver(fn)` / `setLoanRollForwardObserver(fn)`
にコールバックを渡すと登録、`undefined`を渡すと解除。呼び出し側は必ず
`try { ...シミュレーション実行... } finally { setXxxObserver(undefined); }`の形で、
finally節で解除する（`scripts/financingSnapshotDiagnosis.ts`の`collectSnapshots`、
`app/lib/v2/financing/__tests__/underwritingSnapshotTestHelpers.ts`の`runOnce`を参照）。
これにより、シミュレーション実行中に例外が投げられても、オブザーバーが
登録されたまま他の実行・他のテストへ残ることがない。

**オブザーバー自体が例外を投げた場合**: `liquidityClose.ts`内の`invokeObserverSafely`
ヘルパー関数が、オブザーバー呼び出しを`try/catch`で囲む。オブザーバーが例外を
投げても`console.error`に記録するだけで処理を継続し、**本番の四半期クローズ処理
（`planQuarterFinancing`・`closeQuarterWithFinancing`の残りの計算・戻り値）へは
一切伝播しない**。これは今回追加した安全対策であり（三宅さんの是正指示4番への
対応）、`SNAP-12`テストで、意図的に例外を投げるオブザーバーを登録した状態で
8四半期のシミュレーションを実行し、(a) シミュレーション全体が例外を投げずに
最後まで完了すること、(b) オブザーバーは実際に呼ばれたこと（例外を投げる前の
処理は実行されたこと）を確認済み。

**テスト分離**: `underwritingSnapshotObserver`/`loanRollForwardObserver`は
モジュールスコープの`let`変数であり、プロセス内でグローバルに共有される。
本ブランチのテスト（`underwritingSnapshotInvariants.test.ts`等）は、各テストが
`runOnce()`という1つの同期的な関数呼び出しの中で「登録→実行→finally解除」を
完結させており、かつ`node --test`はデフォルトで同一ファイル内のテストを
直列実行するため、現状のテストスイートでは競合は発生しない。
**将来「複数テストを並行実行するオプション」を有効化する場合は、この
グローバル状態が競合点になりうる**（対策案は`liquidityClose.ts`の
`setUnderwritingSnapshotObserver`のドキュメントコメントに記載）。

**Pass1/Pass2との関係（二重捕捉の防止）**: `closeQuarterWithFinancing`内部では
`finance/quarterClose.ts`の`closeFinancialQuarter`をPass1（予備）・Pass2（確定）の
2回呼ぶが、`loanRollForwardObserver`の発火はこの2回呼び出しの**外側**、
`closeQuarterWithFinancing`全体の最後（return直前）に1箇所だけ置かれている。
したがって1社×1turnの引受判断につき、オブザーバーは**必ず1回だけ**発火する
（Pass1/Pass2それぞれで発火するわけではなく、二重捕捉は構造的に発生しない）。

**未登録時の挙動（改めて明示）**: `setUnderwritingSnapshotObserver`は
`planQuarterFinancing`内で`invokeObserverSafely(underwritingSnapshotObserver, ...)`
として呼ばれるが、`invokeObserverSafely`の実装は`if (!observer) return;`から
始まる——未登録時（`observer === undefined`）はこの1行のガード以外、
一切の追加処理（オブジェクト構築・関数呼び出し）を行わない。
`setLoanRollForwardObserver`側は、外側の`if (loanRollForwardObserver)`ガードが
既にこの役割を果たしており（未登録時は`priorShortTermLoansUsd`等の集計
そのものがスキップされる）、`invokeObserverSafely`はその内側で追加の
例外隔離のみを行う。**いずれの経路でも、未登録時に本番処理へ追加される
コストはガード判定1回のみ（実質ゼロ）である。**

### 11-4 tierCap不一致（118.461M vs 119.933M）の根本原因の確定

三宅さんが指摘した具体的な不一致——turn3の実測tierCapが以前は約118.461Mだったのに、
候補比較表では119.933Mになっていた——の原因を特定した。

`creditTierCapUsd = max(0, totalEquityUsd) × creditTierEquityMultiple[tier]`
（`borrowingCapacity.ts`）。turn3・tier Bで`multiplier=1.1`。

- **今回の同一時点スナップショットでの実測**: `totalEquityUsd = 107,691,743`
  （`borrowingCapacityInput.totalEquityUsd`をそのまま参照）。
  `107,691,743 × 1.1 = 118,460,917.3` → tierCap = **118,460,917**（実測と一致）。
- **§9の候補スクリプトで使っていた値**: `equity: 109,030,429`
  （turn3自身の`totalEquityUsd`表示値を使っていた）。
  `109,030,429 × 1.1 = 119,933,471.9` → tierCap = **119,933,472**（三宅さんが指摘した値と一致）。

**原因は「equityの参照時点」**（三宅さんが挙げた選択肢の1つ）。
`planQuarterFinancing`の実装（`liquidityClose.ts`）では
`totalEquity = fs.capitalStock + fs.retainedEarnings`が`input.prevFinanceState`
（前期末の財務状態）から計算される——既存借入残高・EBITDA代理と全く同じ
「前期末＝引受時点」の参照規律に従っている。turn3の実測値107,691,743は
**turn2末の純資産**であり、§9のスクリプトが使った109,030,429は**turn3自身の
（当期末に近い）純資産表示値**だった。既存借入残高・EBITDA代理では§9是正時に
このタイミングのずれに気づいていたが、equityについては見落としていた。

これは**コードのバグではない**（`planQuarterFinancing`は一貫して前期末値を参照する
設計を守っている）。§9の候補スクリプトが、この一貫した規律から**equityだけ**外れて
当期値を使ってしまっていた診断側の入力ミスである。今回のスナップショット基盤は
`borrowingCapacityInput`を分解せずそのまま使うため、この種の取り違えが
構造的に起こり得ない。

### 11-6 用語の是正: 「拘束条件」の使い方

**是正**: `grossLimit = min(max(collateralBasedLimit, earningsBasedLimit), creditTierCap)`は
`max()`を含むため、「担保上限 > 収益上限」は「担保が絞っている（拘束している）」ことを
**意味しない**。正しい表現は「grossLimitの基準として担保ベース値が選ばれた」
「担保ベース値が収益ベース値を上回った」である。「拘束条件(binding constraint)」という
語は、実際に上限を縮める側——`creditTierCap`（外側の`min`）、または既存債務控除
（`availableAdditionalCapacityUsd = max(0, grossLimit - existingLoanBalance)`）——にのみ
用いる。§5・§6・§9で「binding: collateralBased」等と表示していた既存の`bindingConstraint`
フィールド自体（コード内の命名）は変更しないが、**このドキュメントでの説明文言**は
本セクション以降、`describeGrossLimitBasis()`（`scripts/financingSnapshotDiagnosis.ts`）の
表現に統一する。§5・§9で「拘束条件: collateralBased」という表現を使った箇所は、
「grossLimitの基準として担保ベース値が選ばれた（tierCapが実際に絞っているわけではない）」
という意味に読み替える必要がある——コードの`bindingConstraint`フィールド名自体が
`max()`部分の内訳を指す名前になっており、真に上限を縮める`min(..., tierCap)`とは
別の概念であることに、本セクションで初めて気づいた。**用語自体の整理が必要
（コード変更は不要。フィールド名の意味を正しく説明するドキュメント側の是正で足りる）。**

### 11-10 候補5（`grossLimit = min(max(担保, 収益, tierCap×w), tierCap)`）— 全中間値

## 14. 数値の価値分類（Exact live value / Derived exact value / Approximation）

本ドキュメント§11以降の数値は、原則として以下のいずれかに分類される
（§9以前の数値のうち、担保上限の内訳分解に依存していた候補2・3・5関連の数値は、
§11-3で「Approximation（担保内訳0仮定の近似）」だったことが判明し、
§11以降の値で置き換えられた）。

- **Exact live value**: `computeBorrowingCapacity`へ実際に渡された`borrowingCapacityInput`、
  またはその戻り値`borrowingCapacityResult`／`LoanRollForwardSnapshot`のフィールドを
  そのまま表示した値。§11-2〜§11-5・§11-7〜§11-10の基礎データ（担保上限・収益上限・
  tierCap・grossLimit・既存債務・ロールフォワードの各列）はこれに該当する。
- **Derived exact value**: Exact live valueのみを入力とする決定的な計算式
  （例: `computeBorrowingCapacity`をExact live valueへ別パラメータで再適用した候補2/5の結果、
  `w×tierCap`等）。§11-7〜§11-10の候補比較列はこれに該当する。
- **Approximation**: 真値を直接取得できず、別の値で代替・推測した値。
  §9-2・§9-3の担保上限内訳（原料在庫の輸送中/利用可能を0と仮定）、および
  §9-3の候補5表（equityを当期値で代用していた）がこれに該当し、
  §11の値で上書き・訂正済み。**現時点で本ドキュメントにApproximationとして
  残っている値はない**（§11以降は全てExact live valueまたはDerived exact value）。
  §9の該当箇所は削除せず、是正の経緯として残す（§9冒頭の記述どおりBEFORE/AFTER対比のため）。

**「完全一致」「実測」という語は、本ドキュメントでは同一時点の実データを指す場合にのみ使う。**
§9で一部「実測」と表記していた担保上限の内訳分解値は、正しくは近似値だった
——§11-3で訂正済み。

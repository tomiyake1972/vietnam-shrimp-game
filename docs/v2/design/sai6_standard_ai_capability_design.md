## 0. 結論の先出し

### 0.1 いちばん重要な発見 — 縮小すべきは設備ではなく労務である

> **【v2 訂正】** v1 は fixture の初期値（6,000人・$6.0M/四半期）から推定していたが、
> Phase 0-5 の実測で2点を訂正する。
> (1) **AI はすでに人員を削っている**（6,000人 → 平均4,266人）。問題は「削らない」ことではなく
> **「乱高下していて、削りすぎと持ちすぎを繰り返している」**ことである。
> (2) 遊休比率は条件によって 44.2%（control）〜 61.3%（allOn）。`decision/labor.ts:15-23` の
> 「6割前後」というコメントは allOn 相当の条件で正しかった。

実測（control 生存期間、1社1四半期あたりの平均）:

| 項目 | 金額 | 倍率 |
|---|---:|---:|
| **常用人件費** | **$4.27M** | — |
| うち**遊休**（未配属） | **$2.03M**（44.2%） | — |
| 工場固定費 ＋ 固定ユーティリティ | $1.45M | 常用人件費の 0.34倍 |
| 減価償却 | $1.98M | 稼働率非依存 |
| capex保守費 | $0.00M | 代表シナリオでは capex が完成しない |

**常用人件費は工場固定費＋固定ユーティリティの 2.9倍**であり、能力余剰のコストは労務側にある。

さらに決定的なのは**制約別の「作れなかった量」**である（control 生存期間、平均）。

| 制約 | 欠品量 |
|---|---:|
| **原料制約** | **7,259 t/Q** |
| **労務制約** | **2,704 t/Q**（208四半期中131回、63%で発生） |
| 設備制約 | 83 t/Q |

- **設備制約はほぼ効いていない**（労務の 3%）。設備を減らしても増やしても生産は変わらない。
  → Phase 2（設備休止）を SAI-6 から外すご判断は、実測に照らして妥当である。
- **労務制約は 63% の四半期で発生**しており、人員を持つことには実際の価値がある。
  → 一方通行の削減は誤りで、段階的調整に経済的意味がある。
- **原料制約が最大**（労務の 2.7倍）。SAI-6 の能力調整だけでは default 率の改善に
  構造的な上限があることを、あらかじめ明記しておく（§0.4）。

なお **5社とも工場を1つしか持たない**（`standardBaseline.ts:64-74`）ため、
既存の工場単位休止フックは「事業の全停止」しか表現できず、能力調整の手段として使えない。

### 0.4 事前の但し書き — SAI-6 の効果には構造的な上限がある

実測（§0.1）のとおり、**原料制約による欠品（7,259 t/Q）が労務制約（2,704 t/Q）の 2.7倍**である。
SAI-6 が労務・設備の能力調整と価格戦略に集中する以上、default 率の改善幅には上限がある。

原料が不足する主因は調達の資金制約と考えられる（`PROCUREMENT_CASH_CONSTRAINED` が
allOn 32Q で 566回発火）。これは**設計補正A（二段階財務）が直接効きうる領域**であり、
**SAI-6 の中で最も default 率に効くのは、能力調整でも価格でもなく資金計画の可能性がある**。
このため §7 の実装順序では二段階財務を Phase 1 の先頭へ置いている。

## 2. 【テーマ5】AI 意思決定アーキテクチャ

### 2.1 現在の順序と、その問題

```
observation → pressures → sales → production → { procurement, labor, finance, capex }（4つは相互に独立）
```

真の依存は3本だけである（`policy.ts:109,113,114,120`）:
`sales.desiredByProduct → production` / `production.productionPlans → procurement, labor` /
`production.neededByProduct → capex`。

問題は3つ。

1. **需要見通しが無い。** 能力を増やす/維持する/縮小するの判断は本質的に
   「これから需要はどうなるか」に依存するが、現在その概念自体が存在しない。
   代理指標（ライフサイクルトレンド、供給圧力EWMA）はあるが既定パラメータで不活性。
2. **能力調整が生産計画の下流に埋もれている。** 労務は `productionPlans` を見て
   必要人数を逆算するだけで（`decision/labor.ts:69-72`）、「そもそもこの能力を持ち続けるか」
   という判断をしていない。
3. **財務が最上流の情報しか見ていない。** 借入額は「期首現金 − 目標バッファ」の差だけで決まり
   （`decision/finance.ts:33`）、当期の調達支出・人件費・capex 支出を知らない。
   資金計画が計画の受け皿になっていない。

### 2.2 提案する意思決定順序（**設計補正A: 財務の二段階化**を反映）

```
 [0] 観測構築            buildStandardAiObservation          （財務KPIを追加）
      ↓
 [1] KPI 算定            computeStandardAiKpis               （PressureScores を拡張・再編）
      ↓
 [2] 需要見通し ★新設     buildDemandOutlook                  （§2.5 の情報境界を厳守）
      ↓
 [3] 能力ポジション判定 ★新設  assessCapacityStance            （商品別設備 / 全社労務 を分離: §3.1-B）
      ↓
 [4] **事前資金枠の算定** ★新設  buildFundingEnvelope          ← 財務の第1段
      ↓  期首現金・借入余力・目標バッファから「今期使える上限」を先に決める
 [5] 価格戦略 ★新設       buildPricingStance                  （§4）
      ↓
 [6] 販売計画            buildStandardAiSalesPlans
      ↓
 [7] 生産計画            buildStandardAiProductionPlans
      ↓
 [8] 労務能力調整        buildStandardAiWorkerAssignments     （[3] の stance と pendingHires を受ける）
      ↓
 [9] 調達計画            buildStandardAiProcurementPlan
      ↓
[10] 設備能力調整        buildStandardAiCapexDecision         （増設・未着工案件の取消）
      ↓
[11] **必要借入額の算定と計画の縮小** ★新設  reconcileFundingPlan  ← 財務の第2段
      ↓  各計画の支出見込みを積み上げ、[4] の枠を超えたら優先順位に従って縮小する
[12] 最終的な意思決定一式を返す
```

#### 設計補正A: 財務の二段階構造

**第1段（[4] 事前資金枠）**

```
fundingEnvelope = 期首現金 + 借入余力（availableAdditionalCapacityUsd）
                − 目標最低現金バッファ（targetMinimumCashUsd）
                − 当期に確定している支出（返済元本・利息・capex分割払い）
```

これを先に確定させ、以降の計画（価格・販売・生産・労務・調達・設備）はこの枠を上限として作る。

**第2段（[11] 必要借入額と計画の縮小）**

```
plannedOutflow = 原料買付 + 人件費（常用+臨時+残業+採用/解雇の一時費用）
               + 販管費 + capex分割払い + 返済 + 利息
requiredBorrowing = max(0, plannedOutflow + 目標バッファ − 期首現金)

if requiredBorrowing > 借入余力:
    優先順位に従って計画を縮小する
```

**縮小の優先順位（案）**。逆転できない制約から順に守る。

| 順位 | 対象 | 理由 |
|---:|---|---|
| 1 | **既存契約の履行に必要な原料・生産** | 履行できないと延滞・信用毀損に直結する |
| 2 | 常用人件費 | 削減には解雇コストと再取得コストがかかる（往復3四半期が損益分岐、§3.2.2） |
| 3 | 新規成約に対応する原料・生産 | 減らせば売上機会を失うが、当期の債務不履行にはならない |
| 4 | 臨時ワーカー・残業 | 当期限りの費用で、翌期に持ち越さない |
| 5 | **新規 capex 提案** | 最も後回しにできる。未着工なら取消も可能 |

**実測に基づく注記（§0.1 の §1.7）**: 生存期間中、借入余力を超えた四半期は **0/208 件**だった。
つまり破綻は「借入枠が尽きた」ことでは起きていない。
したがって**二段階財務の主たる価値は「枠を超えないよう縮小すること」ではなく、
「当期の支出見込みを事前に把握して必要額を借りること」にある**。
現状は「期首現金 − 目標バッファ」の差だけで借入額を決めており（`decision/finance.ts:33`）、
**枠に余裕があるのに借りずに現金が尽き、調達制約から生産不能へ連鎖する**構造になっている。
第2段の縮小ロジックより、**第1段と `requiredBorrowing` の算定のほうが効果が大きい可能性が高い**。

### 2.3 この順序にする理由

- **[2] 需要見通しを最上流に置く**のが今回の設計の核である。能力調整も価格も、
  「一時的な変動か、恒久的な変化か」の判定なしには決められない。現在この判定は
  labor が2時点比較で局所的に行っているだけ（`decision/labor.ts:103-104`）で、
  他のドメインと共有されていない。共通の見通しを1箇所で作り、全ドメインが同じ前提で動く形にする。
- **[3] 能力ポジション判定を独立させる**ことで、「増やす／維持する／縮小する」という
  三択が明示的な出力になる。現在この判断は capex と labor に別々に埋め込まれており、
  互いに矛盾しうる（例: 労務は削っているのに設備は増設提案を出す）。1箇所で決めて両者へ配る。
- **[4] 価格戦略を販売計画から分離する**。現在は `decision/sales.ts` の中に
  数量ロジックと価格ロジックが同居しており、価格が在庫だけを見る構造になっている。
  分離して、能力余剰・市況・原価を受け取れるようにする。
- **[4]/[11] 財務を二段階にする**（設計補正A）。「最後へ移す」だけでは、
  計画が枠を超えたときに縮小する手段がない。先に枠を決め（[4]）、
  計画を積み上げた後に必要額を算定して超過分を縮小する（[11]）。
  これは現在の最大の構造的欠陥の解消であり、実測（§0.4）に照らすと
  **SAI-6 の中で最も default率に効く可能性がある**。

### 2.4 需要見通しの情報境界（**厳守事項**）

`buildDemandOutlook`（[2]）は、**AIがその時点で知り得ない内部情報を一切参照してはならない**。

**参照してよいもの（すべて既存の情報境界の内側）**

| 種類 | 具体例 | 出所 |
|---|---|---|
| 公開済みの過去実績 | 前期の市場結果、前期の対象需要、前期の実現価格 | `PublicMarketInfo.lastMarketResult` |
| 現在の自社観測 | 完成品在庫、原料在庫、能力、人員、財務状態 | `CompanyOwnState` |
| 既知の契約 | 未履行契約の数量・納期・単価（＝確定した将来需要） | `ownState.contracts` |
| 公開トレンド | ライフサイクル構成比とその前期差分、供給圧力EWMA | `productLifecycleOutlook` / `productSupplyPressureOutlook` |

**参照してはならないもの**

- 将来のライフサイクル曲線（`computeMarketProductMix(turn + n)` の直接評価）
- シナリオの将来ターン入力（`getScenarioTurnInput` の未来分）
- 乱数の結果（品質事故の抽選など）
- 他社の非公開の計画・状態
- 当期の市場結果（まだ確定していない）

**予測値と確度を分けて持つ。**

```
DemandOutlook {
  byProductMarket: {
    committedTons        // 既知の契約（確度 = 1.0。確定した将来需要）
    expectedTons         // 予測値（過去実績＋公開トレンドの外挿）
    confidence           // 0〜1。何四半期先か・トレンドの安定性・データ点数から決まる
    horizonQuarters      // 何四半期先の見通しか
  }
}
```

能力ポジション判定（[3]）は **`committedTons` と `expectedTons × confidence` を区別して使う**。
- **縮小（`contract`）の判断は保守的に**: `committedTons + expectedTons × confidence` を下限として使い、
  見通しが不確かなら削らない。
- **拡大（`expand`）の判断はさらに保守的に**: 確度の高い需要だけで判断する。

確度が低いときに「予測が外れても致命傷にならない側」へ倒すのが原則である。

新設は [2][3][4]、移動は [10] のみ。既存の真の依存3本は保たれる。

## 3. 【テーマ1・3】能力調整ロジック

### 3.1 能力ポジション判定（`assessCapacityStance`）

#### 3.1-A 4つの姿勢

| stance | 意味 | 発動条件（実測に基づく推奨初期値） |
|---|---|---|
| `expand` | 能力を増やす | 不足が **2四半期**連続、かつ市場が過剰供給でない |
| `hold` | 維持する | 保有が必要量の **100〜115%** の帯にある（デッドバンド） |
| `trim` | 可逆な範囲で縮小 | 余剰が **1四半期**（残業・臨時の停止のみ） |
| `contract` | 恒久的に縮小 | 余剰が **3四半期**連続、かつ需要見通しが回復しない |

**拡大側（2Q）を縮小側（3Q）より短くする**のは、実測で
**不足の機会損失（$1,068/t）が遊休の費用（$1,000/人/四半期 ≒ $167/t）の 6.4倍**であるため。
非対称の根拠を実測値で持てるようになった。

縮小側 3Q は `(解雇費 + 採用費) ÷ 四半期給与 = ($2,000 + $1,000) ÷ $1,000 = 3` とも整合する
（3四半期以上続く余剰でなければ、削って戻す往復が損になる）。

`sustainedShortageQuarterThreshold` / `sustainedExcessQuarterThreshold`
（`parameters.ts:107,109`、現在は参照ゼロのデッドパラメータ）を、この persistence 閾値として実接続する。

#### 3.1-B **設計補正B: 商品別設備能力と共有労務を分離する**

> **商品別の capacity stance をそのまま常用人員の削減へ合算してはならない。**

**実測による根拠**（`sai6_phase0_measurement_report.md` §1.5）:

| 指標 | control 生存期間 |
|---|---:|
| HOSO 余剰 | 4,743 t/Q |
| PD 余剰 | 3,122 t/Q |
| VAP 余剰 | 2,796 t/Q |
| **商品別余剰の単純合計** | **10,661 t/Q** |
| 共通前処理の余剰 | 8,951 t/Q |
| 労務余剰（遊休人員×効率） | 12,167 t/Q |
| **商品別合計 > 共通余剰 となった標本の割合** | **100.0%（全標本）** |
| 超過分の平均 | **1,710 t/Q** |

原因は構造的である。標準初期条件の名目能力は
HOSO 10,000 ＋ PD 8,000 ＋ VAP 6,000 = **24,000 t** に対し、
共通前処理は **22,000 t** しかない（`standardBaseline.ts:68-71`）。
**商品別ラインの合計が共通工程を 2,000t 上回っているため、
商品別余剰を単純合計すると必ず共通工程のボトルネック分を二重に数える。**

#### 分離した3つの軸

```
軸1: 商品別の設備能力      hoso / pd / vap の各ラインごとに独立
       → 使い道: 商品別の設備投資判断（増設・見送り）と販売数量の上限
       → 実測では設備制約の欠品が 83 t/Q しかなく、当面の主役ではない

軸2: 共通工程の能力        commonProcessing（全商品で共有）
       → 使い道: 「全社としてどれだけ作れるか」の上限
       → 軸1の合計ではなく、この値が全社の生産上限を決める

軸3: 全社の労務能力        常用・臨時・残業（全商品・全ラインで共有）
       → 使い道: 常用人員の増減判断
       → 実測では労務制約の欠品が 2,704 t/Q・63%の四半期で発生する主役
```

#### 全社必要人員の算定規則（二重計上を構造的に防ぐ）

常用人員の必要量は、**商品別 stance の合算ではなく、全社の生産計画から一度だけ**導く。

```
全社の生産可能上限 = min( 共通工程の有効能力,          … 軸2
                          Σ_p 商品別の有効能力,        … 軸1（参考。通常は軸2が律速）
                          原料から作れる量 )

全社の計画生産量   = min( 全社の生産可能上限, 販売計画＋約定残から必要な量 )

全社の必要常用人員 = 全社の計画生産量 ÷ (常用効率 × 出勤率 × 技能)
                     ※ 残業ゼロ・臨時ゼロを前提とした「素の必要人数」
                     ※ 残業込み・臨時込みの必要人数を別に算出し、
                        「残業でカバーできるから常用は減らさない」判断に使う

削減余地           = 保有常用人員 − 全社の必要常用人員 × (1 + 安全余力)
```

**商品別 stance は人員の増減には直接使わない。** 商品別 stance が使うのは
(a) 商品別の設備投資判断、(b) 商品別の販売数量、(c) 商品別の価格判断 の3つに限る。

**検証方法**: `Σ 商品別余剰 ≠ 全社削減余地` であることをテストで固定する
（現在は 100% の標本で `Σ商品別 > 共通余剰` になっており、合算すれば必ず過大になる）。

### 3.2 【テーマ2】労務能力調整

#### 3.2.1 段階の定義と、現状の実装状況

三宅さんのご提示の順序に、現状の実装状況を突き合わせた。

| 段 | 内容 | 現状 | エンジン変更 |
|---|---|---|---|
| ① 残業削減 | `overtimeRate` を下げる | **実装済み**。`isShortage=false` なら 0（`decision/labor.ts:131`） | 不要 |
| ② 臨時停止 | `temporaryHeadcount` を減らす | **実装済み**。`isShortage=false` なら 0（`decision/labor.ts:130`） | 不要 |
| ③ 採用停止 | `sustainedShortage` でも採用しない | 未実装（不足なら常に採用） | 不要 |
| ④ 常用削減 | `regularHeadcount` を減らす | 機構は実装済み（damping 0.5、`:118`）だが**経済的トレードオフが存在しない** | **必要** |
| ⑤ 再採用 | 需要回復時に戻す | 機構は実装済み（同じ式、`:108`）だが同上 | **必要** |

①②は既に「不足でなければ即ゼロ」という強い実装になっている。したがって
**段階①②は実質「常に最初に削減される」状態にあり、SAI-6 の課題は③④⑤である。**

> **【v2 訂正】** v1 は「④の機構はあるが使われていない」と書いたが、実測では
> **AI は 6,000人 → 平均4,266人まで実際に削っている**。damping 0.5（`decision/labor.ts:118`）で
> 毎期「必要人数の半分まで」寄せるため、**削減速度は速いが上限がなく、乱高下する**。
> 実測の人員変動総量は 20ケース×平均10.4四半期で **50,961人**（1四半期あたり平均245人）。
> 解雇コストを導入すると、この乱高下だけで人件費の **11.5%（$101.92M / $887.29M）** に相当する費用が発生する。
> **したがって④の課題は「削らない」ことではなく「削り方に上限と観察期間がない」ことである。**

#### 3.2.2 ④⑤を成立させるためのエンジン変更（最小限）

解雇が無料である限り「段階的縮小」に経済的意味がない（§1.2）。
そこで**最小限の追加**を提案する。

```
finance/parameters.ts の labor ブロックへ追加:
  severanceCostUsdPerHead : 常用1人を減らすときの一時費用
  hiringCostUsdPerHead    : 常用1人を採る時の一時費用（募集＋立ち上げ）
```

- 実装箇所は `finance/quarterClose.ts` に「前期人数 vs 当期人数」の差分経路を1本追加し、
  `CostRecord`（`finance/types.ts:125-144`）へ `stepFixed` / `committed` として計上する。
  現在アダプタは当期人数しか渡していない（`companyLabAdapter.ts:263-265`）ので、
  前期人数の受け渡しが必要になる。
- **水準はご判断により確定**: **採用 = 1四半期分（$1,000/人）、解雇 = 2四半期分（$2,000/人）**。
- **実測による裏付け**（`sai6_phase0_measurement_report.md` §2）:
  この水準を現行AIの実績軌跡へ課すと、乱高下だけで **$101.92M**（人件費の 11.5%）の費用が発生する。
  これは遊休人件費（$2.03M/四半期 × 208四半期 ≒ $422M）と同じオーダーであり、
  **削減の速さと乱高下の抑制が実際にトレードオフになる**ことが数値で確認できた。
- **回収期間**: 1人削減の節約 $1,000/四半期に対し一時費用 $2,000 → **回収 2四半期**。
  削減して再採用する往復は一時費用 $3,000 なので、**3四半期以上続く余剰でなければ損**。
  これが §3.1-A の「余剰確認期間 3Q」を経済的に規定している。

#### 3.2.2b **設計補正D: 採用リードタイム（pendingHires）**

> **採用した人員が同じ四半期に即時能力化する設計にしてはならない。**

技能ramp の全面実装は Future とするが、**採用リードタイムだけは Phase 1 に含める**。

```
CompanyWorkforceState へ追加:
  pendingHires: readonly { readonly headcount: number; readonly effectiveFromPeriod: PeriodV2 }[]

規則:
  - 当期に決めた採用は pendingHires へ入る。当期の労働能力には一切寄与しない。
  - 原則として**翌四半期から**能力化する（リードタイム 1Q。ご判断6と整合）。
  - 採用の一時費用は**決定した四半期に**計上する（能力化を待たない）。
  - 解雇は即時反映とする（人員が減り、当期から人件費が下がる）。
    ＝ **増やすのは遅く、減らすのは速い**という非対称を明示的に持たせる。
```

**永続化**: `WorkforceState` への追加になるため、スキーマ版上げ（4→5）が必要。
`salesBaseState` / `marketEvolutionState` と同じ「追加的変更のみ・マイグレーション不要」方式を使う。

**実測での注記（正直な報告）**: Phase 0-5 のリプレイでは **リードタイム 0Q と 1Q で差が出なかった**。
理由は、リプレイした方針が「実際に不足したときだけ採用する」形のため、
208四半期で採用イベントが 7回しか発生せず、リードタイムの影響が現れる場面がほぼ無かったこと。
**これは「リードタイム1Qが不要」という根拠にはならない。** 効果は、AI が
需要見通しに基づいて**先行採用**するようになって初めて現れる。
検証は Phase 1 の全再シミュレーション（受入試験 S3）で行う。

#### 3.2.3 AI が労務判断で見るべき情報

三宅さんのご指示の観点に、実装可能性を突き合わせた。

| 観点 | 使う情報 | 現状 |
|---|---|---|
| **将来需要** | `demandOutlook`（[2] で新設） | 新設 |
| **稼働率** | **全社**の労務余剰＝`遊休人件費 ÷ 給与`（商品別余剰の合算ではない。§3.1-B） | **今すぐ計算できる** |
| **教育期間** | — | **エンジンに存在しない**（`skills` は fixture 固定）。SAI-6 では扱わず Future へ |
| **採用コスト** | `hiringCostUsdPerHead` | 新設（§3.2.2） |
| **解雇コスト** | `severanceCostUsdPerHead` | 新設（§3.2.2） |
| **品質維持** | 残業ストレス・臨時ストレス・急増産ストレスの寄与 | **既存**（`quality/parameters.ts:109-122`）。ただしAIは観測していない → KPIへ追加 |
| **遊休の実コスト** | `idleLaborCost` | **既存だがAIは見ていない**（`finance/types.ts:317`）→ 観測へ追加（最優先） |

**追加すべき最重要の観測は `idleLaborCost` である。** これが見えない限り、
AIにとって余剰人員を抱えるコストは永久にゼロである。実測では
control 生存期間で **$2.03M/四半期（常用人件費の44.2%）**、
allOn 生存期間で **$3.20M/四半期（同61.3%）** が見えないまま流出している。

同時に、**労務制約による欠品（2,704 t/四半期・63%の四半期で発生）も観測できるようにする**。
片方（遊休コスト）だけを見せると、AI は一方通行に削って欠品を増やす。
**「持ちすぎのコスト」と「足りないコスト」の両方を見せて初めて、段階的調整が意味を持つ。**

#### 3.2.4 推奨する初期閾値（実測に基づく）

`sai6_phase0_measurement_report.md` §2 で 18通りを総コスト比較した結果。
**18通りすべてが現行AIより改善し**、最良は次の組み合わせだった。

| パラメータ | 推奨初期値 | 根拠 |
|---|---:|---|
| **安全余力**（削減の上側帯） | **15%** | 実測で「不足人月0」を達成する最小値。10%では不足が発生。20%との差は $1.5M と僅少 |
| **余剰確認期間** | **3四半期** | 2Q より一貫して +$60M〜96M 良い。かつ `(解雇費+採用費)/給与 = 3` と整合 |
| **1Q当たり削減上限** | **15%** | 10%は削減が遅く人件費最大、20%は削りすぎて欠品回避価値を失う |
| **採用リードタイム** | **1四半期** | ご判断6。実測では差が出なかったが、それは現行方針が先行採用しないため |

この組み合わせの実測改善額は **+$203.31M（総コスト 20.6%改善、$989.21M → $785.91M）**。

**この数字の限界**: 実績軌跡を所与とした一次近似であり、絶対額の予測には使えない。
方針の相対比較にのみ使える。最終判断は Phase 1 の全再シミュレーションで行う。

#### 3.2.5 現行ロジックの既知の癖（設計時に踏まえる）

- AIの必要人数計算は**残業ゼロ・臨時ゼロ前提**（`decision/labor.ts:78-79, 97-98`）。
  したがって「残業でカバーできるから常用は減らさない」という判断が現状の
  `requiredRegular` からは導けない。段階的縮小を設計するなら、
  **残業込み・臨時込みの必要人数を別に計算する**必要がある。
- 過剰判定の分母は**当期の生産「計画」**であり実績ではない（`:71`）。
  原料不足で作れなかった期でも、計画が大きければ過剰判定が出ない。
- `temporaryHeadcount` / `overtimeRate` は状態に残らない（`workforce.ts:108-142`）。
  「臨時を段階的に減らす」には前期値を持つ必要があり、
  `WorkforceState` の拡張（＋永続化スキーマの版上げ）が要る。
  ただし現行は「不足でなければ即0」なので、**段階性が必要かどうかは要検討**。
  臨時は本来「即時に増減できる緩衝材」であり、段階的に減らす対象ではないと考える。

### 3.3 【テーマ3】設備能力調整（**SAI-6 では最小限**）

#### 3.3.1 ご判断と実測に基づくスコープ

ご判断2により **Phase 2（設備休止）は SAI-6 から外す**。
実測もこれを支持する: **設備制約による欠品は 83 t/Q** で、労務制約（2,704 t/Q）の 3% にすぎない。
**設備を止めても増やしても、当面は生産量が変わらない。**

| 選択肢 | SAI-6 での扱い |
|---|---|
| 継続稼働 | 既定 |
| 低稼働（生産を絞る） | **既に可能**。生産計画を減らせば低稼働になる。追加実装なし |
| **新規増設の抑制** | **Phase 1 で実装**（既存の `CAPEX_DEFERRED_OVERSUPPLY` 経路を能力ポジション判定へ接続） |
| **未着工案件の取消** | **Phase 1 で実装**（§3.3.2） |

#### 3.3.2 未着工案件の取消（Phase 1）— 落とし穴に注意

`applyCancelRequest` は `cumulativePaidUsd > 0` の案件に対して
**例外を投げる**（`capex/projectLifecycle.ts:162-164`）。したがって

現在の観測は `activeCapexProjectTargets`（Set）と `suspendedCapexProjectIds` しか持たず、

#### 3.3.3 将来ライン単位の休止を実装する場合の前提（記録として残す）

ご判断3により**固定費のライン別分解比率は今回決めない**が、
将来の検討のために制約を記録しておく。

- 5社とも工場を1つしか持たない（`standardBaseline.ts:64-74`）ため、
  既存の工場単位休止フック（`production/capacity.ts:30-42`、`runner.ts:1224` の
  `activeFactoryCount`）は「事業の全停止」しか表現できず、能力調整には使えない。
- ライン単位の休止を有効にするには、現在「工場数」ドライバーしかない固定費
  （`quarterClose.ts:383-384`）を「工場基礎 ＋ 稼働ライン別」へ分解する必要がある。

- ただし商品別ライン能力の合計（24,000t）は共通前処理（22,000t）を上回っており、
  **どのラインを止めても共通工程が先に律速する**（§3.1-B）。
  休止の経済効果を見積もる際は、この構造を踏まえる必要がある。
- 再稼働には **1四半期の立ち上げ遅延**を設ける（ご判断6）。遅延がないと毎期の振動が起きうる。

#### 3.3.4 観測のギャップ（Phase 1 で先に直す）

設備を扱わなくても、**能力を扱う以上これは必須**である。

- **AIが見ている能力は名目値で、エンジンの有効能力より約17%大きい。**
  エンジンは `× baseUtilizationRate 0.9 × equipmentAvailabilityRate 0.95 = 0.855` を掛ける
  （`production/capacity.ts:44-55`）が、観測は掛けていない（`observation.ts:82-103`）。
- **`decision/production.ts:34` と `:71-75` で capex 完成分の扱いが食い違う。**
  結果として capex 完成後は計画生産量の合計が必要量を下回る。

### 3.4 設備売却を実装しない理由（Future へ）

三宅さんのご質問（「設備売却まで実装する必要があるかどうか」）への回答である。
**SAI-6 では実装しない**（ご判断2とも整合）。理由は4点。

1. **会計恒等式に触れる。** `fixedAssetsGross` と `accumulatedDepreciation` は
   現在**加算のみ**（`quarterClose.ts:1074-1076`）。減額可能にすると、
   BS貸借一致（`quarterClose.test.ts:255`）・CF恒等式（`:262`）・
   直接法/間接法照合（`quarterClose.ts:1134-1135`）のすべてを再検証する必要がある。
2. **売却損益を受けるPL行が存在しない。** `ProfitAndLossStatement` に営業外損益の区分がない。
   新設するか売上原価へ押し込むかの判断が要り、いずれも既存テストへ広く波及する。
3. **既存設備は売れない。** レガシー資産には個別台帳が存在しない
   （`finance/depreciation.ts:10-14` に「精密な固定資産台帳は新設しない」と明記）。
   売却できるのは capex 経由で完成した資産だけになり、
   **ゲーム開始時の設備（＝過剰能力の本体）は売却対象にならない。** 効果が薄い。
4. **休止で目的の大半が達成できる。** 「能力を減らして固定費を落とす」という
   ゲーム上の意思決定は休止で表現でき、しかも可逆なのでゲーム性（判断の巧拙が出る）も高い。
   売却は不可逆で、32四半期のゲーム長では判断機会が乏しい。

**Future として残す**。もし将来実装するなら、capex 完成資産に限定し、
簿価は `capitalized × (1 − 経過/耐用)` から導出できる（`capex/depreciation.ts:70-82`）ため
新規台帳は不要である。ただし
`nonDepreciatingCapexGrossAtPeriodStartUsd`（`capexClose.ts:174-176`）が
レガシー資産の償却基数の除外項に使われている（`quarterClose.ts:694-696`）ため、
**`fixedAssetsGross` の減額と除外額の減額を厳密に同時・同額で行わないと
レガシー資産の減価償却が誤って跳ね上がる**。この落とし穴は設計書に残しておく。

## 4. 【テーマ4】価格戦略との連携

### 4.1 現状の限界

価格は「自社完成品在庫」と「前期設備稼働率」の2つだけで決まり、最大 −12%
（`decision/sales.ts:74-89`）。市況・原価・限界利益・営業基盤は一切入っていない。
さらに:

- **原価フロアが強制されていない。** `minimumAcceptablePriceUsdPerHosoEqKg` は
  計算されるが（`:70`）、askPrice との比較箇所がコードベース全体にゼロ。
  現状の値下げの下限は「在庫過剰度に基づく −12%」という機械的な上限だけが担保している。
- **AIは自分がいくらで売れたかを知らない。** 実現単価も限界利益率も単位変動費も観測できない。
- 値下げの効果は **−15.67% で飽和**する（`exp(3d)=1.6`）。それを超える値下げは
  成約力を1ミリも増やさずに単価だけ落とす純損である。

### 4.2 提案する価格判断の構造（**設計補正C: 価格下限を在庫の性質で区別する**を反映）

価格調整比率を、4つの入力から**上下限つきで**決める。

```
                          ┌── 原価フロア（**在庫の性質ごとに異なる**。§4.2-C）
                          │
priceAdjustmentRatio  ←───┼── 能力余剰（下げる圧力）
                          ├── 市況＝供給圧力（下げない圧力。値下げ競争の抑制）
                          └── 営業基盤・ライフサイクル局面（下げない圧力）
```

```
rawDiscount     = f_capacity(全社の能力余剰) + f_inventory(在庫過剰度)
marketDamper    = g(supplyPressureEwma)
baseDamper      = h(salesBaseScore)
lifecycleDamper = k(lifecycleTrend)

discount = clamp(rawDiscount × marketDamper × baseDamper × lifecycleDamper,
                 0, normalDiscountCap)               // 通常上限（ご判断5により当面 12%）
askPrice = max(basePrice × (1 − discount), 在庫区分ごとの下限価格)   // §4.2-C
```

#### 値下げ幅の上限（ご判断5）

| 種類 | 値 | 意味 |
|---|---:|---|
| **数学的な絶対上限** | **15.67%**（`ln(1.6)/3`） | 価格スコアの飽和点。これを超える値下げは成約力を1ミリも増やさず単価だけ落とす**純損**。パラメータとして明記し、コード上のハード上限とする |
| **通常上限** | **12%**（現行のまま据え置き） | ご判断5により、直ちには広げない。Phase 0-5 後に 12% と 15.67% を比較して決める |
| 値上げ方向 | **今回は見送り** | ご判断5 |

`sales/parameters.ts:66-67` のコメント（「約20%で上限」）は**誤り**なので、
式から導いた 15.67% へ訂正する。

#### 4.2-C **設計補正C: 原価フロアを一律のハード下限にしない**

> **在庫の性質によって「売らない損失」が異なるため、下限も分けなければならない。**

| 区分 | 下限価格 | 根拠 |
|---|---|---|
| **① 新規生産を必要とする販売** | **総原価**（変動費 ＋ 配賦固定費 ＋ 最低貢献利益）＝ 現行の `minimumAcceptablePriceUsdPerHosoEqKg` | まだ作っていないので、作らない自由がある。総原価を割るなら作らないほうがよい |
| **② 通常の完成品在庫** | **変動費 ＋ 最低貢献利益** | すでに作ってあり原価は埋没している。変動的な販売物流費と最低限の貢献が取れれば売る価値がある |
| **③ 期限接近在庫** | **廃棄損との比較で決める**（下限を下回る受注を許容する） | 売らなければ `finishedGoodsWriteOffLoss` として全損する。§4.2-C1 |

#### 4.2-C1 期限接近在庫の判定式

```
売る場合の損益   = askPrice × 数量 − 増分販売物流費 × 数量
売らない場合の損益 = − 廃棄損（＝ 在庫評価額の全額）
                    − 廃棄に伴う費用（あれば）

→ askPrice > 増分販売物流費 − (在庫評価額 ÷ 数量)  なら売ったほうがよい
```

在庫評価額が正である限り、**この下限は変動費すら下回りうる**。
つまり**原価割れ処分を明示的に許容する**。ただし無制限にはしない。

**歯止め（乱用の防止）**

- 対象は **`expiryPeriod` まで残り N 四半期以内**のロットに限る（N は要校正、初期案は 1〜2）
- 対象数量は**そのロットの残数量まで**。新規生産を伴う販売には適用しない
- 値下げ幅は**数学的絶対上限 15.67% を超えない**（超えても成約力が増えないため）
- 処分価格での成約は**専用の reason code**（例 `CLEARANCE_SALE_NEAR_EXPIRY`）を出し、
  通常の値下げと診断上も区別する

**必要な観測**: ロット別の `expiryPeriod` と残数量、`FinishedGoodsUnitCostBreakdown`
（`finance/types.ts:156-206`）。いずれも `ownState` に既にあり、情報境界は広げない。

### 4.3 価格と能力調整の組み合わせ（利益最大化）

三宅さんのご指示の中心である「価格だけでなく能力調整との組み合わせで利益最大化」は、
次の比較式で表現できる。実際の計算式から導ける。

```
選択肢A: 値下げして稼働を埋める
  Δ利益_A = (P − v) × ΔQ − ΔP × (Q + ΔQ)

選択肢B: 価格を維持して能力を縮小する
  Δ利益_B = 削減した固定費（常用人件費 ＋ ライン固定費）
          − 一時費用（解雇コスト）
          − 将来需要が戻ったときの再取得コスト（採用コスト × 確率）

選択肢C: 何もしない（価格維持・能力維持）
  Δ利益_C = 0 − 遊休コスト（idleLaborCost ＋ 稼働しない設備の固定費）
```

A が有利になる条件は式から `ΔQ / (Q + ΔQ) > ΔP / (P − v)` である。
`P − v`（単位限界利益）は `contributionMarginRatio`（`finance/quarterClose.ts:1187`）と
`netRevenue`・販売トン数から算出できる。

**実測値（control 生存期間）を入れると次のようになる。**

| 項目 | 実測値 |
|---|---:|
| 単位限界利益 `P − v` | **$1,068 / トン** |
| 遊休1人あたりの費用 | $1,000 / 四半期 |
| 常用1人の生産能力 | 6 トン / 四半期 |
| **遊休のトンあたり費用** | **$167 / トン** |

つまり **1トン売る価値（$1,068）は、1トン分の人を遊ばせる費用（$167）の 6.4倍**である。
**能力を切るより、値下げしてでも売って稼働を埋めるほうが有利な局面が多い**ことを意味する。
§3.1-A で拡大側の確認期間（2Q）を縮小側（3Q）より短くする根拠でもある。

**ただし現状、AIはこの3つのどれも計算できない。** `P`（実現単価）も `v`（単位変動費）も
`idleLaborCost` も観測できないからである。したがって

> **価格戦略の再設計は、KPI（観測）の拡張なしには成立しない。**
> §5 の観測拡張が価格戦略の前提作業である。

### 4.4 併せて直すもの

- 診断 `PRICE_REDUCTION_FOR_EXCESS_STOCK` が価格調整0でも発火する不整合
  （`decision/sales.ts:83-84` と `:246-255` の条件不一致）
- askPrice が許容範囲外だと throw する（`sales/allocation.ts:41-45`）。
  価格自由度を広げるならAI側で `basePrice × [0.5, 2.0]` を自己制約する
  （エンジン側を clamp に変えるのは、値の由来が追えなくなるので推奨しない）
- `sales/parameters.ts:66-67` のコメント（飽和点20%）の訂正

## 6. 【テーマ7】テスト計画・受入試験案

### 6.1 テスト設計の原則（SAI-5 の学びを最初から適用）

1. **結果水準で検証する** — 「stance が contract になった」ではなく
   「人件費が実際に減り、営業利益が実際に改善した」を見る
2. **単一変数にする** — 機能ON/OFF比較は複数パラメータを同時に変えることがある。
   何を変えたか1つに絞れない比較は因果の証拠にならない
3. **テスト側の計算を実装と別経路にする** — 実装の関数で実装を検証しない
4. **前提は guard ではなく assert にする** — `if (前提) { assert }` は前提が崩れた瞬間に無検証になる
5. **リグレッションを注入して検出力を測る** — 「テストが通る」ではなく「バグを入れたら落ちる」

### 6.2 受入試験シナリオ

#### 能力調整

| ID | シナリオ | 期待される結果（結果水準） |
|---|---|---|

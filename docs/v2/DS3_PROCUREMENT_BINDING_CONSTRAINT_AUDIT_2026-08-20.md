## 結論（先に）

**原料調達は DS3 の binding constraint ではない。**
前回の夜間報告で「原料調達が全社共通のbinding constraint」と述べたのは誤りで、
本監査で撤回する。真の制約は

1. **凍結・包装能力（freezingPackaging）**
2. **共通前処理能力（commonProcessing）**
3. **労働（labor）**

であり、原料は余っている。

分類（§12）:

| 会社 | 分類 | 根拠 |
|---|---|---|
| MASS | **ENGINE_CAPACITY**（凍結包装 → 労働） | 不足理由に rawMaterialShortage が一度も現れない。国内充足率100% |
| JPQ | **ENGINE_CAPACITY**（共通前処理・凍結包装） | 同上 |
| VAP | **ENGINE_CAPACITY**（共通前処理・凍結包装） | 同上 |
| CONSV | **ENGINE_CAPACITY**（共通前処理・凍結包装） | 同上 |
| BAL | **AI_LIQUIDITY_POLICY / ENGINE_FINANCING**（+ 副次的に能力） | scaleRatio 0.75 で国内買付が縮小、輸入も遮断。ただしT32の不足理由の主因も共通前処理・凍結包装 |

`ENGINE_DOMESTIC_SUPPLY` は**否定された**（下記§2）。

## 2. 「国内原料が足りない」は成立しない（§6）

VN国内原料市場の実測（seed平均）:

| Turn | VN総供給 | 実効需要 | 成立量 | **未売却** | 5社の意向 | 5社の実配分 | 価格 |
|---|---|---|---|---|---|---|---|
| T16 | 698,824 | 419,185 | 419,185 | 279,639 | 58,298 | 53,888 | 3.59 |
| T20 | 861,882 | 429,863 | 429,863 | 432,019 | 89,049 | 88,289 | 2.25 |
| T24 | 1,207,567 | 524,016 | 524,016 | 683,551 | 124,259 | 119,016 | 3.59 |
| T28 | 1,484,301 | 529,102 | 529,102 | 955,199 | 124,751 | 124,102 | 3.11 |
| T32 | 1,559,774 | 535,724 | 535,724 | **1,024,050** | 131,372 | 130,724 | 3.08 |

- 成立量 = 実効需要（全Turn）。つまり**数量調整（供給不足）は一度も起きていない**。
- T32時点で **1,024,050t（総供給の66%）が未売却のまま残っている**。5社の購入量は総供給の8.4%にすぎない。

### 「未配分0t」という指標の落とし穴

`DomesticPurchaseAllocationResult.unallocatedSupply` が常に0だったため、
夜間報告では「供給を使い切っている」と誤読した。実際には
`app/lib/v2/turn/runner.ts` が

```
companyAvailableDomesticSupply = transactedVolume × min(1, aggregatedPurchaseIntent / effectiveDemand)
```

として、**会社側へ渡す配分原資を会社側の意向量に比例させている**（外部加工業者需要と分け合う設計）。
供給が充足しているときは `transactedVolume = effectiveDemand` なので
配分原資 ≒ 5社の意向量となり、**未配分が0になるのは定義上の帰結**であって
希少性の証拠ではない。判定は `transactedVolume < effectiveDemand` で行う必要がある。

## 4. MASS 詳細（§5・§9）

T32:

```
生産計画（= AIの必要原料）      59,850 t
  能力プール    共通前処理 63,270 / ライン計 68,785 / 凍結包装 59,850
  → 生産計画は「凍結包装能力 59,850」にちょうど張り付いている

不足理由                       packagingCapacityShortage 5,534t
                               commonCapacityShortage    3,241t
                               laborShortage             2,716t
                               ★ rawMaterialShortage は 0（一度も現れない）
期末原料在庫                   利用可能 27,709 t ＋ 輸送中 17,955 t
```

**「64.5kt作れる会社がなぜ49kt分しか原料を確保しないのか」への回答:**

前提が誤っている。MASSは64.5kt作れない。真の天井は**凍結・包装能力 59,850t**であり、
さらに労働・共通前処理により実生産は53.0ktに留まる。
調達52.6ktは「実際に消費する53.8ktとほぼ同量」であり、在庫を27.7kt保有したまま
消費に見合う量だけを買っている。**AIの調達判断は生産実績と整合しており、過少ではない。**

候補A〜Hの判定:
- A（AI desired がそもそも49kt）→ **該当するが原因ではない**。生産できる量に見合っている
- B（国内allocation cap）→ **否**。充足率100%
- C（輸入cap）→ 輸入は固定15%だが、原料は余っているため増やす必要がない
- D（financing gate）→ **否**。scaleRatio 1.000
- E（timing）→ 輸送中17,955tがあり、定常フローとして機能している
- F（scale mismatch）→ **否**
- G（単位換算）→ **否**（下記§6）
- H → **凍結包装能力・共通前処理能力・労働**が真因

## 6. 単位整合（§10）

比較した数量はすべて **HOSO換算トン／四半期** で統一されており、換算由来の差ではない。
確認済みの対応:

- `productionPlans[].desiredQuantity`（AI生産計画）= HOSO換算トン
- `calculateFactoryEffectiveCapacity` の各プール = HOSO換算トン／四半期
- `domesticPurchasePlan.desiredQuantity` / `importOrders[].orderedQuantity` = HOSO換算トン
- `batch.rawMaterialConsumedTotal` → `batch.finishedGoodsQuantity` の差は加工歩留り（約1.4%）

### ただしベンチマークの「生産能力」列は定義が不完全

`scripts/dynamicScenario3Benchmark.ts:297`

```ts
productionCapacity: Math.min(c.hoso + c.pd + c.vap, c.commonProcessing)
```

**凍結・包装能力（freezingPackaging）が含まれていない。**
MASSでは凍結包装59,850が最小プールであるため、ベンチマークは真の天井を
63,270（共通前処理）と過大に表示していた。「調達 < 生産能力」という見かけの差の
一部はこの定義漏れに由来する。

## 7. 輸入の分析（§7）

- 輸入発注量 = `requiredRawMaterial × importMixRatio(0.15)` の**固定比率**。
  availability・価格差・在庫・現金のいずれも参照していない（`decision/procurement.ts`）。
- したがって「国内が足りないのに輸入を増やさない」という状況は**そもそも起きていない**
  （国内が足りていないという前提が成立しない）。
- 輸入着荷は正常に機能している（T32 MASS 8,978t発注、輸送中17,955t）。
- 輸入遮断（`importOrdersBlocked`）が発生しているのは **BALのみ**（重大延滞・支払不能による）。

**分類: AI_IMPORT_POLICY（固定比率）だが、現時点では制約になっていない。**
将来、国内供給が本当に逼迫した場合には、この固定比率が適応を妨げる設計上のリスクとして残る。

## 9. import ratio 上昇可能性とShockへの含意（§15）

現在の輸入比率17〜19%は `importMixRatio = 0.15` に養殖・在庫調整を加えた結果であり、
**国内供給の逼迫度とは無関係に決まっている**。したがって

- 調達量が増えても輸入比率は 15% 近傍から自然には上がらない
- EC / India shock が経営へ効きにくいのは、輸入比率が構造的に固定されているため

**Shock倍率を上げるべきではない**（指示どおり変更していない）。効かせたいのであれば、
輸入判断を availability / 価格差に応じて動く設計にする（#05）ほうが筋が良い。

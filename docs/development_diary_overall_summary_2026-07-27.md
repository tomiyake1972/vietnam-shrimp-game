## 0. この文書について

日々の開発日誌9本（07-16／17／18／19／20／23／24／25／27）を通読し、プロジェクト開始時点から現在に至るまでの流れを1本の物語として再構成したものである。個々の技術的詳細は各日の日誌・完了報告書に譲り、ここでは「何が、なぜ、どの順番で作られてきたか」という大きな骨格を追う。

## 1. 全体の流れ（要約）

ShrimpXは、既に稼働していたV1（本番の会社経営研修ゲーム）の細部の是正から日誌の記録が始まり、7月18日夜に「V1とは完全に独立した新しい経営シミュレーション基盤」としてV2の開発に着手した。V2はその後10日間で、

**市場価格が決まる → 長期の需給トレンドが供給を動かす → 5社が販売計画を立てて契約を取り合う → 原料を確保し工場で加工する → 財務諸表が意思決定を制約する → 借入・設備投資が時間を伴う → すべてを永続化して中断・再開できるようにする → 実際にプレイヤー（三宅さん）がテストプレイし、そこで見つかった不具合・改善要望を直しながら育てる**

という一連の因果関係を、段階的に、かつ「表示層は再計算しない」「0埋めしない」「新しい経済係数を推測で足さない」という一貫した規律のもとに積み上げてきた。

7月24日からは三宅さんご自身によるテストプレイが本格的に始まり、以降の開発は「エンジンを作る」フェーズから「実際に打った手が正しく反映されるか、テストプレイで確認しながら是正する」フェーズへ性格を変えている。7月27日現在、Phase 8G（Test13是正指示 全10セクション）まで完了し、三宅さんの正式な受け入れ確認を待っている状態である。

テスト件数は、V2着手直前の75件（V1由来の11件を含む）から、現在の**1,651件**まで積み上がった。

## 2. 期間別の詳細

### 2.1 7月16日〜17日：V1の足場固めと会計是正

日誌記録が始まった7月16日時点で、V1は既に本番稼働していた。この2日間はV2着手前の準備期間にあたる。

- **7/16**：本番と完全分離されたテスト環境の基盤（`isTestGame`・環境判定・GM代行操作モード・提出状況モニター・スナップショット保存/復元）を構築。Vercel Marketplaceの制約変化により「Redis物理分離」という当初計画が使えなくなったことが判明し、急遽「同一Redis＋`staging:`キー接頭辞による論理分離」へ設計変更した。「安全側に倒す」という方針を、環境判定・キー検証・エラーメッセージの均質化まで一貫させた。
- **7/17**：V1会社画面のPL表示を、「売上・純利益の2行」から正式な損益計算書構造（売上高→売上原価→売上総利益→販管費→営業利益→支払利息→経常利益）へ拡張し、同日中に会計上の誤り（加工費を販管費側に誤計上）を発見・是正した。

### 2.2 7月18日：V2着手 — Phase 0（コア基盤）

7月18日午前はV1のGMコンソール・貸借対照表の精緻化（未提出企業の非現実的な赤字の是正、貸借一致の設計、在庫繰越、財務諸表の完全形式化）を続けたが、夜からV2の実装に着手した。

V2はV1と物理的に同じRedisを共有しながらも、**V1のコードを一切importしない、完全に独立した名前空間・検証ロジック**として設計された。branded number型（`HosoEqTons`・`UsdPerHosoEqKg`等）、決定論的なターン状態機械（P0〜P8）、`Math.random()`を使わない決定論的乱数（RandomStream）、遅延効果キューという、以降すべてのPhaseが依存する基盤をこの1日で作った。

### 2.3 7月19日：1日でPhase 0〜7Bを駆け抜けた日

V2の歴史上、最も密度の高い1日。テスト件数は75件から769件まで積み上がった。

| Phase | 内容 |
|---|---|
| Phase 1 | 市場・価格形成（4か国HOSO FOB価格、ベトナム国内市場、PD/VAPプレミアム） |
| Phase 2 | 長期シナリオ・イベントエンジン（20種の基礎変数、価格を直接動かさないことを型で強制） |
| Phase 3 | 業界シミュレーション統合テスト環境（`/v2/industry-lab`、32ターン実行） |
| Phase 4 | 販売計画・契約配分（水位法配分、値下げ競争の抜け穴を発見即日修正） |
| Phase 5 | 原料調達・輸入・養殖・在庫（希望数量の過大申告による価格操作の抜け穴を発見即日修正、ターン・オーケストレーター、永続化の最小状態モデル） |
| Phase 6 | 工場・生産・完成品在庫（HOSO換算歩留まりの二重適用・ワーカー重複計上という2件の実質バグを発見即日修正、5社統合テスト環境、ベトナム国内原料価格が下限に張り付く構造問題を特定・7件の是正） |
| Phase 7A/7B | 品質・顧客信頼・納期信頼性とそのダッシュボード（今期の品質結果が今期の受注に遡及しないという因果順序を徹底） |

この日の特徴は、**実装したその日のうちに設計上の抜け穴・二重計上バグを自ら発見し、即座に修正している**ことである（値下げ競争、原料価格操作、歩留まり二重計上、ワーカー重複計上など）。

### 2.4 7月20日：財務諸表が「意思決定を制約するシステム」になった日

Phase 8A（原価計算・運転資本・PL/BS/CF・固変分解）で、財務諸表を単なる結果表示から次の意思決定を制約する仕組みへ格上げした。続くPhase 8B-1（銀行信用・借入限度・支払不能）で資金制約を接続し、Phase 8B-2A（設備投資案件・建設中勘定）で設備投資に時間軸を持たせた。

この日、MASS（大量生産・価格競争型の検証用会社）が「過剰生産→安値販売→在庫滞留→資金繰り悪化→信用低下→支払不能」という経営破綻の連鎖を実際に辿ることを確認し、これがバグではなく経済構造から生じる正当な結果であると判断した。またこの日、開発モデルの運用（Fable「超高」への大規模実装一括依頼が非効率だったことを踏まえ、Fableは複雑な設計判断に限定し、通常実装はSonnet 5が担う）を見直し、以降のPhase 8B以降の効率が改善した。

### 2.5 7月23日：実機検証の価値とPhase 8C-0（永続化設計）

Phase 8B-3（設備投資UI）の実機ブラウザ検証で、「エンジンの上限を超えた投資提案が、例外にもならず画面にも何も表示されない」という、ユニットテストだけでは気づけない不具合を発見・修正した。

続いて、コード変更を一切行わない調査・設計フェーズとしてPhase 8C-0を実施し、「会社ラボ画面が再読込に一切対応していない」という事実を確認したうえで、専用の永続化モデル（`CompanyLabPersistedStateV1`）の設計を提出した。実装と調査・設計を明確に分離するという、以降も踏襲される進め方がここで確立した。

### 2.6 7月24日：永続化の実装とテストプレイ開始

Phase 8C-1（永続化のストレージモデル・Repository・Redis原子コミット）、Phase 8C-2（四半期処理フローへの接続、再開時の履歴注入、冪等性・競合処理）、Phase 8C-3A（HTTP API接続、turnId解決ロジックの自己発見的な設計不備の修正）、Phase 8C-3B（プレイヤー画面接続、セッション管理でSTAGING_ADMIN_TOKEN自体を露出させない設計、ブラウザE2E）を1日で積み上げた。

そして、この日**三宅さんご自身によるテストプレイが実際に始まった**。最初の混乱（V1の旧ゲームへ迷い込む）を解消したのち、三宅さんの指摘から2件の不具合を発見・即日修正している。

1. 営業人員が画面上18人のはずが54人に見える重複配置バグ（市場×商品ごとの行がそれぞれ独立に人員配置を主張できてしまう設計不整合）
2. 資金調達（借入・返済）の入力欄が画面に一度も実装されていなかった抜け漏れ

以降、**「テストプレイで発見し、その場で直す」というサイクルが開発の中心手法**になった。

### 2.7 7月25日：「経営判断できる画面」への転換

新しいエンジン機能は一切追加せず、「三宅さんが実際に経営判断を下せるだけの情報を画面とExcelから取り出せる状態にする」ことに全リソースを充てた日。PL/BS/CF・資金調達・設備投資結果の画面表示、読み取り専用Export API、管理者ダウンロードUIを実装した。

この過程で、Preview環境固有の障害が3段階連続で発生し（Deployment Protectionによる自己fetch遮断→原因不明のfetch失敗→真因の`x-vercel-set-bypass-cookie`ヘッダー）、診断専用のコミットを重ねて原因を特定した。また、三宅さんから「これだけのデータで経営判断ができると思っているのですか」という強い指摘を受け、Export DTOを大幅拡充するとともに、**「Export APIに無い」だけではエンジン不足と判定しない**という規範を確立した。市場パネルの一覧表化・前四半期比表示、加工能力（現時点・現在追加中）の可視化、入力/情報エリアの色分け、`CollapsibleSection`による折りたたみ機能もこの日に実装した（テスト1,347件→1,452件）。

### 2.8 7月26日午前：Phase 8D（設備投資・工場スペース・Worker再設計）

この日は日誌単体のエントリは無いが、Phase 8Dとして、設備投資の実効果（工場スペース会計・Worker人数の永続化・凍結梱包処理能力と冷凍冷蔵保管能力の分離・品質/環境設備効果の開示）を仕上げ、独立監査（承認・一部是正付き）を経て`develop/v2`へ統合した（テスト1,474件→1,523件）。

### 2.9 7月26日午前〜昼：Phase 8F-1（消費国在庫・購買サイクルモデル）

各需要市場（CN/US/EU/JP/OTHER）の「需要」を最終消費・消費者在庫・購買の3つへ分解する`consumerInventory.ts`を新設し、需要配分・仕向市場価格係数を動的化した。旧保存データからの決定論的な後方互換再構築、会社ラボUIへの表形式表示も含め、`develop/v2`へ統合した（テスト1,544件→1,580件）。その後、GM/dev統合テスト画面への配線漏れ修正とラベル改善も同日中に行った。

### 2.10 7月26日夜〜7月27日：Phase 8G（Test13是正指示 全10セクション）

三宅さんの実プレイ（Test13）から起票された是正指示に、Section 0（事前調査）からSection 6（四半期結果スプレッドシートUI）まで全て対応した。

- **Section 0**：初回ターン価格表示バグ・営業配分詰み状態・消費国在庫配線の原因を切り分け
- **Section 1・3**：営業配分の詰み状態解消（`withdrawDraft`操作の新設）と、初回ターン価格の代用値表示バグ修正。`develop/v2`へ統合済み
- **Section 2**：営業人員の追加採用（採用は次四半期から反映、当期の配分・SG&Aには使えないという時間軸を厳密に実装）
- **Section 4**：消費国在庫表示に「前期からの増減方向」を追加
- **Section 5**：輸入原料の到着原価・到着時期の可視化（`ImportLotsPanel`）
- **Section 6**：自社の四半期結果を一覧できるスプレッドシート型UI

全体回帰・Preview確認を経て、三宅さんご自身によるTest13実画面での確認へ進んだ。この過程で2つの行き違い（古いブランチのPreviewを開いていたこと、V1旧ロビー画面とV2 Company Labの別データを混同したこと）が起き、URLの取り違えとその解消を記録した。Test13の実画面で「営業人員の追加採用」節に指示時の例（BAL 18人→採用6人→次期24人）がそのまま表示されることを確認いただいた。

確認と同時に「画面が縦長になる」という追加要望を受け、`CollapsibleSection`のデフォルト開閉状態を「開いている」から「畳んだ状態」へ変更する対応をその場で行った。

テスト件数はこの区間で1,591件→**1,651件**まで積み上がった。`feature/v2-8g-remaining`（現HEAD `a4bcb66`）は、三宅さんの正式な受け入れ確認をもって`develop/v2`へ統合する予定で、現時点ではまだ未統合である。

## 3. 一貫して守られてきた設計規律

12日間・多数のPhaseを通じて、繰り返し確認・強化されてきた規範を横断的にまとめる。

1. **表示・出力層は再計算しない。** UIもExcelもDTOも、エンジンの純粋関数が既に計算・確定した値を書き写すだけにする。これはPhase 7B（ダッシュボード）・Phase 8C-3B（Export DTO）・Phase 8G Section 4〜6まで一貫している。
2. **値が無い箇所は0で埋めず「-」を出す。** 0は「実績としてゼロだった」ことを意味する予約された表現として扱う。
3. **新しい経済係数・閾値を推測で追加しない。** 追加が必要な場面（±8%/±12%の価格クランプ新設など）では、実装せずAskUserQuestionで確認し、三宅さんの判断を仰いでから進める。
4. **安全側に倒す設計は、リスクの性質が変われば見直す。** Redis物理分離が使えなくなった際、「判定できなければ非本番」から「判定できなければ起動を止める」へ踏み込んだ判断がその例。
5. **実装フェーズと調査・設計フェーズを分離する。** Phase 8C-0がその典型で、コードに一切触れずに設計文書だけを提出した。
6. **実機・実プレイでしか見つからない不具合がある。** 設備投資却下の非表示、営業人員54人問題、資金調達UIの欠落、画面が縦長になる問題は、いずれもユニットテストではなく実際の操作・実プレイから見つかっている。
7. **他社・他スコープへの情報混入を許さない。** GM専用データと会社スコープの分離は、Export DTO・四半期結果スプレッドシート・品質ダッシュボードのすべてで個別にテスト固定されている。
8. **重要な統合判断は三宅さんの確認を経てから行う。** develop/v2への統合は各Phaseで独立監査や実機確認を経ており、Phase 8Gも「三宅さんの正式な受け入れ確認」を待って統合する運用を維持している。

### 3.3 Blocker A — 営業基盤が実際の成約に一切効いていなかった

競争力の合計処理が2箇所（公開ヘルパー `computeCompetitivenessWeight` と実エンジン
`allocateMarketProduct` の手書き合計）に分岐しており、**実エンジン側だけ `salesBaseContribution` が
抜けていた**。つまり営業基盤は状態として蓄積されるだけで、成約量・価格・財務結果に一切影響して
いなかった。

合計処理を `sumCompetitivenessContributions` へ一本化し、係数キー→内訳キーの対応表を
マップ型 `{ [K in keyof SalesParameters["competitivenessWeights"]]: ... }` で定義することで、
**係数を1つ足したら合計にも入れるまでコンパイルが通らない構造**にした。加算順は旧手書きと同一の
ため、ウェイト0の既定パラメータでは結果がビット単位で不変。

修正後、他条件が完全に同一なら営業基盤100の会社は営業基盤0の会社より **13.6%多く成約**する。

### 3.4 Blocker B — 供給圧力の分子・分母のスケール不一致

分子が「5社の提示量」（5社だけ）、分母が「全ベトナム対象需要」（市場全体）で母集団が一致して
おらず、圧力が構造的に 1.0 を中心にできなかった。実測では PD 0.27 / VAP 0.49 前後に留まり、
`target = 1 − (pressure − 1) × 感度` が常に1を超えるため、
**供給フィードバックが設計意図と逆の「恒久的なプレミアム引き上げ」として働いていた**
（PD倍率の中央値 1.361）。

ご指示に従い、**係数を調整する前に分子・分母の意味をそろえた**。候補4種を実装し、
`scripts/sai5SupplyPressureStudy.ts` で 4seed × 32Q・SAI-5全機能ON・定義以外は完全に同一の
条件で実測比較した。

| 定義 | PD 圧力中央値 | VAP 圧力中央値 | PD 倍率 | VAP 倍率 | 1.0中心 |
|---|---:|---:|---:|---:|:-:|
| raw_target_demand（旧実装） | 0.268 | 0.492 | 1.361 | 1.251 | × |
| addressable_demand 候補(i) | 0.299 | 0.545 | 1.345 | 1.223 | × |
| neutral_baseline 候補(ii) | 0.830 | 0.658 | 1.078 | 1.153 | △ |
| **completed_supply 候補(iii)【採用】** | **1.026** | **1.102** | **0.991** | **0.948** | **○** |

採用した `completed_supply` は代数的に `1 + (提示量 − 成約量) / 対象需要` と等しく、
「**売りたかったのに売れ残った量が、市場需要の何％にあたるか**」という意味の明確な指標になる。
候補(i)が届かなかったのは「5社が全ベトナム需要に対して能力上小さい」という構造的事実が原因で、
分母の掛け直しでは解消しないため。候補(ii)は市場成長トレンドに対してEWMAが遅れ、恒常的な
下方バイアスが残るため。棄却理由はすべて実測値つきで設計書 §2.3-R に記録した。

構造修正の**後で**しきい値を測り直し、`supplyPressureRetreatThreshold` 1.2→1.14、
`capexOversupplyPressureThreshold` 1.15→1.20 とした（実測分布 PD 1.000〜1.044 / VAP 1.070〜1.318）。

### 3.5 重要指摘 C〜J

- **C**: 実現プレミアム比率に品質プレミアム・稼働率倍率が乗ったまま、それらを含まない基準比率と
  比較していた。ベトナムの品質スコアは基準より高いため、割安シグナルが「常にマイナス＝普及を
  遅らせ続ける」定数バイアスになっていた。両辺を「品質プレミアムを除いたベース比率」にそろえた。
- **D**: 成約強化だけが定額加算で、数年で上限100へ飽和し営業努力が結果に反映されなくなっていた。
  ヘッドルーム `(1 − score/100)` を乗じた。順位が初期値で固定されないことを
  「撤退した先行を、継続営業した後発が追い越す」テストで検証。
- **E**: `validateCompanyLabConfig` が4フィールドしか再構築しておらず、保存した `config.sai5` を
  黙って捨てていた（保存→復元で機能が全OFFに戻り、carry state だけ残る不整合）。
- **F**: turn を `history.length` から導出しており、永続化復元経路（直近1件だけ注入）で破綻していた。
  `scenarioState.currentTurn` を正典とし、さらに前々期の適用構成比を carry state
  （`recentAppliedMixes`）に持たせて履歴の深さに依存しないようにした。
- **G**: `SALES_BASE_ADVANTAGE` が、営業基盤が成約に一切影響しない状況でも発火していた。
  エンジンが実際に使うウェイトを観測へ公開し、正のときだけ発火させる。
- **H**: `PD_CAPACITY_MAINTAINED` が3箇所で定義されているだけで一度も発火しない「実体のない判断」
  だった。当初のご指示にある必須 reason code のため削除せず、
  「VAPが過熱している局面で、投資済みで自力採算の取れているPDを回し続ける」という
  実際の判断へ接続した（4seed×32Qで82回発火）。
- **I**: `salesBaseScore` を計画に載せていたのは Standard AI の販売判断だけで、autoPolicy・
  手入力経路では常に中立50扱いだった。runner 側で正典の状態から一括上書きする形に統一し、
  意思決定側の自己申告値は採用しないようにした。
- **J**: 品質事故の3経路（品質スコア／顧客信頼／営業基盤）を機械的に削除せず、severity 0.5 の
  事故1件の伝播を数値で測定した。3経路は粒度・観測系列・回復速度がすべて異なり三重計上では
  ないことを記録。合計影響は合成競争力の約2%で過大ではなかったが、営業基盤経路が48%と主シグナルの
  品質(39%)を上回り、かつ**営業基盤だけが severity を無視した定額**だった。severity 比例へ統一して
  寄与26%に収め、毀損自体は残した。

### 3.6 「テストが通る」ではなく「バグを入れたら落ちる」

**既存1918件のテストが Blocker A・B を1件も検出できなかった**。原因は、テストが
「状態が蓄積される」「値が有限で範囲内に収まる」しか見ておらず、
**状態が結果を変えるかを一度も確かめていなかった**ことにある。

そこで結果水準の因果テストを追加したうえで、Fable の再監査に
**実際にリグレッションを注入して検出力を測定させた**。その結果、私が追加したテスト自身にも
同種の弱さが見つかり、**2件は「1971テスト中0件しか落ちない」**ことが判明した。

- 因果テスト(1)が Blocker A を検出できなかった — 機能ON/OFF比較は営業基盤以外に
  coverage/relationship/quality の3ウェイトも同時に変わるため、営業基盤の寄与がゼロでも
  「結果が変わった」が成立していた（交絡）。
- `config.sai5.supplyPressureDefinition` の実行時経路が完全に無テストだった
  （runner が config を無視しても全テスト green）。Blocker B と同型の穴。

あわせてトートロジー・恒真 assert を6件、前提不成立のテストを2件検出し、すべて修正した。
特に「内訳の合計を実装の関数で検証していた」箇所は、実装から項を落とすと両辺が同時に変わって
検出できないため、**テスト側で手書きして実装と別経路にした**。

修正後のリグレッション検出力（実測）:

| Blocker A 再現 | 5件（因果テストは素通し） | **6件** |

| config の供給圧力定義を無視 | **0件** | **1件** |

### 3.8 default率の高さ — 構造バグではなく Calibration

default率が高い件は、構造バグかどうかを数値で判定した。

- **ライフサイクルON/OFFで対象需要の合計が8四半期すべて完全一致**（差 0.000000）。
  総需要の増減・二重計上はない。
- 供給圧力の恒等式 `(5社提示量 + 外部供給量) = 対象需要` が実運転で成立。
- 内訳6項目の合計と実配分に使われたウェイトが1,200セルすべてで厳密一致。
- 当期の決定・結果が当期の価格・需要へ遡及する経路はない。

control（全機能OFF）の時点で既に 42.5% であり、SAI-5 が持ち込んだものではない。
lifecycleOnly の 97.5% は、需要が低採算のHOSOへ寄る一方で5社の設備構成が現状の
ライフサイクル曲線に合っていないことによる採算悪化。したがって
**最終的なバランス調整は Calibration として残す**と整理した。

## 7. 今回の学び

1. **結果水準で検証する** — 状態の存在・範囲ではなく、成約量・価格・投資判断・財務結果が
   変わることを見る。1918件のテストが2件のBlockerを見逃した原因はここにあった。
2. **単一変数にする** — 機能フラグのON/OFFは複数パラメータを同時に変えることがある。
   何を変えたのかを1つに絞れないなら、その比較は因果の証拠にならない。
3. **テスト側の計算を実装と別経路にする** — 内訳の合計を実装の関数で検証すると、
   実装から項を落としたとき両辺が同時に変わって検出できない。
4. **前提は guard ではなく assert にする** — `if (前提) { assert }` は前提が崩れた瞬間に無検証になる。
5. **リグレッションを注入して検出力を測る** — 「テストが通る」ではなく「バグを入れたら落ちる」
   ことを確認する。
6. **係数を触る前に、まず分子と分母の意味をそろえる** — Blocker B は感度係数の問題に見えたが、
   実際は定義の問題だった。係数から調整していたら、逆符号のフィードバックを校正で塗り潰していた。

**Phase SAI-6: Standard AI 意思決定強化（設備投資／供給過剰対応／価格戦略強化）** の設計に入る。

SAI-5 で整備された基盤のうち、SAI-6 が直接使えるもの:

- 公開供給圧力（`productSupplyPressureOutlook`、前期末EWMA）と、その実測レンジ
  （PD 1.000〜1.044 / VAP 1.070〜1.318）
- 公開ライフサイクルトレンド（`productLifecycleOutlook`、前期構成比と前期差分）
- 会社×市場×商品の営業基盤（`salesBaseByMarketProduct`）と、成約競争力への実ウェイト
- 拡張設備投資判断の枠組み（成長エントリ・過剰供給リトリート・resume提案）と
  会社別の反応度パラメータ（`growthTrendResponsiveness` / `oversupplyRetreatSensitivity`）

設計時に踏まえるべき既知の制約:

- PD側の供給圧力は本シナリオでは 1.048 を超えず、供給過剰系の判断が発火しない
  （→ SAI-6 で PD 側の過剰対応を扱うなら、しきい値ではなく別のシグナルが必要）
- プレミアムフィードバックは中立1.0以下の片側のみ（R-2）
- 価格戦略は現在「完成品在庫過剰時の値引き（最大 `maxDiscountRatioForExcessStock`）」のみで、
  供給圧力・営業基盤・ライフサイクル局面を価格判断へ接続する経路は未実装

## 0. 本書の読み方

本書は「いつ何をしたか」を並べた作業記録ではなく、**なぜ今のコードがこの形なのか**を後から追えるようにするための通史である。ShrimpX V2 のコードには、一見すると回りくどい設計、あるいは一見すると不要に見える制約が数多く存在するが、そのほとんどは実際に起きた問題への対処として入っている。その経緯を失うと、後任者が「これは要らないだろう」と善意で外してしまい、同じ問題を再発させる。本書はそれを防ぐために書かれている。

記述の粒度は次の方針に従う。フェーズ単位で「何を作ったか」「なぜそう作ったか」「何が壊れて何を直したか」を記し、コミットハッシュとテスト件数を証跡として添える。個々のコードの詳細は KB-01、パラメータの値そのものは KB-03、プレイヤーから見た挙動は KB-02 を参照する。

一次資料は、リポジトリの `docs/development_diary_2026-07-16.md` から `docs/development_diary_2026-07-25.md` までの8本の開発日誌（07-21・07-22 は欠番）、各パラメータファイルのヘッダーコメントに記録された校正履歴、および `git log` である。本書はそれらを統合し、フェーズ横断の因果関係を補って再構成したものである。日誌の原文はリポジトリに残っているので、より細かい事実が必要なときはそちらを直接読むこと。

## 2. 前史（07-16 〜 07-18午前）— V1 とテスト環境

### 2.1 テスト環境の物理分離が使えなくなった日

当初の設計では、本番用とテスト用で別々の Upstash Redis データベースを使う「物理分離」を一次防御としていた。Step 6 完了後、Vercel Marketplace の仕様変更により無料プランで新しい Upstash Redis データベースを追加できなくなったことが判明し、この前提が崩れた。

代替として採用したのが、**同一データベースを共有し `staging:` キー接頭辞のみで論理分離する**方式である。このときの意思決定が重要なので、当時の記録をそのまま要約しておく。

物理分離が失われたことで、環境判定を誤ったときの結果が非対称になった。

- 本番を誤ってテスト扱いにする → 新しい書き込みに `staging:` が付くだけで、既存の本番データは変わらない（軽微、気づきやすい）
- テスト環境を誤って本番扱いにする → プレフィックスなしで本番の実データと同じキー空間に書き込む（重大、気づきにくい）

後者が起きる唯一の経路は、テスト用 Vercel プロジェクトの Production Branch のデプロイに Vercel が自動的に `VERCEL_ENV=production` を設定してしまうことだった。この経路を完全に塞ぐため、**Vercel 上では `APP_ENV` の明示設定を必須にし、未設定・不正値なら例外で起動を停止する**ようにした。従来あった `VERCEL_ENV=production` への自動フォールバックは廃止した。加えて、`app/lib/redis.ts` の Redis クライアントを facade でラップし、書き込み系（`set`/`del`/`lpush`/`lrem`）については実際に Redis へ命令を発行する前に `assertAllowedKeys`（`app/lib/redis.ts:43`、本体は `app/lib/redisKeyGuard.ts:17` の純関数）で全キーを検証する最後の砦を置いた。

> **この設計を後から外してはいけない。** 物理分離が存在しない以上、`APP_ENV` 必須化と `assertAllowedKeys` がテストデータと本番データを分けている唯一の仕組みである。

ここで得られた教訓は、後続のすべてのフェーズに波及している。「安全側のデフォルト」は、リスクの性質が変わると見直しが必要になる。物理分離があった頃は「判定できなければ非本番として扱う」で十分だったが、Redis 共有後は「判定できなければ起動そのものを止める」方が適切になった。

### 2.2 静的プリレンダリングと環境判定

動的セグメントを持たないページは Next.js が静的にプリレンダリングすることがあり、環境変数に基づく判定がビルド時点の値で固定されてしまう問題が発生した。「staging 向けにビルドしてから production 向けの環境変数で起動する」という組み合わせで実際に再現し、ルートレイアウトに `export const dynamic = "force-dynamic"` を置くことで解決した。全ページが動的レンダリングになる点は、安全性を優先して許容している。

### 2.3 V1 側の会計是正（07-17〜18）

V1 では、加工費を販管費側に計上していた会計上の誤りを是正した（`0a2bcf8`）。加工費は製造原価であり売上原価の一部である。原料費と加工費を合算して売上原価とし、固定費のみを販管費とする形に直した。

```
売上高 → 売上原価（原料費＋加工費） → 売上総利益 → 販管費 → 営業利益 → 支払利息 → 経常利益
```

この構造は V2 の Phase 8A にそのまま引き継がれている。V2 の `quarterClose.ts` が原料費・加工費・労務費・工場固定費・遊休人件費をすべて `totalCostOfSales` に含め、SG&A を別立てにしているのは、この日の是正の延長線上にある。

また、未提出（AI担当）企業が全市場で `requested=0` となり売上ゼロのまま費用だけ発生し続けるバグを修正した（`d9af53e`・`53f2f01`）。「保守的な継続運転」という設計思想でデフォルト値を与えるという考え方は、V2 の `autoPolicy.ts` にも受け継がれている。

## 3. Phase 0（07-18夜）— コア基盤

### 3.1 V1 のロジックを意図的に重複させた

`app/lib/v2/core/version.ts` は V1 の `app/lib/env.ts` を import せず、独立して `APP_VERSION`/`APP_ENV` を検証する。`app/lib/v2/redis/redisKeyGuard.ts` も、V1 のキー検証ロジックを import せず、同じ許可ルールをこのファイル内へ**意図的に重複再実装した**。

理由は、V1 と V2 のキー検証ロジックが誤って結合し、片方の変更がもう片方に波及する事故を防ぐことである。DRY 原則に反するが、ここでは「一箇所を直したら本番ゲームが壊れた」という事故のコストの方が高いと判断した。

V2 用の Redis キー（`v2:games`／`v2:game:*`、`staging:v2:games`／`staging:v2:game:*`）は、本番/非本番 × V1/V2 の4象限すべてで近似衝突（例：`staging:v2:game:X` を v1-staging の `staging:game:` と誤認する）を確実に拒否する設計にした。

### 3.2 branded number 型を選んだ理由

`HosoEqTons`・`UsdPerHosoEqKg`・`UsdM`・`Ratio`・`Score0to100`・`PeriodV2` は、実体はただの number として持つ branded（nominal）型 + スマートコンストラクタとして実装した。クラスは不採用とした。

選択理由は三つある。JSON 往復がそのまま通ること、V1 コードとの書き味の落差が小さいこと、ランタイムコストがゼロであること。

トレードオフとして `as HosoEqTons` という型アサーションで境界検証を回避できてしまう問題があり、ESLint での機械的禁止は未実装のまま残っている（改善候補）。

### 3.3 決定論性の確保

`Math.random()` は V2 のどこでも使用しない。文字列シードからハッシュ経由でストリームを生成する `RandomStream`（mulberry32）を使い、同一シードからは常に同一の値列が生成される。この性質は、後の Phase 7A（重大事故の乱数）や Phase 2（Variation モード）でも守られており、「同じ入力からは常に同じ結果が出る」というシミュレーションの再現性の基礎になっている。

`TurnPhase` 状態機械（P0〜P8）は、スキップ（P0→P2）・後退（P1→P0）・二重実行（P1→P1）を機械的に拒否する純粋関数として実装した。

## 4. Phase 1〜3（07-19）— 市場・シナリオ・統合環境

### 4.1 Phase 1：二段階の価格形成

HOSO FOB 価格の算出は二段階に分けた。**Market Opening**（`openHosoMarket`）が国別需給圧力 L_i と世界共通圧力 G を確定するだけで価格には触れず、**Market Clearing**（`clearHosoMarket`）が L_i・G・決定論的ショックから当期価格を確定する。

ベトナム国内未凍結原料市場は、国際 HOSO 価格から導く買付上限・需給調整・按分最低受注ルールを持つ**独立した市場**（`vietnamRawMarket.ts`）として実装し、国際 HOSO 価格計算とは意図的にファイル・型を分離した。ベトナム国内市場の係数変更が国際価格計算に波及しない一方向参照になっている。

PD/VAP プレミアムは、各国の処理能力に対する PD/VAP 需要の稼働率と、国別 `qualityScore` 入力から算出する。**特定国名をハードコードせず**、データから品質優位が自然に立ち上がる設計にしている。

国別需要配分については、完全な数量ベースの softmax 原産地シェア配分（仕様書 §9.1）ではなく、簡略化した世界影響度ウェイト式（§9.2：EC 0.45／IN 0.25／VN 0.18／ID 0.12）を採用した。この簡略化は当時明示的に文書化されたが、後に Phase 6.3 で深刻な副作用を生むことになる（§7.3 を参照）。

### 4.2 Phase 2：価格を設定できないことを型で強制した

シナリオエンジンは 20 種類の「基礎変数」を長期トレンドとイベントで動かすが、**このモジュールは価格を一切直接設定できない**ことを型レベルで強制している。`ScenarioBaseVariable` には価格フィールドが一切存在せず、「疾病 → HOSO 価格 +10%」のような効果は仕様として書けない（コンパイルエラーになる）。

これは「イベントが直接価格をいじれると、価格形成モデルが意味を失う」という判断による。疾病は生残率を下げ、生残率の低下が供給を減らし、供給の減少が需給圧力を通じて価格を上げる——という因果の連鎖を必ず経由させる。

イベントの重複時合成規則も明文化した。乗算的効果（`multiplicative`、重複時は比率同士を乗算。-10% が2つ重なると 0.9×0.9=0.81 で -19%、単純な -20% にはならない）と加算的効果（`additivePoint`、重複時は差分を合算）を区別し、乗算 → 加算 → 変数域へのクランプの順で適用する。

情報開示レベルは `public ⊂ standard ⊂ advanced ⊂ gm` の累積構造とし、ゲーム終了後のみ開示される `postGame` チャネルは他レベルから厳格に隔離した。

### 4.3 Phase 3：情報漏洩を構造的に防ぐ

情報レベル別の表示は、レンダリング時のフィルタではなく、**レコードごとに4レベル分を事前計算して保存する構造**にした。レンダリング時フィルタは「フィルタを一箇所忘れると上位レベルの情報が漏れる」という事故を起こしやすいが、事前計算方式ならレベルごとに別のデータが存在するため、構造的に漏れない。

CLI（`npm run v2:simulate`）は経済ロジックを一切持たない薄いラッパーとし、CLI 出力と UI 直接呼び出しの結果がバイト単位で一致することをテストで確認した。この「表示層・CLI層は再計算しない」という規約は、後の Export API・Excel 生成にも一貫して適用されている。

会社の意思決定機構がまだ存在しなかったため、2ターン目以降の国内調達意向は「直近4四半期の実績調達量の移動平均 × 係数（既定1.0）」で暫定代替し、この仮定を `assumptions.ts` に文書化して UI に常時表示した。この `domesticPurchaseTrailingWindowTurns: 4` は現在も `scenario/parameters.ts` に残っている。

## 5. Phase 4〜5（07-19）— 販売と原料調達、そして最初の抜け穴

### 5.1 Phase 4：値下げ競争の抜け穴（実装15分後に発見）

Phase 4 で水位法（`waterFillAllocate`）による契約配分を実装した約15分後、値下げ競争の抜け穴を発見し即座に修正した（`5b26b1d`）。

当時の価格競争力スコア `priceScore = exp(-priceSensitivity × (askPrice − basePrice)/basePrice)` には上限がなく、値下げすればするほど際限なく成約力が伸びた。極端な安値提示 + 大量の営業人員 + 大量の希望数量を組み合わせれば、1社が需要のほぼ全量を独占できた。

三つの独立したガードレールを設けた。

1. 価格競争力スコアを `[0.5, 1.6]` にクランプする飽和処理
2. 個社の成約上限に「市場需要 × 最大供給者シェア（既定 0.35）」を追加
3. 将来の与信管理システムとの接続点として `approvedAllocationCap`（承認済み取引枠）を追加

このガードレールは「いくら値下げできるか」を制限するものであり、「価格そのもの」を制限するものではない。値引きされた契約が成約後に単価を書き換えられないことも回帰テストで確認している。

> **現在の `maximumSupplierShare = 0.35` は、この日に入った抜け穴対策である。** Turn 2 で BAL の JP VAP が 704.49t で頭打ちになったのは、この制限が意図どおり効いた結果であり、バグではない。

### 5.2 Phase 5：過大申告による価格吊り上げの抜け穴

Phase 4 と同種の抜け穴を原料調達側でも発見・修正した（`da5189b`）。会社が希望数量を意図的に過大申告（例：100万トン）するだけでベトナム国内市場価格を吊り上げられた。

実効購買意向の上限（調達能力・承認済み購買上限・基準供給量 × 最大価格影響シェアの min）を設け、さらに市場価格未満で入札しても取得原価を市場価格未満にはできない下限処理（`unitCost = max(市場価格, 入札価格)`）を導入した。

### 5.3 レイヤーの積み上げ

Phase 5 では、経済ロジックとは別に、実行基盤を独立した責務のレイヤーとして積み上げた。純粋なターン・オーケストレーター `runTurn()`、次ターンへの持ち越しを決める状態遷移層 `buildNextTurnInput`（契約・原料ロットは持ち越し、販売計画・調達意向・輸入発注・養殖計画は毎ターンリセット）、永続化専用の最小状態モデル `PersistedGameStateV2`（ターン実行IDによる二重適用防止＝最初の冪等性ガード）、Redis 永続化アダプター（本番環境での `deleteGame` を無条件拒否）である。

このときに入れた「ターン実行IDによる冪等性」という考え方が、Phase 8C-2/8C-3A の turnId ベース冪等性へ直結している。

## 6. Phase 6（07-19）— 生産、そして歩留まりの二重計上

### 6.1 二つの実質的なバグ

Phase 6 実装直後（`62ab198`）、二件の実質的なバグを発見・修正した。

**歩留まりの二重適用。** 契約・原料・完成品在庫・能力はすべて HOSO 換算トンという共通単位で管理しているにもかかわらず、PD（物理歩留り約 80%）等の**物理**歩留り比率をそのまま HOSO 換算数量に掛けてしまい、物理的な減少を HOSO 換算上の損失として二重計上していた。

修正として、物理歩留り（`physicalYieldRatio`、参照専用）と HOSO 換算上の真の回収率（`saleableRecoveryRatio`、規格外・破損等のみを表す）を明確に分離し、HOSO 換算の数量計算には後者のみを使うようにした。

> **この分離は現在も生きており、極めて壊しやすい。** `production/parameters.ts` の `physicalYieldRatio {hoso: 1.0, pd: 0.54}` は `yieldConversion.ts` の `calculatePhysicalOutputTons` からのみ参照され、永続化されない。`saleableRecoveryRatio` は現在 3商品とも 1.0 である。「PD の歩留まりが 1.0 なのはおかしい」と考えて値をいじると、二重計上が復活する。

**ワーカーの重複計上。** 同じ 100 人の労務力が HOSO・PD・VAP それぞれについて独立に「100人分の能力」として数えられ、実質 300 人分の能力があるかのような計算になっていた。工場ごとの有限な共有人員プールとして水位法で配分する方式に修正した。

## 7. Phase 6.3 の三つの構造的是正（詳説）

### 7.1 調達能力の約100倍補正の撤廃

会社ラボ版には、旧 `COMPANY_LAB_RAW_MATERIALS_PARAMETERS` として、調達能力に一律約 100 倍の補正をかける仕組みがあった。診断の結果、これは調達能力を工場能力の 7〜11 倍にしてしまい、**調達能力という制約が一度も効かない**状態を作っていた。

撤廃し、工場能力連動式に置き換えた。

```
調達能力 = 工場共通原料処理能力 × (0.5 + 1.2 × 人員/(人員+10))
```

人員 8〜20 人で工場能力の 1.03〜1.30 倍となるよう校正した。これにより調達人員を増やす意思決定に意味が生まれ、同時に「調達だけ突出して増やしても工場で処理できない」という自然な上限が生まれた。

現在 `rawMaterials/parameters.ts` に残っている `baselineCapacityTons: 150` / `capacityMaxIncrementTons: 3600` / `capacitySaturationHeadcount: 10` は、工場能力が取得できない場合のフォールバック曲線である。通常経路では `capacityFactoryLinked` の方が使われる。

### 7.2 農家留保価格と数量調整

ベトナム国内市場に、農家が「これ以下では売らない」価格として留保価格 $2.25/kg を導入した。単に価格に下限を置くのではなく、**留保価格を下回る需給状況では価格を下げるのではなく取引数量を絞る**（`quantityRationing`）という形にした点が設計上の要である。

現実の一次産品市場では、価格が生産コストを割り込むと供給者は出荷を止める。価格だけを床でクランプすると「安い価格でいくらでも買える」という非現実的な状態が残るが、数量調整を入れると「安すぎる価格を提示すると買えない」という正しい制約になる。

`absolutePriceFloorUsdPerKg: 0.05` は現在もパラメータに残っているが、これは純粋な数値的バックストップであり、経済的な床は農家留保価格の方である。

### 7.3 国際 HOSO 価格の下限張り付き

Phase 6.2 の診断で、ベースラインシナリオですら IN／ID／VN の HOSO 価格が $0.50 の絶対下限に張り付くことが判明した。原因は二つあった。

**原因1：固定シェアによる需要配分。** Phase 1 で簡略化として採用した世界影響度ウェイト（EC 0.45／IN 0.25／VN 0.18／ID 0.12）は固定値である。一方、供給側は国別に独立に動く。結果として、たとえば EC は需要シェア 45% に対して供給シェア 27% というような恒常的なミスマッチが生じ、それが**永続的な国別需給不均衡**として残り続けた。

**原因2：価格式が積分器になっていた。** 価格式は「不均衡の水準」を直接「価格の変化率」に結びつけている。これは数学的には積分器であり、永続的な不均衡があると、価格は毎四半期削られ続けて発散する。

式そのものを書き直さずに解決するため、三つの対策を入れた。

1. **需要配分を前期価格に応答させる**：`share_i ∝ weight_i × exp(-sensitivity × 相対価格乖離)`。安い国の需要シェアが自然に増え、ミスマッチが自己解消に向かう。
2. **コスト連動アンカーへの平均回帰**：長期アンカー（`initialHosoFobPrice × aquacultureCostIndex`）へ引き戻す項を追加。これにより、永続的な下方圧力 P があっても価格は P / meanReversionRate という**有限の割引**に収束し、発散しなくなる。
3. **国別価格の ±35% クランプ**：需要加重の世界参照価格から一定以上乖離しないよう上下限を設ける。

校正の結果、ベースライン（世界供給 180万t／世界需要 120万t）でアンカー比 −30〜−40% に収束するようになった。下限張り付きは解消したが、供給過剰シナリオでは依然として大幅な下方乖離が残る。これは校正結果として意図されたものである。

対応するパラメータは `market/parameters.ts` の `hosoPriceSelfCorrection`（`demandReallocationPriceSensitivity: 2.0` / `meanReversionRate: 0.8` / `maxCountryDeviationRatioFromReference: 0.35`）である。

## 8. Phase 7A・7B（07-19）— 品質、そして「休止中の警告」

### 8.1 呼び出し順序で遡及効果を防ぐ

Phase 7A で品質・顧客信頼・納期信頼性をターンをまたいで蓄積するようにした。設計上もっとも重要な点は、当期の意思決定を組み立てる `buildCompanyOwnState` が、**当期の品質状態を更新する前の状態を必ず参照する**という呼び出し順序である。

これにより「今期の品質結果が今期の受注に遡及的に影響しない」という制約を、特別な分岐や条件式を一切作らずに満たしている。分岐で実現していたら、後から誰かが順序を入れ替えたときに静かに壊れていた。

### 8.2 数量保存則

規格外の内訳のうち、**廃棄のみが実際の数量損失**であり、格落ち・手直しは記録のみで完成品数量を減らさない。これにより「原料消費 ＝ 完成品数量 ＋ 加工損失」という数量保存則が維持される。

重大事故は市場価格・シナリオイベントの乱数列とは**独立にシード分離された乱数**を使い、同一シードでの完全再現性を保証している。

### 8.3 警告閾値の較正と「事実上休止中の警告」

Phase 7B で警告閾値を較正した際、初期の暫定値では「商品構成複雑度」警告が 98.75% のターンで、「労務稼働率」警告が 61% のターンで誤発火していたことが判明した。5シナリオ × 決定論/変動 × 32ターン（1,600 会社ターン分）の実際の分布に対して較正し直した。

この過程で、5社すべてがほぼ常に3商品を同時生産するため `complexityStress` が 99.37% のバッチで 1.0 に張り付き、実質的にほぼ一定の +0.10 を操業リスクへ加算するだけの信号になっていることを突き止めた（重大事故率を約 0.52% から約 0.92% へ実際に押し上げている）。警告閾値自体は到達不能な範囲に設定されていたため、「事実上休止中の警告カテゴリ」として診断のみ記録し、Phase 8 以降の校正対象とした。

> **この診断は現在も未解決である。** さらに、後の分析で `laborUtilizationRate = totalProduced / totalLaborCapacityAllocated` が構造的に ≈1.0 になり、`utilizationStress` を 1.0 に固定していることも判明している（KB-01 §5.6）。操業リスク 0.565 のうち、稼働率 0.35 と複雑度 0.10 の計 0.45 が実質的に定数として乗っている。品質モデルを本格的に機能させるには、この二つを同時に扱う必要がある。

## 9. Phase 8A・8B（07-20）— 財務が制約になる

### 9.1 Phase 8A で財務諸表が「成績表」でなくなった

Phase 8A で原価計算・運転資本・財務三表・固変分解を実装した。この日の総括にある一文が、このフェーズの意義をよく表している。

> 財務諸表が後から表示される成績表ではなくなった。利益が出ても売掛金や在庫が増えれば現金は減る。現金が減れば信用と借入余力が悪化する。借入できなければ調達が止まる。設備投資を決めても、支払えなければ着工・完成できない。

実際、代表的な BAL の四半期では純利益が約 +10.1 百万 USD である一方、営業 CF は約 −15.7 百万 USD となった。売掛金増加によって「利益は出ているが現金が減る」状態が再現されている。この構造は現在の Test12 Turn 2 でも同じで、純利益 +$9.3M に対して営業 CF は −$56.5M である。

受入前に確認した項目は、生産時廃棄と期限切れ廃棄の二重計上がないこと、初期売掛金の回収が PL へ影響しないこと、輸入未着原料が会計上 Goods in Transit として在庫に含まれること、実際の FIFO 消費と COGS が一致すること、全四半期で BS 貸借一致、CFO+CFI+CFF と現金増減の一致、直接法 CFO と間接法 CFO の一致、全シナリオ×32ターンで NaN／Infinity がないこと、である。

### 9.2 開発モデルの運用見直し

Phase 8A では最上位モデルに大規模実装を一括依頼した結果、約7時間以上を要し、週間枠の約34%を消費した。最終段階で長時間進まなくなり、別モデルへ commit・push を引き継ぐことになった。

この経験から次の運用方針が定まり、以降は大幅に効率が改善した。

- 最上位モデル：複雑な横断設計、経済校正、難しい設計判断に限定
- 標準モデル（高）：通常の大規模実装、テスト、文書化
- 標準モデル：限定的な確認、テスト追加、merge 作業
- **大きな Phase は複数の小 Phase へ分割する**
- 長時間停止時は作業ツリーを保全してモデルを切り替える

Phase 8B が 8B-1／8B-2A／8B-2B／8B-3 に分割されたのは、この見直しの直接の結果である。

### 9.3 Phase 8B-1：MASS の破綻経路

資金繰り・借入・銀行信用を接続した結果、MASS では Phase 8A の事業上の苦境が金融面へ波及した。

```
過剰生産と在庫滞留 → 安値販売と廃棄損 → 営業CF悪化 → 信用区分低下
→ 通常融資停止 → 緊急融資利用 → 国内買付停止 → 支払延滞・支払不能
```

全5シナリオで、MASS は turn 1 のみ healthy、turn 3 以降は 31/32 ターンで paymentDefault となった。**MASS を救済するための会社別ハードコードは行っていない。**

財務状態は healthy / watch / stressed / covenantBreach / paymentArrears / insolvent / paymentDefault の7種類を区別している。赤字・債務超過・現金不足・支払延滞・支払不能を同じ状態にしなかったのは、債務超過でも支払を継続できる場合があり、逆に純資産がプラスでも現金がなければ支払不能になり得るためである。

### 9.4 古いテスト前提と新しい経済構造の衝突

Phase 8B-1 導入後、支払不能となった MASS が国内原料を買えなくなったことで、Phase 6.3 時代のテスト（「全社が自社養殖だけで恒常的に完全自給しない」）が1件失敗した。

これは融資ロジックのバグではなく、**古いテスト前提と新しい経済構造の不整合**であると判断し、テストを二種類に分割した。

- 健全企業が理由なく恒常的完全自給にならないこと
- 支払不能企業では、説明可能な資金制約がある場合に調達停止を許容すること

MASS という会社 ID を特例扱いせず、財務状態と資金制約だけで判定するよう修正した。会社IDによる特例分岐を作らないという原則は、V2 全体を通じて守られている。

### 9.5 Phase 8B-2A：設備投資を「時間のかかる案件」にする

設備投資を「意思決定した瞬間に能力が増える処理」にせず、proposed / approved / underConstruction / suspended / completed / cancelled の6状態を持つ案件として実装した。

工程支払は**全額支払方式**とした。必要額を全額支払えれば工程が1段階進み、全額支払えなければ支払なし・工程進行なし・建設中なら suspended へ移行し、支払済み CIP は維持される。標準工期は暦期間ではなく「支払と工事が成功した四半期数」で判定するため、1四半期中断すれば完成も原則1四半期遅れる。

受入前の重点確認として、**capex がゼロの場合に Phase 8B-1 の結果と完全一致するか**を CC-9 として追加した。PL・BS・CF・次期 finance state を構造全体で比較し、完全一致を確認している。この「新機能を足しても、その機能を使わなければ以前と完全一致する」という後方互換テストの型は、以降のフェーズでも有効な検証パターンである。

この比較の過程で、設備投資支払がゼロの四半期に `investingCashFlow` が `-0` になる問題を発見した。会計上は 0 と等価だが厳密比較では不一致となるため、`finance/quarterClose.ts` で 0 へ正規化した。経済ロジックの変更ではなく数値衛生上の修正である。

また、当初の完了報告で「991件中991件成功」と報告されたのは算術誤記であり、正しくは 944 件だった。テスト件数はランナーの実測値で確認する。

### 9.6 Phase 8B-2C：減価償却方式の是正

`finance/parameters.ts` と `capex/parameters.ts` のヘッダーコメントに記録されているとおり、Phase 8B-2C で減価償却の実装を是正した。

- 財務側：`depreciationRatePerQuarter`（平坦な 2.5%/四半期。定率法と誤って表記されていた）を廃止し、既存資産を建物 35% / 機械 65% に按分したうえで残存耐用四半期（建物 80Q / 機械 32Q）による定額法へ変更
- 設備投資側：案件種別ごとの `usefulLifeQuarters` による定額法を廃止し、建物／機械のコンポーネント別（建物 100Q / 機械 40Q）定額法へ変更。`usefulLifeQuarters` フィールド自体を削除

### 9.7 意図的な非対称性（スナップショットするもの・しないもの）

Phase 8B-2C で入った設計判断のうち、もっとも注意を要するのが次の非対称性である。

- `futureCapacityEffect` は案件承認時に `CapitalProject` へ**スナップショットコピーされ凍結**される
- `buildingRatio` / `machineryRatio` / `maintenanceRatePerQuarter` は**スナップショットせず、毎四半期テンプレートを live 参照**する

つまり、能力効果は承認時のテンプレートで固定されるが、償却比率と保全費率は将来テンプレートを校正すると**既存案件にも遡及適用される**。これは実装指示に基づく意図的な設計であり、バグではない。校正時にはこの非対称性を必ず意識すること。

### 9.8 品質・環境設備が能力を増やさないことの帰結

実装指示 §7 により、品質管理設備と排水・環境設備は能力を増やさず、品質スコア・事故率・規制順守のいずれにも接続されていない。したがって現状は**減価償却と保全費だけが増え、運用上の便益がゼロ**である。

`capex/parameters.ts` のコメントにも「通常のプレイヤー向け提案候補として安易に推奨される投資ではないことに留意」と明記されている。将来これらに効果を与えるのは自然な拡張だが、その際は品質エンジン側の受け口を先に作る必要がある。

同じく実装指示 §3.1 により、HOSO/PD/VAP ラインの増設は共通前処理能力を自動的には増やさない。ボトルネック管理を独立した投資判断にするため、`commonProcessingExpansion` が別案件として用意されている。

## 10. Phase 8C（07-23〜24）— 永続化・API・テストプレイ開始

### 10.1 Phase 8C-0：コードを一切変更しない調査フェーズ

### 10.2 Phase 8C-1／8C-2：復元の正しさ

Phase 8C-2 の最重要要件は、**再開時の直近履歴注入**（監査指摘 AUD-01）だった。turn 2 以降の処理では、current の runtime snapshot に加えて直近確定履歴エントリの `record` を必ず復元時に注入する。

「中断なし連続実行」と「毎四半期の保存・復元を挟んだ実行」が、4四半期・全状態フィールドの deepEqual で完全一致することを回帰テスト化し、**履歴注入を外すと実際に乖離することもネガティブコントロールで確認**している。ネガティブコントロールまで取ってあるので、この回帰テストは信頼できる。

冪等性の実装で注意を要するのは判定順序である。commit 成功時に draft は原子的に削除されるため、同一 turnId 再試行の判定（`current.lastProcessedTurnId === turnId`）を draft 確認より先に行わなければならない。順序を誤ると、正当な再試行が `DraftNotFound` に誤変換される。

ロック TTL の検証は、実時間で待つテストを書かず、in-memory 版は論理時刻、Redis 版はキー削除による TTL 到達の模擬という決定論的方法で行った。安全性の中核は TTL の精度ではなく、原子コミット時のロックトークン検証にある。

### 10.3 Phase 8C-3A：turnId 解決の設計不備を自己発見

本フェーズ最大の技術的山場。当初「毎回 `currentTurn` から `turn-${currentTurn}` を再計算する」方式で実装したところ、自作の冪等性テストで、**turnId ベース冪等性が本来守るべき主要シナリオそのもの**（コミットは成功したが応答が失われクライアントが再送する）が壊れていることが判明した。

コミット成功時に draft が原子削除され `currentTurn` が進むため、再送時の再計算が誤って次 turn 向けの値になり `DRAFT_NOT_FOUND` へ倒れていた。`turnId.ts` に優先順位ベースの解決関数 `resolveNewDraftTurnId`（draft 保存用）と `resolveInFlightTurnId`（提出・処理用。draft 不在時は `current.lastProcessedTurnId` を優先）を追加して修正した。

**自分で書いたテストが自分の設計不備を捕まえた**という点で、このケースは冪等性テストを書く価値をよく示している。

### 10.4 Phase 8C-3B：`playerCompanyId` の扱い

8C-3A 時点では `playerCompanyId` がどこにも永続化されず、API 層が `"BAL"` 固定で渡していた。これを廃止し、ラボ作成時の必須パラメータかつ `CompanyLabPersistedStateV1` の不変フィールドへ変更した。

このとき採用した設計判断が特徴的である。単に検証を追加するのではなく、**`ProcessQuarterInput` から `playerCompanyId` フィールド自体を完全に削除**し、`processQuarter()` は内部で `stored.playerCompanyId` のみを参照するようにした。これにより「処理リクエストごとに別会社へ差し替える」ことが実装上そもそも不可能になる。フィールドが存在しない以上、悪意によってもバグによっても渡しようがない。

**検証で防ぐより、渡せなくする方が強い。** この原則は他の箇所にも適用できる。

### 10.5 トークンをブラウザへ出さない構造

`app/lib/companyLabUiSession.ts` は、ログイン時に一度だけ `STAGING_ADMIN_TOKEN` を検証し、成功したら**トークン自体を含まない署名付き opaque セッション値**を HttpOnly・Secure・SameSite=Lax の cookie へ書き込む。署名鍵はトークンから都度導出する（ドメイン分離文字列を前置）ため、トークンをローテーションすると全セッションが自動失効する。以後の画面・操作はセッション Cookie だけを検証し、トークン自体を読み返すことは一切ない。

ブラウザ → 永続化状態への経路は、同一 Next.js アプリ内での自己 HTTP fetch を避け、Server Component・Server Action から `handlers.ts` の関数をサーバー側から直接呼ぶ構成にした。状態変更を伴う全 Server Action には、Next.js 組み込みの Origin 検証に加えてアプリケーション層でも `assertSameOriginRequest` を多重防御として追加している。

本番ビルドの client bundle に管理トークンの値が一切含まれないことを grep で確認済みである。

### 11.6 加工能力の可視化（`24f74fe`／`ed7b8ab`）

工場の現時点能力と現在追加中（設備投資により将来加わる）能力を、Excel と意思決定画面の両方に出力した。あわせて入力エリア（sky）と情報エリア（gray）の色分けを導入し、各情報を `<details>` / `CollapsibleSection` で折りたためるようにした。amber/rose は警告・エラー専用として予約している。

続く `ed7b8ab` では、優先順位に基づく処理見込みと実効率の内訳を表示した。ここで 85.5% という実効率の由来を明示した。

```
実効能力 = 名目能力 × baseUtilizationRate(0.9) × equipmentAvailabilityRate(0.95) = 名目 × 0.855
```

補正係数はこの二つだけであり、5つの能力プールすべてに一律に適用される（`calculateFactoryEffectiveCapacity` in `production/capacity.ts`）。工場が `active` でなければ全能力が 0 になる。

このとき、依頼者の指示文に書かれていた制約順序（共通能力 → 商品別能力 → 冷凍・包装能力）が、実際のエンジンの順序と異なることを発見し、報告した。正しい順序は次のとおりである。

```
① 原料在庫（status === "available" のロットのみ）
② 工場共通処理能力
③ 冷凍・包装能力
④ 商品別設備能力
⑤ 有効労働能力
```

歩留まり（`saleableRecoveryRatio`）は ② と ③ の間で一度だけ適用される。優先順位は**数字が小さいほど高優先**であり、同順位は水位法で比例配分される（入力配列の順序には一切依存しない）。

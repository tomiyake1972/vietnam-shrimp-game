# 開発日誌

最終更新: 2026-07-15

## この開発日誌の目的

このプロジェクトでは、「ベトナムエビ産業経営シミュレーション」というゲームそのものの開発に加えて、**AIを使ったバイブコーディング（vibe coding）の学習記録**も重要な成果物として残すことを目的としている。

開発日誌には、単なる作業ログではなく、次の観点を記録する。

- その日に実施したこと
- 実装・修正した内容
- 決定した仕様
- 学んだ技術や考え方
- AIへの指示でうまくいった点
- 失敗した点・詰まった点
- 未解決事項
- 次にやること

コードの変更履歴はGitのコミット・PRを見れば分かるが、「なぜその実装にしたか」「AIにどう指示したらうまくいった／いかなかったか」「その日何を理解したか」といった思考の過程は、コミットログだけでは残らない。この開発日誌は、その部分を補うためのものである。

## 命名規則

- ファイル名は `YYYY-MM-DD.md`（例：`2026-07-15.md`）とする。
- 1日に複数の作業セッションがあった場合も、原則として1日1ファイルにまとめる。
- 保存場所は `docs/development_log/` 直下。

## 記録のタイミング

- 原則として、その日の開発作業が終了した時点で1ファイルを追加する。
- 作業が複数日にまたがる場合は、区切りの良いタイミング（その日の作業終了時）ごとに記録する。

## 何を記録するか

単なる作業記録（「〇〇を実装した」）だけでは終わらせず、以下も合わせて記録する。

- **技術学習**：新しく知った技術・仕組み・注意点
- **判断理由**：なぜその実装・仕様を選んだか（他の選択肢との比較を含む）
- **失敗・詰まった点**：うまくいかなかったこと、遠回りしたこと
- **改善点**：次回はどう変えるか、AIへの指示をどう変えるとよいか

## 仕様変更との関係

開発日誌の中で重要な設計変更・仕様決定が生まれた場合は、その日誌に書くだけで終わらせず、必要に応じて `docs/decision_log.md`（仕様変更の正式な記録）にも反映する。開発日誌は「その日の思考の記録」、`decision_log.md`は「確定した仕様変更の正式な記録」という役割分担とする。

## コード変更との関係

日誌の中でコードの変更に触れる場合、該当するコミットやプルリクエストが存在するときは、そのハッシュ値やPR番号・リンクを可能な範囲で「関連ファイル・コミット」欄に記載する。日誌自体はコードの変更内容を再掲する場所ではなく、変更の背景・理由・学びを記録する場所とする。

## 日誌テンプレート

新しい日誌を作成する際は、以下のテンプレートをコピーして使用する。

```markdown
# 開発日誌 YYYY-MM-DD

## 今日の目的

## 実施したこと

## 実装・変更内容

## 決定したこと

## 学んだこと

## AI活用の記録
### うまくいった指示
### 改善が必要だった指示

## 問題・詰まった点

## 未解決事項

## 次にやること

## 関連ファイル・コミット
```
